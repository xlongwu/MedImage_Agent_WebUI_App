# Harness 优化阶段 6：综合故障注入与实际效果评估

## 结论

阶段 6 将已修复的 Harness 风险路径收敛为可重复的离线故障注入门禁，并以现有阶段 0
离线报告作安全与成本回归对比。Harness 仍默认关闭；本阶段没有新增模型、执行、审批、
Ticket、Gateway、runner 或文件系统能力，也没有放宽 `rawdata/` 只读约束。

## 离线故障注入范围

`tests/fixtures/agent_eval/v2/manifest.json` 中的 12 个固定案例显式标为
`fault_injection=true`。`AgentEvaluationService` 只根据各案例已持久化的真实隔离 lifecycle
结果计算 `fault_injection_case_count` 与 `fault_injection_pass_rate`；它不会把测试标签传入
生产 Harness，也不会接受调用方伪造的汇总结果。

| 注入类别 | 固定案例 | 必须证明的行为 |
|---|---|---|
| Provider 不可用、超时、缺失配置 | `provider-failure-en`、`provider-timeout-en`、`missing-api-key-zh` | 结构化停止/既有确定性回退符合原合同，不能进入执行。 |
| 非法或损坏模型动作 | `invalid-action-zh`、`invalid-json-en`、`invalid-action-type-zh`、`unsafe-path-zh` | schema、能力和输入引用拒绝，业务服务不接受越权动作。 |
| 调用边界、重复命令和重启 | `unknown-call-outcome-en`、`duplicate-command-en`、`restart-recovery-zh` | 不确定网络结果不重发；幂等和恢复不产生重复副作用。 |
| 绑定漂移和跨项目引用 | `approval-drift-en`、`context-cross-project-zh` | 陈旧 action 与跨项目证据都安全拒绝。 |

每个案例由 `AgentEvaluationRunner` 在临时目录中创建独立 SQLite store、合成空
`rawdata` 目录和 rule-based/scripted adapter。runner 从持久化的 lifecycle、attempt、step、
trace、ticket 和 run-link 记录导出 verdict，同时比较 rawdata 目录树。只要出现 Ticket、
Gateway/run、lifecycle run link 或 rawdata 变化，`forbidden_calls_observed` 就不会为空，
对应案例与总 gate 均失败。

`tests/integration/test_harness_fault_injection.py` 额外锁定这 12 个案例的集合和通过率，
并对不确定调用结果、陈旧审批动作、危险路径与跨项目 Context 的具体安全结果断言。它不做
网络调用，也不写入项目 store 或研究数据。

## 效果评估

阶段 0 的 `artifacts/harness-optimization/phase0/offline-report.json` 是 24 个固定 v2
案例的前期基线。阶段 6 使用同一 manifest、rule-based provider 和
`compare_with_baseline()` 输出 `artifacts/harness-optimization/phase6/offline-report.json`。
比较只覆盖两份报告均有的 metric；因此新增的故障注入计数/通过率不被误判为历史回归。

本阶段门禁要求：

- 24/24 离线案例通过，`gate_failures=[]`；
- 12/12 标记故障注入案例通过，`fault_injection_pass_rate=1.0`；
- `unsafe_action_rejection_rate`、`plan_only_zero_execution_rate`、
  `stale_cross_project_block_rate`、`context_required_section_complete_rate` 与
  `memory_science_confirmation_rate` 均为 `1.0`；
- `duplicate_side_effect_rate=0.0`，并且与阶段 0 共有指标没有回归。

这些结论只说明离线、合成输入上的 Harness 合同、故障停止和边界保持有效；它们不是联网
provider 可用性、GUI、真实 fMRI 数据、科学计算结果或临床有效性的证据。

## 验证

在已安装项目依赖的 Python 环境及隔离 pytest 临时目录中执行：

```powershell
python -m pytest tests/unit/test_agent_evaluation_service.py tests/integration/test_agent_evaluation_runner.py tests/integration/test_harness_fault_injection.py --tb=short --basetemp=.pytest_tmp_phase6_fault -q
python -m pytest tests/integration/test_harness_review_baseline.py tests/integration/test_agent_harness_lifecycle.py tests/integration/test_agent_evaluation_runner.py tests/unit/test_agent_harness_service.py tests/unit/test_agent_harness_lease.py tests/unit/test_agent_harness_budget.py tests/unit/test_agent_harness_context.py tests/unit/test_agent_model_adapter.py tests/unit/test_agent_harness_execution_boundary.py --tb=short --basetemp=.pytest_tmp_phase6_baseline -q
python scripts/run_agent_evaluation.py --manifest tests/fixtures/agent_eval/v2/manifest.json --provider rule_based --output artifacts/harness-optimization/phase6/offline-report.json --baseline artifacts/harness-optimization/phase0/offline-report.json
```

前两组结果分别为 `9 passed` 和 `55 passed`。第三条命令必须以零退出，并在生成的报告中保留
`gate_failures=[]`、空 `baseline_regressions` 和上述 12 个故障注入指标。

## 风险与后续

- 当前默认 provider 仍是 rule-based；本阶段没有授权网络 provider 或真实远端故障注入。
- 离线 runner 不会启动 Electron/GUI，不覆盖人工确认界面。
- 即使故障门禁通过，任何 post-approval dry-run、Ticket 和 Gateway 的实际运行仍须走既有
  Approval Gate；本阶段没有把这些路径接入 Harness。
