## 一、目标与实施原则

本方案依据当时的 Harness 审查结果（一次性分析材料，未纳入仓库），并核对了当前 Harness、调度器、状态协调器、记忆检索、数据结构及测试入口。

**目标：先解决任务断链、重试失效和恢复不完整，再改善上下文与记忆的实际使用效果。**

已确定：

- 完整覆盖可靠性、预算、记忆、上下文和评估，按阶段验收。
- 离线评估必须完成；联网模型评估作为独立验收项。
- 持久格式切换前先处理活动任务；不迁移、不兼容读取旧格式，不自动删除旧数据。
- 保留两个模型动作：`request_decision`、`draft_plan`。本期不增加 Agent、科学执行节点或通用工具。
- Harness 默认关闭；所有阶段均保留审批、Ticket、Gateway、rawdata 只读和 GET 无副作用约束。

审查中的“已复现问题”“源码风险”“优化建议”分别处理，不把建议直接视为已确认缺陷。本轮只制定方案，不执行修复。

### 阶段安排

| 阶段 | 主要交付 | 人工验收重点 |
|---|---|---|
| 0 | 复现测试与行为基线 | 测试是否真正经过出错调用链 |
| 1 | 提问、回答、动作提交闭环 | 能回答、能继续、不重复提交 |
| 2 | 自动重试与调用崩溃恢复 | 自动继续，结果未知时不重发 |
| 3 | 中间状态恢复、长任务与预算 | 等待用户不耗预算，长任务不失去跟踪 |
| 4 | 记忆检索及用途接入 | 旧记忆可召回，建议确实进入允许的消费者 |
| 5 | 上下文完整性与请求预算 | 长目标不丢限制，完整请求调用前受检 |
| 6 | 综合故障注入与效果评估 | 有证据证明可靠性与实际效果 |

每阶段独立提交评审；前一阶段未通过验收，不进入依赖它的阶段。故障测试从阶段 0 开始编写，不集中留到阶段 6。

## 二、逐阶段实施内容

### 阶段 0：建立可重复的修复基线

**任务模式：Architecture / Refactor，限只读分析和测试准备。**

#### 具体工作

1. 为审查问题建立逐项清单：触发条件、当前实际结果、预期结果、测试入口、修复阶段。
2. 使用临时 SQLite 和 scripted provider，通过真实 service 调用链补充以下复现测试：
   - 首次模型提问后提交回答。
   - 延迟重试入队后，不再发送任何命令。
   - 在 provider 调用边界中断并重新创建服务。
   - 在 `OBSERVING`、`EVALUATING` 状态重新启动。
   - 201 条记忆中，仅最旧记录匹配关键词。
   - 用户等待超过 300 秒后回答。
   - Action 状态冲突返回结构化错误。
3. 保存现有离线评估结果作为后续比较基线。
4. 核对存储事务、租约、状态机和前端消费者，记录每项修改涉及的完整调用链。

#### 人工 review 材料

一张问题对照表，以及每项测试的“输入 → 实际结果 → 预期结果”。崩溃用例必须从生产代码生成账本，再注入中断，不能只手工构造理想记录。

**通过条件：** 每个确认缺陷都有可失败的回归测试；尚不能复现的风险明确标为待验证，不写成已证明。

### 阶段 1：修复提问与动作提交闭环

**主要模块：Harness Service、Planning Action Service、Planning Service、事务存储。**

#### 具体改动

1. **显式传递本次输入来源。**
   - Action 执行接收服务端产生的 `action_id`、`context_hash`、`evidence_snapshot_hash`。
   - 来源取自本步已持久化 Context，不从 lifecycle 中重新猜测。
   - 删除 `harness-evidence-unavailable` 占位路径；缺少真实证据时停止，不生成可回答的问题。

2. **将问题和输入来源一起提交。**
   - 同一事务保存 pending decision、来源 hash、生命周期变化及关联事件。
   - 回答仍校验 batch、有效期、项目、计划及证据一致性。
   - 证据已改变时明确提示重新确认，不能放宽校验让旧回答通过。

3. **建立动作与业务结果的确定关联。**
   - `AgentActionRecord` 保存已生成的 decision batch 或 Reviewed Plan 的 ID/hash。
   - 使用稳定 action ID 作为业务提交幂等依据。
   - 崩溃恢复先查该动作已提交的结果，不能仅凭生命周期状态推断“已完成”。
   - 多记录业务写入以一个事务完成；纯计划计算可在事务外进行，最终提交时重新校验输入版本。

4. 修复 `self.code` 引起的 `AttributeError`，返回现有结构化冲突错误。
5. 已确认答案仍适用于当前证据时，拒绝重复提问；使用 decision kind、确认值和证据绑定判断，不按问题文字相似度判断。

#### 人工验收场景

| 操作 | 预期 |
|---|---|
| 创建任务，模型首次提问，提交答案 | 进入后续规划，不报占位 hash 导致的过期 |
| 重复提交同一 answer command | 返回原结果，不重复推进 |
| 提问后改变项目证据 | 拒绝旧答案，并给出重新确认说明 |
| 业务提交成功、动作账本更新前中断 | 重启后关联原结果，不生成第二个问题或计划 |
| 用错误 expected state 提交 Action | 返回冲突错误，无 `AttributeError` |

**通过条件：** 创建、提问、回答、继续规划、重启恢复全链通过；审批前执行调用次数为 0。

### 阶段 2：修复自动重试和模型调用恢复

#### A. 调度器到期唤醒

- 存储层增加“最近可处理时间”查询，包含 pending/retry 到期时间和已占用任务的租约到期时间。
- worker 无到期任务时等待最近时间；新任务通过条件通知提前唤醒。
- 空队列退出、通知和 worker owner 更新共用同步保护，消除“通知到达但线程正退出”的丢唤醒窗口。
- 启动恢复必须安排未来 RETRY 的唤醒，不能只消费当前到期记录。
- 长模型调用期间续租；所有提交继续检查 owner 和租约，旧 owner 不得覆盖新 owner。
- shutdown 唤醒等待线程、停止新 claim，并有界等待自己的工作结束。

#### B. 有限重试

采用明确默认值：

- 同一 wake 最多尝试 **5 次，包含首次**。
- 保留现有指数退避及 30 秒间隔上限。
- 明确未发送的暂时错误允许重试。
- 配置、权限、schema 和不变量错误直接停止。
- 结果未知不进入普通重试。
- 次数耗尽后，以结构化原因进入 `HUMAN_HANDOFF`，同时关闭该 wake，避免重启再入队。
- 新用户命令产生新的受控推进机会，不在后台自动清零次数。

#### C. 调用发送状态

用明确的发送状态替代 `network_called` 作为恢复判断依据：

| 状态 | 含义 | 恢复处理 |
|---|---|---|
| `not_sent` | 尚未跨越 provider 边界 | 可在预算内继续 |
| `may_have_been_sent` | 已持久化发送意图，可能已发送 | 结果未知，禁止自动重发 |
| `response_received` | 已取得并持久化响应结果 | 使用已保存结果继续 |

- 网络调用前，先持久化 `may_have_been_sent` 并预占一次调用额度；失败则不调用 provider。
- 明确证明未发送时才能释放预占额度；未知请求保留额度占用。
- rule-based 路径不预占网络额度。
- 返回后的类型错误、解析错误不能再把发送状态改成“未发送”。
- Trace、Replay、预算统计和不变量检查同步使用新语义。

#### 通过条件

无后续用户操作时，重试仍发生；重启后未来重试仍发生；双 worker 不重复提交；发送边界中断后 provider 不被再次调用；未知 token usage 保持未知。

### 阶段 3：补齐恢复入口，分离等待与工作时间

#### A. 每类持久状态明确下一步

| 持久状态 | 恢复行为 |
|---|---|
| 规划中间状态 | 通过现有规划 wake 继续 |
| 等待输入、科学决策、审批 | 保持等待，不自动回答或批准 |
| 已批准但执行结果未确定 | 核对审批、Ticket、Gateway 记录；不确定时人工接管 |
| `RUNNING`、`RETRYING`、`RECOVERING` | 查询原 run 的执行证据，不另建 run |
| `OBSERVING` | 复用已有 Observation，缺失时按确定性入口补齐 |
| `EVALUATING` | 复用已有 Evaluation，继续提交目标判断 |
| `DIAGNOSING` | 生成或复用唯一恢复提案 |
| 恢复提案待审批 | 展示待审批状态，不自动执行 |
| 终态 | 无后台推进 |

Observation、Evaluation 和恢复提案的生成、关联与状态提交必须可幂等恢复。证据不足或互相冲突时进入人工接管，不能补造成功结果。

#### B. 长任务监控

- 保留单次有界检查，但到界限后必须持久化下一次协调时间。
- 使用独立的执行协调任务类型和 handler；规划 scheduler 不获得执行能力。
- 同一 lifecycle/run 只允许一个有效协调 owner。
- 启动扫描采用分页续扫，不能因前 20 条或时间上限而永久漏掉后续任务。
- run 终态事件提前唤醒；到期检查保证事件遗漏后仍能推进。
- GET/list 仅返回投影，不补登记、不协调、不调用模型。

#### C. 三种时间分别计算

| 时间 | 默认处理 |
|---|---|
| Harness 活跃工作预算 | 保留 300 秒累计上限，只计算实际处理 step 的时间 |
| 单次模型请求超时 | 使用现有请求配置，并受剩余活跃预算约束 |
| 用户决策有效期 | 保留 24 小时；与模型工作预算分开 |

- 排队、用户等待和后台退避不消耗活跃工作预算。
- 持久化已用时间及当前工作区间；重启不能重置累计预算。
- 崩溃区间按已持久化请求期限/租约边界保守结算，不将停机时间无限计入。
- 正常调用和 repair 使用同一套调用前预算检查。

#### 人工验收

使用可控时钟模拟等待 10 分钟、运行 20 分钟和应用重启。要求答案仍可接受、原 run 完成后自动收敛到终态、恢复提案最多一份；真实证据变化仍使旧答案失效。

### 阶段 4：修复记忆召回，明确实际消费者

#### A. 检索顺序

1. FTS 命中直接关联 Memory SQLite 权威记录。
2. 在候选截断前完成项目、active 状态、有效期和敏感等级过滤。
3. 合并置顶项和 canonical key 匹配项，按 memory ID 去重。
4. 保留现有置顶、显式用户来源、相关度、更新时间、ID 的排序规则。
5. 最后应用候选数量与 Context 字节预算。

删除“先取最新 200 条，再筛 FTS 命中”的处理。

#### B. 中文检索

- 英文保留现有规范化分词。
- 中文增加确定性的连续汉字二元词项，单字查询保留单字项。
- 写入索引与查询共用同一处理函数，不新增模型分词服务。
- FTS 是可重建索引，只从当前权威记忆重建；不得从已遗忘来源重建。
- 覆盖自然中文、中文夹英文、同义表述、无关近似词和长查询。

#### C. 记忆用途

| 类型 | 允许用途 | 必须限制 |
|---|---|---|
| 非科学偏好 | 在用户未指定时，建议语言、展示方式等已有选项 | 不改变科学参数、审批或写路径 |
| 科学建议 | 生成 typed decision suggestion | 当前任务重新确认后才进入计划 |
| 失败经验 | 为 Harness 提供脱敏原因和建议检查项 | 不能作为当前环境事实 |
| 过期或冲突记忆 | 显示冲突/过期提示 | 不自动选择一个值 |

普通记忆增加受限的建议内容投影，不能只留下无法参与判断的来源 ID；保留来源、revision hash 和用途。`planner_constraints` 不用于注入未经确认的科学参数。

**通过条件：** 最旧唯一命中可召回；跨项目、过期、遗忘及限制级内容不泄露；来源变更使 Context hash 改变；科学建议未确认时不进入执行计划。

### 阶段 5：保护目标完整性，检查完整模型请求

#### A. 目标及字段投影

- 移除目标固定截取 512 字符的行为，在允许预算内保留完整脱敏目标。
- 从已有目标合同和用户确认数据投影范围、禁止项、输出要求；不额外调用模型推断这些字段。
- 完整目标和必需字段超限时返回明确错误，请用户缩小目标，禁止静默丢弃末尾限制。
- 每个 section 使用明确字段白名单，替换按 `image`、`log` 等宽泛名称误删字段的逻辑。
- 数组和嵌套对象裁剪统一记录字段、原数量、保留数量和省略原因。
- ID/hash、科学确认值和执行限制不得截断。

#### B. 完整请求检查

在 `CanonicalModelRequest` 构建后、调用前检查：

- system prompt；
- Product Skill；
- Context；
- Action JSON Schema；
- model parameters；
- 预留输出量。

保留 Context 32 KiB 上限，并增加完整请求字节上限，默认 **64 KiB**。必需内容超限则停止，不继续裁剪用户限制。

Token 策略：

- 未启用 token 限额时，保留实际 usage 统计和未知值。
- 启用严格限额时，要求 provider profile 具备可信计数和输出上限能力；不具备时明确拒绝该配置。
- 正常请求和 repair 都先检查剩余额度，再限制输出上限。
- 估算值与实际 usage 分开记录，不把估算声明为实际消耗。

**人工验收：** 将“不执行计算”“不修改 rawdata”等限制放在长目标末尾，确认仍在请求中；增大 Skill/schema 使完整请求超限，确认 provider 调用次数为 0。

### 阶段 6：综合故障注入和实际效果评估

#### A. 必须通过的离线验收

在现有评估集上增加：

- 首次提问后回答、同答案重复提交、模型重复提问；
- 未来重试、重启后重试、租约过期、重试耗尽；
- 请求发送前、发送意图提交后、响应后、动作提交后的中断；
- 各中间状态重启、超过监控时限、启动扫描超过一批；
- 旧记忆、中文检索、冲突记忆、遗忘后检索；
- 长目标末尾约束、必需 section 超限、repair 预算不足。

通过门槛：

- 新增缺陷回归全部通过。
- 审批前执行、未知请求自动重发、重复业务提交均为 0。
- 安全拒绝、项目隔离和科学建议确认指标为 100%。
- 原有无关功能不回退。

#### B. 独立联网评估

比较三组：关闭 Harness 的确定性路径、修复前 Harness、完成优化的 Harness。

- 使用同一批无研究数据的中英文任务、相同 provider/model 配置，每个任务重复 3 次。
- 记录完成率、必要提问遗漏、重复提问、交互轮次、耗时、调用次数和实际 token。
- 缺少 usage 的案例不填 0；价格未确定时只报告 token，不编造费用。
- 在执行前登记模型、endpoint 配置指纹、额度和总调用上限；凭据不进入报告。
- 联网前必须单独确定上述配置和额度；这属于实验输入，不影响离线阶段实施。

只有安全门槛全部通过、完成率不下降，且成功任务的多余交互减少，才能声明观察到效果改善。未达到时如实报告，不更换案例或放宽门槛。

## 三、接口、格式和切换要求

### 需要同步更新的接口

| 变化 | 同步范围 |
|---|---|
| Action 来源与业务结果引用 | Service 参数、Action record、存储、Trace、Replay |
| 发送状态和调用预占 | ModelCallRecord、Attempt、provider adapter、预算与不变量 |
| 到期任务与租约 | ProjectStore Protocol、SQLite 实现、测试替身、应用生命周期 |
| 活跃工作时间 | Attempt、Context budget、只读 summary、前端类型与中英文文案 |
| 记忆建议和裁剪说明 | MemoryContext、Context schema、hash policy、消费者和评估 |

### 持久格式切换

2. 无法安全结束的科学 run 是切换阻塞，不通过删除记录或强制结束来解决。
3. 新格式提升对应 schema/policy version，同步替换所有消费者。
4. 旧格式保留；访问时返回明确“不支持该记录版本”，不兼容读取、不自动迁移。
