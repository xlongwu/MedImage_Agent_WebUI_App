# 协调、调度、聚合与单一规划链接入方案

> 状态：Proposed；G2-G4 实施依据

## 1. 责任分层

| 组件 | 责任 | 不得承担 |
|---|---|---|
| `MultiAgentEligibilityPolicy` | 校验全局 flag、项目 consent、任务显式 mode 和确定性复杂度/可拆分条件 | 模型判断、状态写入、自动启用 |
| `AgentTeamCoordinatorService` | 创建 Team、冻结 context、生成固定 work items、检查收敛、聚合、handoff | 生成计划、审批、执行 |
| `AgentTeamScheduler` | durable wake、claim、lease、deadline、并发和 startup recovery | 业务聚合和模型决策 |
| `AgentTeamWorkerService` | 构建角色请求、记录模型调用、校验 finding | 读取 store 任意数据、spawn、写 plan |
| `AgentTeamFindingAggregator` | 引用验证、去重、冲突、blocking 规则、advisory hash | 调用模型或自由改写 finding |
| `AgentPlanningService` | 接收冻结 advisory，沿现有 Harness/planner 生成唯一候选计划 | 创建第二 Team 或把 finding 当审批 |

## 2. 启动条件

Team 只有同时满足以下条件才创建：

1. `MEDIMAGE_MULTI_AGENT_ENABLED=1`。
2. 当前项目 `multi_agent_consent=true`，包含允许的数据类别和预算上限。
3. create request 明确 `planning_mode="multi_agent"`。
4. 真实脱敏评估 manifest/report/source-tree/role-registry/context-projector/model-adapter/aggregator hash 与批准配置一致。
5. structured model provider 健康，model profile hash 已冻结。
6. 当前 lifecycle 尚无活动 Team。
7. context projection 完整且不含禁入字段。
8. `MultiAgentEligibilityInput` 按下节规则得出 `eligible=true`。

任一条件不满足都返回结构化 disabled/blocked reason；不得把显式 Team 请求静默改成 single。

### 2.1 确定性 Eligibility Contract

`MultiAgentEligibilityInput` 只使用现有 goal contract、EvidenceSnapshot、decision state 和 policy 的结构化字段：

```text
task_kind
independent_evidence_domains[]
has_science_decision
has_path_or_scope_risk
has_competing_interpretations
context_is_role_splittable
provider_allowed
project_consent_epoch/hash
```

硬拒绝：简单状态查询、纯 UI 命令、单一已知目标且无风险/未决项、完整上下文不可安全拆分、provider/consent 禁用。通过规则为：`context_is_role_splittable` 且满足以下任一条件：至少两个独立 evidence domain；科学决定与路径/能力风险同时存在；存在由 goal contract 明确标记的竞争解释。每个分支返回固定 reason code，并由 G0 manifest 的 eligible/ineligible labels 验证 precision/recall。

显式 `multi_agent` 不能覆盖 eligibility 拒绝；拒绝时 Worker 启动数必须为 0，用户可创建新的 single Agent Task。

## 3. 正常时序

```text
create Agent Task command
-> persist lifecycle + planning wake
-> AgentPlanningService sees explicit multi_agent
-> build and freeze AgentPlanningBaseContext v1 (no Team advisory)
-> eligibility gate
-> transaction: lifecycle current team epoch CAS + team + base/role snapshots + 3 work items + wake
-> scheduler claims independent work items (bounded parallelism)
-> each worker persists model started before network
-> provider call preflight revalidates global policy + project consent epoch/hash
-> validate and persist findings
-> coordinator observes all required roles terminal
-> canonical pure deterministic aggregate shared with G0
-> persist advisory + team completed + planning wake atomically
-> AgentPlanningService resumes only if lifecycle current team id/epoch still match
-> AgentHarnessContext v4 includes typed team_advisory section
-> existing Harness action provider sees advisory and returns request_decision or draft_plan
-> draft-plan path builds PlanningRequest with advisory refs/hash
-> existing validation -> Reviewed Plan -> Approval Summary
```

Team 不直接创建 `request_decision`；blocking advisory 由现有 Harness action provider/validator 转成受支持的用户决定或安全停点，且最终状态仍由 lifecycle state machine 决定。Action validation 必须拒绝忽略 unresolved blocking code 的 `draft_plan`，只有覆盖相同 code/ref 的 `request_decision` 或确定性 safe stop 才能继续。

## 4. 并行 DAG

首期 DAG 固定，不允许模型生成：

```text
freeze_context
├─ science_review
├─ safety_review
└─ completeness_review
     \  |  /
      aggregate_findings
             |
      resume_existing_harness
```

- `freeze_context` 和 `aggregate_findings` 是确定性本地步骤。
- 三个 review 最多并发 3；受全局 model concurrency 和 available-memory gate 限制。
- `resume_existing_harness` 通过现有 durable planning wake 触发，从 `AgentPlanningService.advance_planning()` 的唯一公开 seam 进入 `_harness_or_plan()`，不直接调用 `_plan()` 或其他私有 finalizer。
- 首期没有 reviewer-to-reviewer、第二轮辩论或动态 work item。

## 5. 确定性聚合规则

顺序固定为 `safety -> science -> completeness`，但输入到达顺序不得影响输出 hash：

1. 校验 team/project/lifecycle/current team epoch/context/model/policy/consent/role-registry/context-projector/model-adapter/aggregator hash 和最新 fencing token。
2. 按 allowlisted code、severity、规范化 input refs 校验每个 finding。
3. 拒绝未知引用、跨项目引用、禁止建议和迟到 fencing token。
4. 按 `(code, severity, sorted(input_refs))` 去重。
5. 同 code 的 blocking 覆盖 warning，并保留来源角色集合。
6. 互斥 code 由代码内 conflict table 标记；不得让模型裁决。
7. safety reviewer 失败、缺失或存在 unresolved safety conflict：Team `NEEDS_ATTENTION`。
8. 其他单一 reviewer 失败：只有批准策略明确允许 partial 且不降低 reference coverage 时才能生成 `partial` advisory；首期默认 handoff。
9. canonical JSON 生成 `advisory_hash`，包含 accepted/rejected finding refs、conflicts、coverage 和所有绑定 hash。

实现使用 G0 已创建的唯一 `agent_review_finding_aggregator.py` 和 role registry；G3 不复制或重写第二套聚合器。若生产需要修改规则，必须先更新共享纯模块并重新运行 G0 acceptance Gate。

## 6. 规划输入绑定

修改现有 `PlanningRequest`，新增唯一当前字段：

```text
planning_mode: single_agent | multi_agent
team_id?
team_epoch?
team_base_context_hash?
team_harness_context_hash?
team_advisory_ref?
team_advisory_hash?
team_role_versions[]
team_role_registry_hash?
team_consent_hash?
```

约束：

- `single_agent` 时所有 Team 字段必须为空。
- `multi_agent` 时字段全部存在，Team 必须 `COMPLETED` 且 project/lifecycle/base/harness/advisory hash 匹配。
- lifecycle 当前 `planning_team_id/planning_team_epoch` 必须与 Team、wake、advisory 和 request 完全匹配。
- `request_hash` 必须覆盖完整 advisory payload 或稳定 ref+hash、role versions 和 planning mode。
- Reviewed Plan 的 planning input identity 和 Approval Summary 必须覆盖 `team_advisory_hash`。
- advisory、base/harness context、model profile、policy 或 memory context 任一变化，都生成新 Reviewed Plan 和新 Approval Summary；旧审批无效。
- 不新增 `TeamPlan`、第二 planner route 或 Team 专用 Approval Summary。

### 6.1 Base Context 与 Harness Context 唯一接入

规划上下文拆成两个有明确先后关系的不可变快照：

1. `AgentPlanningBaseContext v1`：从当前十个权威 section 构建，不含任何 Team finding/advisory；用于 eligibility、三个 reviewer projection 和 `base_context_hash`。
2. `AgentHarnessContext v4`：single mode 在 base 冻结后立即构建，使用 typed empty `team_advisory`；multi mode 只在 advisory 冻结后构建，包含 `base_context_hash`、typed `team_advisory` 安全投影及 hash。
3. base 与最终 Harness context 分别持久化、分别哈希，禁止原地追加或改变已冻结 base。
4. 当前 Context v3 的十 section builder 重构为唯一 base builder；Context service、prompt payload、request hash、Trace/Replay、fixtures 和全部消费者在同一任务切换，不保留 v3 reader。

`advance_planning()` 的顺序固定为：首次进入该 planning epoch 时冻结 Base v1，恢复时按 current epoch 加载并复验同一 base hash，禁止重建后冒充原快照；检查 current Team binding；multi mode 未完成则从该 base 创建/等待 Team；single mode 或 multi advisory 完成后构建 Context v4 并进入现有 `_harness_or_plan()`；只有 Harness 接受 `draft_plan` 后，现有 `_plan()` 才构建 PlanningRequest。权威输入变化必须显式创建新 planning epoch，禁止 Team 直接调用 `_plan()`。

## 7. 失败与 handoff

| 失败 | Team 结果 | Lifecycle 行为 |
|---|---|---|
| 全局 flag/consent 关闭 | 不创建 Team | create/advance 返回结构化 disabled reason，要求选择 single 或启用配置 |
| provider 在任何调用前不可用 | FAILED | `needs_attention`，用户只能创建新的 single Agent Task；原 lifecycle/Team 保持 sealed |
| Worker schema 修复仍失败 | FAILED/NEEDS_ATTENTION | 不聚合 |
| safety reviewer timeout | NEEDS_ATTENTION | 不进入 planner |
| science/completeness timeout | NEEDS_ATTENTION（首期） | 不静默 partial |
| finding/ref/context drift | NEEDS_ATTENTION | CAS 增长 lifecycle team epoch 并新建 Team；旧 epoch 永久失效 |
| eligibility 拒绝 | 不创建 Team | structured ineligible reason；Worker 调用为 0，可另建 single task |
| consent/policy 在网络前撤销 | CANCELED/NEEDS_ATTENTION | 停止调用；已在网络中的迟到响应拒绝应用 |
| budget/deadline | NEEDS_ATTENTION | 停止新调用，保留审计 |
| cancel | CANCELED | 顶层取消规则权威 |
| aggregate 后 planning 失败 | Team 保持 COMPLETED | 由现有 planning recovery 处理，不重跑 reviewers |

## 8. Plan-only 与执行边界

Plan-only 可以使用 Team 审查，但最终仍必须：

- `execution_performed=false`；
- 不创建 execution approval、dry-run、ticket、run 或数值产物；
- Team completed 不得映射成 task completed，只有 Reviewed Plan/结果投影决定用户状态。

## 10. 退出条件

- [ ] 三 reviewer 可并行但到达顺序不影响 advisory hash。
- [ ] safety 缺失、冲突、context drift、budget 和迟到结果全部安全阻断。
- [ ] Team completed 后 planner 只运行一次，重启/重放不重复创建 Reviewed Plan。
- [ ] 当前 Team id/epoch 是 lifecycle 权威绑定；旧 wake、旧 advisory 和迟到 finalize 永不进入新规划。
- [ ] eligibility reason codes 可执行，ineligible 显式请求启动 Worker 为 0。
- [ ] Harness action provider 的真实 request 覆盖 advisory hash，未解决 blocking finding 不能被 draft_plan 忽略。
- [ ] request/plan/approval hash 链覆盖 Team advisory。
- [ ] 全仓不存在第二 planner、Team approval、Team ticket 或 Worker 执行路径。
- [ ] Team 关闭时原 single Agent 行为与测试不变。
