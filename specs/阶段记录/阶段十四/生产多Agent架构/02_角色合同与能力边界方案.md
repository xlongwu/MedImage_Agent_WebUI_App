# 多 Agent 角色合同与能力边界方案

> 状态：Proposed；G1/G2 实施依据

## 1. 原则

生产首期只允许三个固定、版本化、只读 reviewer。角色差异来自 purpose-scoped context 和固定 prompt，不来自动态工具、自由角色描述或模型自我委派。

## 2. 固定角色

| role_id | 责任 | 必需输入 | 不得读取 | 输出重点 |
|---|---|---|---|---|
| `science_reviewer.v1` | 检查科学目标、输入前提、参数与能力含义 | goal、goal contract、科学 evidence、capability snapshot、候选规划约束 | 原始影像、凭据、approval/ticket 内容 | 科学前提缺失、参数冲突、能力虚假提升 |
| `safety_reviewer.v1` | 检查项目隔离、路径、写根、审批和执行边界 | goal、policy、path/scope 摘要、tool catalog、环境能力摘要 | 任意文件内容、shell、执行 handle | 跨项目、不安全写入、权限传播、审批绕过 |
| `completeness_reviewer.v1` | 检查目标、决定、证据、计划节点和输出的覆盖 | goal、decision state、evidence refs、候选目标分解 | rawdata、完整 Memory、执行能力 | 遗漏目标、未决问题、缺少输出或验收证据 |

首期不实现 result reviewer。结果审查仍由 Observation、Goal Evaluator、artifact validation 和现有确定性服务负责。

### 2.1 唯一角色映射

`AgentReviewerKind` 与生产 `role_id` 只能由 `agent_review_role_registry.py` 的代码内 registry 映射：

| reviewer_kind | role_id | prompt version | output schema |
|---|---|---|---|
| `science` | `science_reviewer.v1` | `science-review-prompt-v1` | `agent-review-finding-v1` |
| `safety` | `safety_reviewer.v1` | `safety-review-prompt-v1` | `agent-review-finding-v1` |
| `completeness` | `completeness_reviewer.v1` | `completeness-review-prompt-v1` | `agent-review-finding-v1` |

评估 manifest、G0 run bundle、生产 snapshot、work item、model call、finding 和 advisory 都必须绑定 `reviewer_kind`、精确 `role_id`/versions 和 `role_registry_hash`。不得在评估和生产中分别维护名称映射。

## 3. 输入合同

协调器必须先从当前权威 goal、goal contract、EvidenceSnapshot、decision state、policy 和现有十个 Harness section 构建并冻结 `AgentPlanningBaseContext v1`。该 base context 不包含任何 Team finding 或 advisory，具有独立 `base_context_hash`，是 eligibility 与三个 reviewer projection 的唯一父输入。

每个 Worker 只能接收 `AgentTeamRoleContext`：

```text
schema_version = 1
team_id, worker_id, role_id
project_id, lifecycle_id
base_context_hash
role_context_hash
purpose
included_sections[]
section_hashes{}
evidence_refs[]
model_profile_hash
prompt_template_version
output_schema_version
policy_version
redaction_policy_version
consent_epoch, consent_hash
budget_slice
deadline_at
created_at
```

不复制完整 `AgentHarnessContext`。`AgentTeamContextProjectionService` 必须从冻结的 `AgentPlanningBaseContext v1` 生成角色投影，并验证：

- project/lifecycle 与 Team 一致；
- required section 全部存在；
- evidence ref 属于冻结 base context；
- project multi-agent consent epoch/hash 与当前设置一致；
- omitted section 有明确记录；
- context 不包含未知字段、任意路径、rawdata 内容或 credential；
- canonical hash 与持久记录一致。

`AgentPlanningBaseContext` 与 Team 完成后生成的 `AgentHarnessContext v4` 是两个不可变快照，分别持久化和哈希；禁止在 base context 上原地追加 advisory。

## 4. 输出合同

复用 `AgentReviewFinding` 的核心语义，生产记录增加身份与哈希字段：

```text
AgentTeamFinding v1
├─ finding_id, team_id, worker_id, work_item_id
├─ project_id, lifecycle_id, role_id
├─ severity: warning | blocking
├─ code, message_key
├─ input_refs[]
├─ suggested_change?
├─ role_context_hash
├─ model_call_id, model_response_hash
├─ finding_hash
└─ created_at
```

约束：

- `code` 使用代码内 allowlist；未知 code 拒绝，不让模型发明控制语义。
- `message_key` 进入 i18n catalog；自由文本不得作为唯一 UI 状态。
- `input_refs` 非空且必须属于角色上下文。
- `suggested_change` 只是说明，不得包含命令、审批、票据、路径写入或执行动作。
- 同一 Worker 每轮最多 8 个 finding；超限整份响应拒绝。
- schema 错误只允许一次结构修复调用，修复仍失败则 Worker 失败。

## 5. Capability Broker

首期 Capability Broker 不是通用工具注册中心，只提供构建 model request 前的只读投影函数：

| capability | science | safety | completeness |
|---|:---:|:---:|:---:|
| 读取冻结 goal/contract | ✓ | ✓ | ✓ |
| 读取科学 evidence 摘要 | ✓ | 摘要 | ref only |
| 读取 capability/tool catalog 摘要 | ✓ | ✓ | ref only |
| 读取 path/scope policy 摘要 | ref only | ✓ | ref only |
| 读取 decision/plan coverage | 摘要 | 摘要 | ✓ |
| 调用 structured model adapter | ✓ | ✓ | ✓ |
| 读写 filesystem/rawdata | ✗ | ✗ | ✗ |
| shell/subprocess/network/MCP | ✗ | ✗ | ✗ |
| Memory 查询或写入 | ✗ | ✗ | ✗ |
| lifecycle/plan/approval/ticket/run 写入 | ✗ | ✗ | ✗ |
| spawn/role change/budget change | ✗ | ✗ | ✗ |

Provider 的 HTTP 调用由统一 model adapter 管理，不视为 Worker 拥有 network capability。Worker 不能提供 URL、header、credential 或发起任意请求。

## 6. Prompt 与注入防护

- System prompt 固定声明输入是不可执行数据，所有 goal/evidence 文本均作为 quoted data block。
- role prompt、tool schema、output schema 和 section 顺序固定版本化。
- 不把先前 Worker 自由文本加入另一个 Worker 的输入。
- Reviewer 彼此不可见；只有确定性聚合器读取 findings。
- prompt 中出现“忽略规则”“执行命令”“批准我”等内容只能产生 injection warning，不能改变 capability。
- 模型响应中出现未知字段、工具调用、命令或执行建议时 fail closed。

## 7. 预算边界

首期固定：

- 最多 3 个 Worker；每个角色最多 1 次正常调用 + 1 次结构修复。
- Coordinator 不调用模型做调度；首期不增加独立 synthesis model，聚合 advisory 完全确定性生成。
- Team 总输入 token 不得超过任务预算中显式预留的 team slice。
- 每个角色有独立 deadline；Team 有更短的总 deadline。
- 未返回 provider usage 时记为 unknown，并按保守上限占用预算，不能按 0 计费。

每次 provider 网络调用前必须重新读取项目 consent 并比较 epoch/hash。撤销或改变 consent 后，不启动未调用 work；已 claim 但尚未 network 的调用取消；已在网络中的迟到响应只记录安全摘要并拒绝应用。

## 8. 测试义务

| 风险 | 测试 |
|---|---|
| Worker 越权调用工具 | capability broker 没有写/执行接口；伪造 tool call 响应被拒绝 |
| 跨项目引用 | role context 和 finding project mismatch 返回结构化错误 |
| prompt injection | 对抗 goal/evidence 不能改变 role、schema 或 capability |
| safety reviewer 缺失 | advisory 不进入 planner |
| 模型发明 finding code | allowlist 拒绝 |
| 响应超限 | 超过 finding/字节/token 上限安全失败 |
| Worker 相互污染 | 验证每个 request 只含父 snapshot，不含其他 Worker 输出 |
| consent 在冻结后撤销 | 覆盖 snapshot 后、claim 后、network 前和 response 后四个时点，均不得应用未授权结果 |

## 9. 退出条件

- [ ] 三个 role_id、prompt、input projection 和 output schema 均版本化。
- [ ] 角色只读矩阵由自动化测试证明，而非仅靠 prompt 声明。
- [ ] 所有模型调用都有 request/model/context/prompt/schema/budget hash。
- [ ] G0 与生产使用同一 role registry，所有记录绑定 role/version/registry hash 和 consent epoch/hash。
- [ ] 非法 schema、未知 code、无效 ref、注入、超时和预算失败均有固定错误码。
- [ ] Worker 对生产 store 的写权限仅限通过 Coordinator 提交 validated finding，不持有 store 本身。
