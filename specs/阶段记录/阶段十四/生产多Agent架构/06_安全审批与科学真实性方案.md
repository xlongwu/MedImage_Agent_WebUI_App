# 多 Agent 安全、审批与科学真实性方案

> 状态：Proposed；跨越 G1-G7 的不可削弱约束

## 1. 威胁模型

| H-ID | 威胁 | 影响 |
|---|---|---|
| H14-01 | Worker 获得写入或执行能力 | 绕过唯一执行链 |
| H14-02 | finding/消息被当作审批 | 未经人工授权扩大权限 |
| H14-03 | 跨项目 context 或 ref 混入 | 研究数据隔离破坏 |
| H14-04 | prompt injection 改变角色或工具 | 模型越权、虚假安全结论 |
| H14-05 | safety reviewer 缺失仍进入 planner | 伪造安全审查完成 |
| H14-06 | context/advisory 变化后复用旧审批 | 审批对象漂移 |
| H14-07 | 多数投票覆盖确定性规则 | 安全或科学事实被模型裁决 |
| H14-08 | Team completed 被解释为 computed/validated | 科学能力虚假提升 |
| H14-09 | Trace/API 暴露 prompt、PHI 或路径 | 隐私泄露 |
| H14-10 | 并发/重试产生重复 plan 或副作用 | 状态和审计不一致 |

## 2. 权限不传播

用户对 Agent Task 的 consent、Approval Summary 或 Execution Ticket 都不能传播给 Worker：

- project consent 只允许构建已批准的数据投影和发生模型调用，不是执行授权。
- consent 使用持久 epoch/hash；每次 provider 网络调用前复验，撤销后未调用 work 停止、迟到响应拒绝应用。
- Approval Summary 只批准其绑定的 Reviewed Plan、actor、scope、environment 和 hash。
- Execution Ticket 只由审批后的 dry-run 创建，并只由 Execution Gateway 消费。
- Team finding、advisory、role 状态、model call 或多数票都不能创建、扩展或消费审批/票据。

依赖层面必须保证 `agent_team_*` 模块不导入 Execution Gateway、runner、sandbox process、external tool runner 或文件写服务。

## 3. 审批顺序

保持并扩展现有顺序：

```text
冻结 Team context
-> 完成三角色审查
-> 持久化 advisory hash
-> 单一 planner 生成并持久化 Reviewed Plan
-> 构建并持久化 Approval Summary
-> WAITING_FOR_APPROVAL
-> 校验 plan/advisory/context/model/policy/environment hash 未变化
-> 人工批准
-> 审批绑定 dry-run
-> Execution Ticket
-> 唯一 Execution Gateway
```

规划和 Team 阶段不得执行 dry-run、runner、外部工具或 dispatch。

Approval Summary 新增或通过 planning input hash 间接覆盖：

- `planning_mode`
- `team_id`
- `team_epoch`
- `team_base_context_hash`
- `team_harness_context_hash`
- `team_advisory_hash`
- `team_role_versions`
- `team_role_registry_hash`
- `team_context_projector_hash`
- `team_model_adapter_hash`
- `team_aggregation_policy_hash`
- `team_consent_hash`
- 实际 model profile/prompt/schema/policy hash

任一字段改变都必须重新规划并生成新 Approval Summary。

相同 binding 还必须冻结到 `ExecutionTicket`。责任边界固定为：approve service 在批准前复验；`ReviewedExecutionService` 在 dry-run 和签发前复验；`ExecutionTicketService.issue()` 校验并冻结；项目 multi-agent consent 更新服务在 epoch/hash 改变时同步 revoke issued-not-dispatched ticket；启动期 policy reconciler 处理全局策略漂移；`TeamTicketPolicyVerifier` 在 Gateway `consume()` 前做最后一次 fail-closed 复验。该 hook 只关闭签发与 dispatch 之间的竞态，不改变 dispatch 算法或增加执行入口。

## 4. 数据与路径安全

- Context Projection 只读 ProjectStore 已登记 metadata/evidence，不遍历用户目录。
- rawdata、DICOM、BIDS、NIfTI 不复制到 Team workspace，也不作为 provider payload。
- 路径只允许安全逻辑标识或 project-relative redacted ref；绝对路径在模型请求前拒绝或替换。
- Worker 没有 output_dir、write root、shell cwd 或环境变量字段。
- provider credential 由 ConfigService/adapter 内部读取，不写进 context、Trace、Team store 或 API。
- 每条持久记录和 API 读取均校验 project/lifecycle/team 链。

## 5. 科学真实性

Team 只能指出风险和遗漏，不能提高能力等级：

| Finding/状态 | 允许含义 | 禁止含义 |
|---|---|---|
| science warning | 参数或前提需要复核 | 算法已验证 |
| science blocking | 缺少输入、能力或验证证据 | 自动选择科学答案 |
| Team completed | 三角色 finding 已聚合 | 计划正确、执行完成、结果有效 |
| advisory accepted | 可供 planner 消费 | 用户已批准 |
| reviewer confidence | 调试/评估数值（若保留） | 科学证据或 capability level |

最终 scientific decision 仍由当前用户决定、确定性 validator、kernel、artifact、provenance、Goal Evaluator 和独立 reference validation 决定。多 Agent 不修改 `unavailable/scaffolded/metadata_only/computed/validated` 定义。

## 6. Plan-only

Team 可参与 plan-only 审查，但必须用测试证明 approval、dry-run、ticket、gateway、runner 和数值产物调用均为 0。Team 的 model calls 是规划活动，不得计为 scientific execution。

## 7. 对抗验证

必须覆盖：

- goal/evidence 中的 prompt injection、伪造 system 指令和工具请求。
- finding 伪造 `approved=true`、execution ticket、command、绝对路径或跨项目 ref。
- 三 reviewer 相互冲突、重复 finding、顺序变化、缺失 safety。
- Team/context/advisory/model/environment hash 在审批前后变化。
- lifecycle current Team epoch、project consent epoch/hash 或全局 multi-agent policy hash 在冻结后变化。
- ticket 签发后、consume/dispatch 前发生 flag、consent、base/context/advisory、role registry、projector、adapter 或 aggregator hash 漂移。
- 两 scheduler claim、lease 过期、迟到结果和重复 finalize。
- Trace/API/日志的 secret、PHI、rawdata path 和 provider response 泄露扫描。
- project A 请求 project B team/findings/events。
- 任一 Team 模块尝试导入/调用 Gateway、runner、subprocess 或 filesystem 写接口。

## 8. 审计事件

至少记录以下安全摘要事件：

```text
TEAM_REQUESTED
TEAM_GATE_ACCEPTED | TEAM_GATE_REJECTED
TEAM_CONTEXT_FROZEN
WORK_ITEM_CLAIMED
MODEL_CALL_STARTED | MODEL_CALL_COMPLETED | MODEL_CALL_INDETERMINATE
FINDING_ACCEPTED | FINDING_REJECTED
TEAM_CONFLICT_DETECTED
TEAM_ADVISORY_FROZEN
TEAM_NEEDS_ATTENTION | TEAM_FAILED | TEAM_CANCELED
TEAM_BOUND_TO_PLANNING_REQUEST
TEAM_BINDING_INVALIDATED
```

事件 payload 只含 ID/hash/code/status/metrics，不含完整 prompt/response 或敏感数据。

## 9. Proof Obligations

| 声明 | 证明 |
|---|---|
| Worker 无执行权限 | import boundary + capability broker + write spy |
| Team 不产生审批前副作用 | ordered call log，dry-run/ticket/gateway/runner spy 全为 0 |
| context/advisory 被审批绑定 | hash mutation contract test |
| 旧 Team 不能污染新 planning epoch | multiple terminal teams + stale wake/finalize tests |
| consent 撤销立即生效 | snapshot/claim/network/response 四时点测试 |
| issued ticket 不跨策略漂移执行 | consent update/startup reconciler revoke + Gateway consume 前 verifier race test |
| safety 缺失安全失败 | focused integration test |
| rawdata 不进入模型/存储 | payload fixture scan + path guards |
| 多 Agent 不提升科学等级 | capability matrix diff + result projection tests |
| Team completed 不等于 task completed | backend read model + frontend i18n/component tests |

## 10. 退出条件

- [ ] H14-01 至 H14-10 均有自动化缓解测试。
- [ ] Team 依赖图与运行 spy 证明执行面调用为 0。
- [ ] Approval Summary 绑定 Team identity/hash，漂移时旧审批被拒绝。
- [ ] 日志、Trace、API 和 SQLite 均通过敏感数据扫描。
- [ ] capability matrix 和科学文档没有因 Team 完成而升级声明。
- [ ] rawdata 只读、项目隔离和唯一路径/审批/执行边界没有削弱。
