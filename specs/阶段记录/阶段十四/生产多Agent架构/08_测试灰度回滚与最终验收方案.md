## 1. 实现期 focused verification

每个代码切片验证其直接受影响的接口和执行路径：

- Contract/store：序列化、事务 round-trip、项目隔离与幂等。
- Worker/coordinator：fake provider 输入输出、权限拒绝、预算和失败关闭。
- Planning/API/UI：现有 planner 接入、审批身份绑定、只读投影及受影响的双语组件。
- 仅为真实新增边界或已复现缺陷添加回归；不先创建不存在的测试文件清单，不为每个阶段重复跑同一套合同。

测试使用临时 store/workspace 和合成输入；不得写用户数据库、rawdata 或登记源数据。

## 2. 必须保持的安全不变量

- Worker 不可达 filesystem、shell、MCP、Approval、Ticket、Gateway 或 runner；真实网络/provider 默认关闭。
- flag、consent 或 eligibility 不满足时不启动 Worker；跨项目引用拒绝。
- GET/list 不触发 reconcile、claim 或状态迁移。
- plan-only 不创建执行审批、dry-run、ticket、run 或数值产物。
- context/advisory/consent 身份变化使旧 plan/approval/ticket binding 失效。

## 3. 性能与稳定性

实现期验证实际硬边界：Team/worker/round/token/deadline 有上限；项目隔离、lease/fencing、重启恢复和重复调用行为按受影响路径测试。100 个并发 Team、容量阈值及 provider rate 基准属于真实容量声明前的可选测量，不阻塞离线实现；只有准备开放相应并发能力时才测定目标值。

## 4. 验证方式

- 后端：只运行改动所涉及的 focused tests；测试文件随实现创建，不引用尚不存在的测试路径。
- 前端：只有修改 UI/API consumer 时运行相应的 typecheck 和 targeted tests；build/check 归入集成或 release 阶段。
- full backend/frontend suite、Electron check、packaged smoke 在对应 release 或执行边界发生实质变化时运行，不作为每个源码切片的准入门。
- 任何检查报告其实际命令和结果；未运行的验证不列为通过。
## 5. 灰度策略

### Stage A：离线源码实现（G0 之前可做）

- 使用 fake provider、合成输入和隔离 store 完成受影响的 contract/store/worker/planning checks。
- 默认关闭，无真实 provider 网络调用、真实研究数据访问或项目 opt-in；外部调用路径保持 fail closed。

### Stage B：授权后的 G0 真实评测

- 仅当数据来源、脱敏政策、provider/额度和评测方案获批后运行；指标和报告由冻结输入及实际 run records 计算。
- G0 不通过则保持 `single_agent`，不要求返工已满足 focused checks 的离线代码。

### Stage C：批准研究项目手动 opt-in

- 逐项目人工批准，用户每任务显式选择。
- 不启用 `auto`，不扩大 Worker 数据类别或能力。
- 设定观察窗口和停止条件。

### Stage D：稳定生产能力与发布

- 仍默认 single；Team 作为高级显式能力。
- 是否设计 `auto` 必须另立阶段和新方案，本阶段不预留隐式自动路由。

## 6. 停止与回滚条件

任一条件触发立即关闭全局 flag，并停止创建新 Team：

- 安全、项目隔离、审批或科学真实性出现任何退化。
- 发现 Worker/Coordinator 可达写入或执行面。
- advisory/plan/approval binding violation 非零。
- false blocker 超过 3%，或关键遗漏召回未保持 +10 个百分点。
- 调用量、token 或 P95 时延连续超过批准 Gate。
- 重启产生重复模型调用、finding、advisory 或 plan。
- Trace/API/日志发现敏感数据泄露。

回滚动作：

1. 关闭 `MEDIMAGE_MULTI_AGENT_ENABLED`。
2. Scheduler 停止 claim 新 work；活动 Team 有界取消并记录事件。
3. 保留 Team 记录用于只读审计，不删除或改写历史。
4. 新任务走 single；显式 multi request 返回 disabled reason。
5. 人工 Approval 记录本身保持不可变且不声称存在通用 Approval revoke；但关闭多 Agent flag 或改变 consent/policy 会使未 dispatch 的 multi-agent 执行资格失效，必须按下列状态矩阵在 approve/dry-run/issue/consume preflight 拒绝，并对 issued-not-dispatched ticket 记录权威 revoke。

### 6.1 Rollback/安全事件状态矩阵

| 当前状态 | 处理 |
|---|---|
| Team READY/RUNNING/AGGREGATING | 停止 claim、取消未调用 work；迟到响应拒绝应用 |
| Team COMPLETED、尚未生成 Reviewed Plan | current planning binding 标记不可继续，创建新 single task |
| WAITING_FOR_APPROVAL | approve preflight 重新校验 multi-agent global policy/consent/role/aggregator hash；失配则拒绝审批 |
| 已审批、dry-run/ticket 前 | reviewed execution preflight 重新校验相同 binding；失配则不运行 dry-run、不签发 ticket |
| ticket 已签发但未 dispatch | `ExecutionTicketService.revoke()` 记录权威撤销；Gateway 继续按现有 ticket status fail closed |
| ticket 已消费或 run 正在执行 | 关闭 Team flag不能伪称立即终止；按现有后端权威 cancel/monitor/incident procedure 处理并报告能否停止，不新增旁路 kill |

Team 的 `multi_agent_policy_hash`、consent、base/context/advisory、role registry、context projector、model adapter 和 aggregator hash 必须进入 Approval Summary/Ticket binding，并在 approve、dry-run、ticket issue 和 ticket consume/dispatch 前复验。consent 更新服务与启动期 policy reconciler 负责主动 revoke issued-not-dispatched ticket，`TeamTicketPolicyVerifier` 负责关闭最后竞态。该最小 binding 校验是受保护执行面允许的唯一新增接点；不得重写 Gateway dispatch 算法。

> 接点校正（2026-10-02）：上段的“ticket consume”指 `ExecutionTicketService.consume()`
> （`src/backend/app/services/execution_ticket_service.py:768`），它在
> `ExecutionGateway.dispatch()`（`src/backend/app/runtime/execution_gateway.py:119`）内部
> `execution_gateway.py:255` 处被调用。`ExecutionGateway` 本身**没有** `consume()` 方法，
> verifier 的接点因此是 `dispatch()` 内、`tickets.consume(...)` 之前，见
> `06_安全审批与科学真实性方案.md` §3 的同一条校正。

回滚不是兼容层：生产代码仍只有当前 Team schema，不读取旧格式或双写。

## 7. 最终验收矩阵

| 领域 | 验收 |
|---|---|
| 真实收益 | 获批的 G0 真实脱敏评估及明确范围的项目启用决定 |
| 架构 | 单 lifecycle、单 planner、单 Approval、单 Gateway |
| 状态 | durable Team/work item/finding/advisory/wake，重启可恢复 |
| 权限 | Worker 只读，无 tool/write/execute/approval |
| 安全 | project isolation、rawdata、path、prompt injection、hash drift |
| 科学 | 不改变算法和能力等级，不虚假 computed/validated |
| API/UI | contract/i18n/所有状态/只读详情/后端权威 |
| 审计 | Trace/Replay/invariant/operations 完整且脱敏 |
| 性能 | 调用/token/P95/人工步骤在 Gate 内 |
| 桌面 | build、sidecar、renderer、packaged smoke、进程清理 |

## 8. 完成条件

**离线代码切片完成**：受影响的 contract、存储、规划绑定及安全路径 focused checks 通过；新消费者同步；默认关闭、fake provider 测试无外联；唯一 planner/Approval Gate/Ticket/Gateway、项目隔离及 plan-only 零执行不变量保持。

**真实评测/启用**：只在使用真实语料或 provider 前满足 `00` §11.3；评测结果决定是否 opt-in，不回溯为代码实现的准入条件。

**Release**：只有发布时才运行项目 release checklist、packaged smoke 和对应 GUI walkthrough；逐 Gate 人工签字、无关全量回归和固定 100 并发基准不作为源码完成条件。
