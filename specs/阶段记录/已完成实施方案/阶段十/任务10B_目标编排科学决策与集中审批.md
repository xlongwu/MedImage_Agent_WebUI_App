## 2. Required Behavior

### 2.1 Canonical lifecycle 最小扩展

新增 canonical states：

- `WAITING_FOR_INPUT`：缺数据、缺资源或上下文不确定；
- `WAITING_FOR_SCIENCE_DECISION`：科学含义会变化的参数需要用户决定；
- `CANCELED`：只允许 dispatch 前取消。

新增 immutable pending decision payload，包含 decision_id、kind、question、options、recommended_option、impact、plan_hash_before。它属于 lifecycle 上下文，不保存独立状态机。

允许的关键转移：

```text
CREATED/CONTEXT_READY -> WAITING_FOR_INPUT -> CONTEXT_READY
PLAN_DRAFTED -> WAITING_FOR_SCIENCE_DECISION -> PLAN_DRAFTED
pre-dispatch states -> CANCELED
```

运行中不支持 cancel；不得把“关闭窗口”当取消。

### 2.2 Create command

`POST /agent/tasks` 使用有限编排：

1. 创建 lifecycle 并持久化用户 goal、goal hash、actor、command id；
2. 加载项目上下文和只读 readiness；
3. 缺输入则进入 WAITING_FOR_INPUT；
4. 调用抽取后的 goal planning service；
5. 检测 GSR、Atlas、TR、Template 等科学歧义；
6. 有歧义则进入 WAITING_FOR_SCIENCE_DECISION；
7. 生成 plan，运行 Plan Validator 和 native dry-run；
8. 构建 Goal Contract，并保存 approval_status=pending 的 Reviewed Plan；
9. 生成包含节点、后端、写入 roots、安全边界、局限和 confirmation expansion 的 Approval Summary；
10. 进入 WAITING_FOR_APPROVAL 并停止。

### 2.3 Answer command

- 只接受当前 pending decision_id；
- answer 持久化为 immutable command/evidence；
- 科学答案必须重建 plan 和所有 hashes；
- 如果 answer 导致新歧义，继续停在 decision；
- 不允许模型代表用户选择 Atlas、GSR 或其他改变科学含义的选项。

### 2.4 Approve command

前端只发送：

```json
{
  "command_id": "...",
  "actor": "...",
  "approval_summary_hash": "..."
}
```

服务端验证 current state、reviewed plan、plan hash、goal contract、write roots、node/backend allowlist、summary expiry 后，把批准映射到现有细粒度 confirmation，并调用共享 reviewed execution application service。任何 hash、路径、node、backend 或参数变化都返回 stale approval，重新进入 PLAN_DRAFTED/WAITING_FOR_APPROVAL。

## 4. Detailed Tasks

1. 为 lifecycle schema 升级版本并增加旧 v1/v2 fixture round-trip。
2. 把 plan-from-goal 的 context/application 逻辑移入 service，保持旧 endpoint 响应兼容。
3. 为 profile 隐藏建立确定性 goal → stage graph policy；内部可继续用 `fc_minimal`/`dparsfa_like`，但响应默认不暴露 profile 名。
4. 定义科学决策矩阵：Atlas、GSR、TR 冲突、Template、覆盖已有 run、实验性 GPU；其余资源选择不询问。
5. 抽取 execute-reviewed application service；旧 route 所有 characterization tests 先绿再接 Agent route。
6. Approval Summary 计算 stable hash，写入范围使用规范化 roots，细粒度 confirmations 进入 audit。
7. create/answer/approve/cancel 全部 project-scoped、idempotent、并发安全。
8. 自动 dry-run 失败转成 next action，不生成可审批摘要。
9. BIDS path 打通后再交给 10C；DICOM 自动 execute 明确由 10E gate 管理。

## 5. Acceptance Criteria

- [ ] BIDS 标准 goal 产生 WAITING_FOR_APPROVAL，不需手动 dry-run/validation/report。
- [ ] GSR/Atlas 等歧义产生 WAITING_FOR_SCIENCE_DECISION，未回答不生成执行审批。
- [ ] 一次 approve 形成所有现有 confirmation、audit、ticket 并仅调用一次 Gateway。
- [ ] stale/tampered summary hash 在任何写入或 runner 前失败。
- [ ] scope expansion 自动使旧审批失效。
- [ ] cancel 只在 dispatch 前成功；运行中返回明确不支持。
- [ ] 旧 planner 与 execute-reviewed API 兼容测试不回退。
- [ ] LLM provider 不可用时可解释失败/请求用户处理，不得伪造 deterministic plan。
