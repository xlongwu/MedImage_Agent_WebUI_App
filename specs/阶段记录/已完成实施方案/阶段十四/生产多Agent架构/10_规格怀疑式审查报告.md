## 1. 最终结论

经过三轮只读怀疑式审查和逐项修订，未发现仍会阻塞 G0 启动的 CRITICAL/HIGH 规格问题。方案已经明确唯一 lifecycle、planner、Approval、Execution Ticket 和 Gateway 所有权，并为真实准入证据、上下文时序、durable model call、current Team epoch、consent 撤销、ticket 策略漂移和回滚闭环给出可执行责任与测试。

G0 真实脱敏 Trace/Replay 与人工 capability approval 尚未发生，因此当前状态只能是 `Proposed / READY_FOR_G0`，不能标记为 Implemented，也不能开始 G1 生产运行时编码。

## 2. 已关闭的阻塞问题

| 问题 | 最终收敛 |
|---|---|
| G0 可由 fixture 自报指标伪造 | manifest 只含输入/人工 labels；隔离 runner 产生 append-only observations 和报告 |
| 缺少 durable Team 模型调用账本 | 增加 `AgentTeamModelCallRecord`/表及 pre-network、repair、indeterminate 恢复语义 |
| current Team 所有权不明确 | lifecycle 持久化 `planning_team_id + planning_team_epoch`，旧 epoch 全面拒绝 |
| reviewer 输入与 advisory 形成循环 | 先冻结无 advisory 的 `AgentPlanningBaseContext v1`，Team 后另建 `AgentHarnessContext v4` |
| 状态图无法表达运行期 handoff | Team 任一非终态可进入 `NEEDS_ATTENTION`；Work Item 明确一次 repair 与 `INDETERMINATE` |
| eligibility 依赖模型或显式 mode 可绕过 | 采用确定性 typed input/rules/reason codes，拒绝时 Worker 调用为 0 |
| Team 失败后非法重开原 lifecycle | 原 Team/lifecycle sealed；用户如需 single 必须创建新 Agent Task |
| consent 撤销存在网络竞态 | snapshot/claim/network/response 四时点复验，迟到响应不应用 |
| G0 与生产角色/聚合规则漂移 | role registry、context projector、model adapter、pure aggregator 共享并绑定 hash |
| issued ticket 可跨策略变化 dispatch | approve/dry-run/issue/consume 四处复验；consent/policy reconciler revoke；Gateway 最终 verifier |
| 历史候选文档可能误导实施 | 历史文档标为 Superseded，并列明被阶段十四替换的旧选择 |

## 3. 最终精确化项

- Base v1 的唯一存储是 `agent_planning_base_contexts`；最终 Harness v4 继续存于现有 `agent_harness_contexts`，Team context 只保存 Base ref 和角色投影。
- 共享 structured model adapter 只统一调用协议与元数据；Team reviewer 写 `AgentTeamModelCallRecord`，single/main Harness 保留现有 `ModelCallRecord`。
- `TeamTicketPolicyVerifier` 只位于 ticket 消费前（即 `ExecutionGateway.dispatch()` 内、`ExecutionTicketService.consume()` 调用之前；`ExecutionGateway` 无自身 `consume()` 方法），不改变 dispatch 算法、不创建第二执行路径。
