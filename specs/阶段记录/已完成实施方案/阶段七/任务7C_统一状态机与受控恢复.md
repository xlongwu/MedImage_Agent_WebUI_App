## Exact Anchors and Implementation Sequence

1. **定义状态与迁移表**：只允许主链 `CREATED → CONTEXT_READY → PLAN_DRAFTED → PLAN_VALIDATED → WAITING_FOR_APPROVAL → APPROVED → EXECUTION_READY → RUNNING → OBSERVING → SUCCEEDED`；失败链为 `FAILED → DIAGNOSING → RETRY_PROPOSED → WAITING_FOR_RETRY_APPROVAL → RETRYING → SUCCEEDED | HUMAN_HANDOFF`。增加 `CANCELLED` 或 `PARTIAL` 前须写明语义和所有入/出边。
2. **建立事件溯源式持久化**：每次 transition 写入 schema version、actor、source command、时间、上一/下一状态、ticket/reviewed plan/audit/run 引用和原因；使用原子写/数据库事务，避免前端缓存成为权威。
3. **把执行交给 gateway**：只有 `EXECUTION_READY` command 可请求 gateway；gateway 成功提交才进入 `RUNNING`。拒绝、超时或未提交必须有不同状态，不能假设 HTTP 200 即运行成功。
4. **实现观察与决策**：观察只整合真实 Run summary、node states、artifact reload/validation 和 ticket 范围。证据不足时进入 `HUMAN_HANDOFF`/`NEEDS_REVIEW`，不生成成功。
5. **受控 retry/replan**：仅当 error classifier、ticket retry policy、node contract 与预算均允许时创建 retry proposal；自动/半自动 action 均必须有明确审批规则。任何节点集合、参数、backend、输入输出范围改变均创建新 reviewed plan，不能重用旧 approval。
6. **迁移 UI 和兼容 route**：先提供只读 status/query；在前端不再维护独立 next-step 判断后，再移除旧流程的写操作。必须表示 loading、disabled、partial、failed、human handoff。

## Acceptance Criteria

- [ ] 非法 transition、重复命令、缺失 ticket、跨项目 lifecycle 访问全部被拒绝。
- [ ] 刷新/重启后可以重建生命周期当前状态与事件链；状态事实与 Run artifacts 一致。
- [ ] 诊断与 retry proposal 不等于 retry execute；未审批、超额或高风险 retry 不执行。
- [ ] 参数/节点/路径/后端变化强制回到验证与审批。
- [ ] 前端（如改动）只展示后端状态，不因本地请求结束而推断成功。

## Safety Invariants

- 最大 retry/replan 次数来自 ticket，默认零自动重试。
- 高风险后端和外部执行始终人工审批并走 7A/7B 网关。
- 科学产物未可重载或只产生 metadata 时不能进入 `SUCCEEDED/computed`。
