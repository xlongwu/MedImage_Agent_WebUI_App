# 阶段二：模型动作与请求记录优化方案

> 归档状态：该文档对应的当前阶段范围已完成；仅作为历史实施与审计记录保留。

> 状态：已实施并通过最终集成审查
> 依赖：阶段一完成
> 本阶段不改变审批、执行和科学判断；只收紧模型输入输出合同及审计记录。

## 1. 目标

模型只负责两件事：提出必须由用户回答的问题，或请求确定性规划器生成计划。模型返回值不再使用通用字典；每次模型请求的哈希由真实请求内容生成。

## 2. 当前问题

`ActionEnvelope` 当前允许六种动作，`payload` 为 `dict[str, Any]`。`AgentHarnessService._apply()` 中 `read_evidence` 和 `finish` 基本不产生业务结果，`explain_result` 和 `propose_recovery` 又与确定性结果、恢复流程重叠。

当前 `request_hash` 主要由 `attempt_id`、`step_id`、`context_hash`、模型服务和修复标记组成，无法证明请求模板、动作结构或模型参数是否变化。

## 3. 动作合同修改

### 3.1 只保留两种动作

在 `src/backend/app/schemas/agent_harness.py` 中删除：

- `read_evidence`
- `explain_result`
- `propose_recovery`
- `finish`

保留：

- `request_decision`
- `draft_plan`

结果解释由现有观察和目标评估投影生成；恢复由现有确定性恢复服务处理；受控循环是否结束由任务生命周期状态决定。

### 3.2 用固定数据结构替代通用 `payload`

新增两个不可变数据结构：

```python
class RequestDecisionAction(BaseModel):
    kind: Literal["request_decision"]
    reason: str
    expected_state: str
    input_refs: tuple[str, ...]
    decision: DecisionItem


class DraftPlanAction(BaseModel):
    kind: Literal["draft_plan"]
    reason: str
    expected_state: str
    input_refs: tuple[str, ...]
```

`ActionEnvelope` 改为带 `kind` 区分的联合类型。不得保留 `payload: dict[str, Any]`，也不得用额外字段兼容旧动作。

`DecisionItem` 继续复用当前正式数据结构；不要在 `AgentHarnessService._validate_decision_payload()` 中手写第二套字段校验。切换完成后删除该函数和动作字段白名单。

### 3.3 简化动作应用

从 `AgentHarnessService._apply()` 中移出具体业务操作，新增窄接口 `AgentPlanningActionService.apply()`：

```python
class AgentPlanningActionService:
    def apply(
        self,
        *,
        lifecycle_id: str,
        action: RequestDecisionAction | DraftPlanAction,
        actor: str,
    ) -> HarnessActionResult: ...
```

处理规则：

- `request_decision`：校验当前任务生命周期允许提出决定；持久化 `PendingDecisionBatch`；转入等待用户状态。
- `draft_plan`：只调用既有确定性规划服务生成审阅计划；不得接收模型给出的节点、路径或执行参数。
- `expected_state` 不匹配时返回结构化冲突，不调用业务服务。
- `input_refs` 只能引用当前上下文已登记的记录。

这里只需要两个清晰分支，不增加通用插件注册表。

## 4. 真实模型请求记录

### 4.1 新增标准请求结构

在模型服务调用前构造 `CanonicalModelRequest`：

```python
class CanonicalModelRequest(BaseModel):
    schema_version: Literal[1]
    provider: str
    model: str | None
    endpoint_class: str
    prompt_template_version: str
    system_prompt: str
    context_payload: dict[str, object]
    action_schema: dict[str, object]
    model_parameters: dict[str, object]
    repair: bool
```

构造要求：

1. 字典键排序，时间、随机 ID 和本地临时路径不得进入正文。
2. `action_schema` 使用本次真正传给模型服务的 JSON Schema。
3. `model_parameters` 至少包含温度、最大输出、超时和模型服务支持的确定性参数。
4. 请求原文不持久化；规范序列化后计算 `request_hash`。
5. 模型服务接收的内容必须直接来自该结构，不能在计算哈希后再次拼接隐藏文本。

### 4.2 扩展 `ModelCallRecord`

建议把 `schema_version` 提升一次，并增加：

- `action_schema_hash`
- `model_parameters_hash`
- `request_bytes`
- `request_builder_version`
- `response_schema_version`

继续保留 `context_hash`、`skill_hashes`、token、耗时、模型服务请求 ID 和错误码。不得记录凭据、原始提示词、原始响应、图像内容或研究数据。

### 4.3 增加动作应用记录

新增 `AgentActionRecord`，记录：

- `action_id`
- `attempt_id`
- `step_id`
- `request_hash`
- `response_hash`
- `action_hash`
- `kind`
- `expected_state`
- `status`：`accepted`、`applied`、`rejected`
- `error_code`
- `created_at`、`completed_at`

动作必须先通过数据结构和引用校验，再写 `accepted`；业务状态写入成功后更新为 `applied`。失败只记录结构化错误，不保存模型原文。

## 5. 调用顺序

```text
构建 CanonicalModelRequest
-> 计算 request_hash
-> 持久化 ModelCallRecord(started)
-> 调用模型服务
-> 校验响应数据结构
-> 持久化 response_hash 和调用结果
-> 校验 input_refs 与 expected_state
-> 持久化 AgentActionRecord(accepted)
-> 应用 request_decision 或 draft_plan
-> 持久化 AgentActionRecord(applied/rejected)
```

任何一步失败都不能跳过前面的持久记录。网络请求开始前无法写入 `started` 时，禁止调用模型服务。

## 7. 风险和处理

| 编号 | 风险 | 处理 | 证明方式 |
|---|---|---|---|
| H-02 | 旧提示词或测试样例仍输出已删除动作 | 数据结构一次性切换，旧动作类型直接拒绝 | 全仓搜索和参数化拒绝测试 |
| H-02A | `draft_plan` 偷带模型生成的执行参数 | 数据结构不提供参数字段，规划器只读取已确认状态 | 检查规划器入参 |
| H-03 | 哈希与实际发送内容不一致 | 模型服务只能消费 `CanonicalModelRequest` | 修改任一真实字段即改变哈希的测试 |
| H-03A | 审计记录泄露提示词或数据 | 只持久化哈希、大小和枚举字段 | 序列化快照中无正文测试 |
| H-03B | 调用成功但动作未落库 | 分开记录 call 和 action 状态，后续由阶段四恢复 | 中断注入测试 |

## 8. 测试

必须覆盖：

1. 两种合法动作能解析，四种旧动作和额外字段被拒绝。
2. `DecisionItem` 的 choice、number、boolean 和数组约束继续有效。
3. 修改提示词、上下文、数据结构、模型参数、修复标记中任一项都会改变 `request_hash`。
4. 相同规范请求重复构建得到相同哈希。
5. `started` 写入失败时模型服务调用次数为零。
6. `expected_state` 或 `input_refs` 不匹配时业务服务调用次数为零。
7. `Trace` 和 `Replay` 能区分调用成功、数据结构拒绝和动作应用失败。
8. 持久记录中没有系统提示词、上下文正文、原始响应和凭据。
