# 计划 03：规划、执行、工具调用与记忆完善

> 状态：**差异实施与工程验收已完成。**任务模式：Feature Bundle + Architecture / Refactor。
> 更新日期：2026-08-09。Phase 0-4 已按当前源码完成；下方原始 A-D 清单保留为审计上下文。

## 当前差异实施计划

### Scope Anchor

目标是在不新建执行路径、不放宽审批边界、也不引入兼容层或 fallback 的前提下，补齐 Planner provenance、Node Contract 权威性、执行 dispatch 证据和 Memory 失败语义。

非目标：新增科学算法、自动审批、模型直连 runner、自由 shell/MCP、跨项目记忆、自动写入科学参数、旧格式读取或迁移。

### Phase 0：事实基线与不可逆决策

在修改生产代码前，完成并通过 characterization tests：

1. 列出 `NODE_REGISTRY`、Tool Catalog、NodeContract、planner、validator、approval summary、gateway 和所有当前消费者；确认每个可执行 node 的唯一权威来源。
2. 记录当前 `ExecutionTicket` 消费、Gateway dispatch、run 创建和 artifact 注册的持久化顺序，覆盖 ticket 已消费但 runner 未启动、并发重放和进程重启。
3. 区分三种 memory 状态：显式关闭、显式启用且健康、显式启用但不可用；第三种必须返回结构化阻断结果，不能静默生成空 context 继续计划。
4. 冻结 canonical Plan/Goal Contract、identity hash 与 provenance 字段；动态时间和脱敏摘要只进入审计记录，不进入决定性 plan identity。

Phase 0 的 Go/No-Go 条件：必须明确 NodeContract 的权威所有者、dispatch 的持久化所有者、memory 故障码和所有当前消费者的替换清单；未满足时不得开始后续 Phase。

### Phase 1：Node Contract 与 Planner provenance

- 使每个可执行 node 具有显式 Contract，包含 backend、输入/输出 artifact 类型、参数 schema、审批、人工确认、风险与 write roots；未知、重复或不完整 node 在启动和 CI 中拒绝。
- 删除 Tool Catalog 根据 node ID 推断安全元数据的 fallback；Catalog 仅派生用户可见说明，不得覆盖 Contract。
- 定义唯一 Pydantic Plan schema 和 `PlannerInvocation`/`PlannerEvidence`。provider、模型、模板版本/哈希、输入哈希、输出哈希、校验码和脱敏错误摘要可审计；prompt、API key 和原始响应不得写入持久状态。
- provider 关闭时由请求明确选择 rule-based 或 disabled；已选 provider 的 timeout、一次固定输入 JSON repair 或 schema 失败均结构化停止，不替换为内容不同的计划。

### Phase 2：可恢复的执行证据链

- 新增不可变、持久化的 dispatch 记录，并将 `approval_summary_hash`、`memory_context_hash`、scope/allowlist hash、ticket、dispatch 与 run 用明确字段连接。
- 把 ticket 验证、消费、dispatch 记录、run 创建和拒绝证据设计为可恢复的状态机；定义每个崩溃窗口的重启行为与并发 command 的唯一结果。
- 只在数字产物存在、可重载且 shape、dtype、checksum、输入和参数溯源全部合格时呈现 `computed`；不得以计划或元数据代替产物。

### Phase 3：Memory 运营闭环与投影

- 复用现有 `MemoryRetrievalService` 作为唯一 typed-context 入口，不新建平行 context service。
- 明确安装级 gate、项目 consent、DB health、outbox preflight 和 retrieval policy 的结构化健康投影；GET 无副作用，UI 不显示敏感正文。
- 将冻结的 snapshot hash、已允许的 refs 和 policy version 绑定到 Reviewed Plan、Approval Summary、Ticket；仅重规划可读取新 snapshot。
- 覆盖 cross-project、outbox 崩溃、DB 故障、预算、forget 后 FTS/WAL/重启和审批后 memory 变化。

### Phase 4：前端、文档与分阶段验证

- 前端仅显示后端投影的等待审批、dry-run 阻断、ticket 过期、执行失败、可恢复建议、memory disabled/partial/failure；中英文文案均由 i18n 提供。
- 更新架构、安全、运行时、用户、配置和状态文档；能力矩阵仅在真实科学能力变化时更新。
- 每个 Phase 先运行 focused characterization/regression，再运行 API/前端消费者测试；最终执行 pytest collect、focused suites、完整 backend、前端 format/type/test/build，并按仓库规则安全清理 pytest 临时目录。

## 已取代的原始提案（仅作审计上下文）

不新建第二条执行路径，也不把模型变成权限主体。规划输出、工具元数据、记忆影响和执行证据必须有稳定 schema、hash、错误码和回归测试；已选择的模型失败或已启用的记忆不可用时结构化停止，只有显式关闭的记忆返回 typed disabled context，绝不悄悄换一个计划执行。

本计划与计划 02 的当前实现已完成收敛：Harness 复用本计划锁定的 provider、Node Contract、Execution Gateway 和 Memory 边界。真实 LLM 和长期记忆仍默认关闭，启用必须由安装级配置、项目级 consent 和健康检查共同决定。

## 锁定合同

### 1. 规划

新增统一的 `PlannerInvocation` 与 `PlannerEvidence`，保存到 Reviewed Plan 的 provenance：

```text
PlannerInvocation: provider_id, model_id, prompt_template_version,
input_schema_version, input_hash, started_at, timeout_ms
PlannerEvidence: invocation_id, output_hash, validation_codes,
fallback_used, failure_code, redacted_summary
```

规则 planner 的 `provider_id="rule_based"`，真实 provider 的 `provider_id="openai_compatible"`；两者都只能返回同一个 Pydantic Plan schema。真实 provider 的 JSON 无法通过 validator 时，最多一次同输入的格式修复；仍失败则返回 `PLANNER_OUTPUT_INVALID`，不自动换成内容不同的规则计划。

### 2. 执行

每个 execution attempt 必须保留以下不可变关系：

```text
ReviewedPlan(plan_hash, memory_context_hash)
 -> ApprovalSummary(summary_hash, plan_hash)
 -> ExecutionTicket(ticket_id, summary_hash, expiry, scope_hash)
 -> GatewayDispatch(dispatch_id, ticket_id, allowlist_hash)
 -> Run(run_id, dispatch_id)
 -> Artifact(run_id, input_hashes, parameter_hash, checksum)
```

任何 hash 不匹配、ticket 过期、scope/allowlist 变化、artifact 不可重载或 post-approval dry-run 失败，都必须阻断 dispatch 并写结构化审计。相同 command ID 只能复放已持久化结果，不能重复 dispatch。

### 3. 工具

`NodeContract` 是 node 输入/输出的唯一 schema；Tool Catalog 只补充用户可见说明、风险、审批和 write root。每次应用启动和 CI 都运行 registry consistency check：每个可执行 node 恰有一个 NodeContract 和一个 Tool Catalog item；backend、输入类型、输出类型、requires_approval、manual_required、write roots 不一致即启动失败。

### 4. 记忆

启用条件固定为：安装级 generation/use 配置为真、项目 consent 为真、memory DB migration/health/outbox preflight 通过。planner 只能经 `MemoryRetrievalService` 获取 typed context；显式关闭返回 disabled context，已启用但 health/preflight 失败时结构化阻断；科学参数只形成待确认 decision，永不直接写入 plan 参数；执行时不重新检索 memory。

## 风险与防护

| 风险 | 防护 | 验证 |
|---|---|---|
| 真实 LLM 产生不合法计划 | schema、validator、Goal Contract、一次格式修复上限；失败不执行。 | provider fixture 与 plan-only 回归。 |
| 元数据说允许、runner 实际不允许 | Registry/Contract/Catalog 三方一致性检查，启动和 CI fail closed。 | 缺失/冲突矩阵测试。 |
| 记忆污染或跨项目泄漏 | typed allowlist、双 gate、project 条件、hash、科学参数二次确认。 | PHI/secret/injection/cross-project tests。 |
| hash 链断裂或重复 dispatch | 每层绑定前一层 hash/ID；command idempotency；gateway 二次校验。 | tamper、expiry、replay tests。 |
| 为了可用性绕过默认关闭 | flag/consent/health 任一不满足即 disabled；UI 显示原因。 | config 与 UI tests。 |

## 评审结论

计划 03 不追求“更自主”，而是让四个已有能力变得可证明、可恢复、可解释。当前 Harness 已复用稳定的 provider、工具合同、执行证据和记忆边界，没有复制或绕过现有安全链。
