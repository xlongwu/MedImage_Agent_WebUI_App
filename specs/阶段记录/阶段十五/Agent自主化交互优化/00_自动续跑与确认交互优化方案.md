# 阶段十五：Agent 自动续跑与确认交互优化方案

> 状态：已实施；前后端自动化验证通过，人工 GUI 验收待执行
>
> 任务模式：Feature Bundle + Architecture / Refactor
>
> 目标：将用户面对的研究流程收敛为“在需要时收到一次明确的确认弹窗 -> 确认后由 Agent 自动推进至下一个真实阻塞点”，不再要求用户为了继续工作而在 Plan、Preprocessing、QC、Runs 等页面之间寻找按钮。

## 1. 范围锚点

### 1.1 要解决的问题

当前项目已经具备 Agent Task、持久化规划唤醒、Reviewed Plan、Approval Summary、Execution Ticket、Execution Gateway、执行监控及恢复链路，但用户体验仍有三个断裂：

1. 需要用户输入或批准的状态主要表现为 Agent Workspace 内的一张卡片；用户离开该页后，不能在当前上下文直接处理该请求。
2. 决策、执行审批和恢复审批的确认 UI 分散在多个组件或历史工作区中；用户难以区分“这一次确认后系统会自动做什么”和“还需要去哪里继续点击”。
3. 旧技术面板仍保留大量 `window.confirm()` 和 `approved: true` 的单项运行入口，容易把用户带回逐页、逐节点的手动流程。

本阶段的目标不是追求无人审批，而是让唯一必要的人类决定成为前台、一次性、可解释的弹窗交互；确认完成后，系统必须在既有安全边界内自行继续。

### 1.2 成功标准

- [ ] 只要当前项目的 Agent Task 进入需要用户处理的状态，用户无论停留在 Agent、Runs、Settings 或允许访问的详情页，均能看到同一份项目绑定的确认弹窗；无需先切换回 Agent Workspace。
- [ ] 常规任务的显式人类承诺最多为：提交目标、一个完整科学决定批次（如需要）、一次执行审批；恢复仅在现有策略判定需要恢复审批时出现。
- [ ] 用户确认一个决定批次后，后端持久化唤醒并自动规划至计划审批、plan-only 结果或新的真实阻塞点；前端不提供“继续规划”按钮。
- [ ] 用户批准未变化的 Approval Summary 后，既有 dry-run、ticket、Gateway dispatch、monitor、Observation 和 Goal Evaluation 自动推进；前端不提供“继续执行/继续验证/生成报告”按钮。
- [ ] 所有弹窗只提交后端已经定义的结构化命令和当前 hash；任何取消、过期、项目切换、网络错误或审批摘要变化均不产生执行副作用。
- [ ] 默认路径不再展示或引导至逐节点的技术执行按钮；高级详情仍可只读查看证据、Runs、计划和审计记录。
- [ ] 中英文、键盘焦点、窄屏、刷新、重启、项目切换和命令幂等性均有自动化测试。

### 1.3 非目标与硬性边界

- 不自动替用户确认科学参数、覆盖策略、backend、输入/输出范围或恢复执行。
- 不改变 Approval Gate、Approval Summary、Execution Ticket、Execution Gateway、Pipeline Runtime、node runner、路径 allowlist 或 rawdata 只读规则。
- 不让前端根据本地状态推断命令成功、任务完成、能力等级或实际执行后端。
- 不把轮询、弹窗、Toast 或桌面通知变成新的任务状态权威源。
- 不新增无限 Agent 循环、任意 shell/Python、LLM 直连执行器或新的执行旁路。
- 不修改科学算法、数值产物格式或能力等级。

根因不是缺少一套新的 Agent 状态机：后端已能在用户回答或批准后自动继续。缺口在于前端把“需要一次当前确认”的权威 `next_action` 分散呈现为页面卡片，并且旧工作区仍暴露与 Agent 主线竞争的手动执行表面。

## 3. 目标体验与人机边界

### 3.1 标准流程

```text
用户提交研究目标
  -> Agent 自动读取证据、规划、校验
  -> [仅必要时] 全局决定弹窗：一次填写全部问题并确认
  -> Agent Scheduler 自动继续到 Reviewed Plan
  -> [仅一次] 全局执行审批弹窗：审阅范围并批准
  -> Dry-run -> Ticket -> Gateway -> Runtime -> Monitor
  -> Observation -> Goal Evaluation -> Result Summary
  -> [仅失败且策略要求时] 全局恢复审批弹窗
```

任何方括号内的弹窗都是当前任务的唯一用户停点。确认后，应用保持当前页面，不跳转到 Runs 或旧工作区；后台状态通过现有 controller 更新，页面显示“自动处理中/正在验证/已完成/需注意”。

### 3.2 人类动作预算

| 场景 | 允许的人工动作 | 系统必须自动完成 | 不允许自动完成 |
|---|---|---|---|
| 证据完整、需执行 | 提交目标、批准一次稳定计划 | 规划、dry-run、执行、监控、观察、评价、结果说明 | 批准写入或科学范围变化 |
| 缺少科学输入 | 一次完整决定批次、随后批准计划 | 回答后的重规划和验证 | 自动选择 atlas、TR、GSR、模板、overwrite、实验 backend |
| plan-only | 提交目标，必要时一次决定批次 | 计划、验证、Reviewed Plan 和结果说明 | 创建审批、ticket、run 或数值产物 |
| 运行失败且可恢复 | 批准一次已提出的恢复方案 | 策略允许范围内的恢复执行与后续观察 | 更改 scope/backend/路径或无审批重试 |
| 证据不足、策略拒绝或系统错误 | 查看说明、补充输入、取消或创建新任务 | 结构化停止与审计 | 用 UI 重试绕过拒绝 |

## 4. 架构决策

### D1：在 App Shell 安装单一的 `AgentAttentionDialog`

新增 `src/frontend/src/features/agent/components/AgentAttentionDialog.tsx`，由 `AppShellView` 在项目壳层永久挂载，而非仅由 `AgentWorkspace` 渲染。它只接收：

- 当前 `AgentTaskController`；
- 当前选中的 `project_id`；
- “打开 Agent Workspace”回调，用于用户主动重新打开已关闭的待处理请求；
- 可选的无副作用通知回调。

弹窗的唯一输入是 `controller.task` 的 `task_id`、`project_id`、`next_action`、`decision_batch`、`approval_summary`、`recovery` 和 `mutating`。它不得读取项目文件、调用旧执行 API，或拼装 run/ticket/plan 的本地状态。

这样可保证任何顶层工作区看到的是同一个权威任务投影，并消除“先切页才能找到确认”的交互成本。

### D2：用 action identity 管理弹窗，而不是用布尔状态猜测生命周期

定义仅在浏览器内存在的 `AttentionActionKey`：

```ts
type AttentionActionKey =
  | `decision:${taskId}:${decisionBatchId}:${evidenceSnapshotHash}`
  | `approval:${taskId}:${approvalSummaryHash}`
  | `recovery:${taskId}:${recoveryProposalId}:${recoveryApprovalSummaryHash}`
  | `goal-revision:${taskId}:${decisionBatchId}:${evidenceSnapshotHash}`;
```

规则：

1. 收到新的 key 时自动打开对应弹窗；同一 key 的用户取消只关闭该浏览器会话内的弹窗，不向后端写入“已处理”。
2. 用户取消后，在 Agent Workspace 的摘要卡与 Top Bar 待处理提示中提供非破坏性的“重新打开确认”入口；不得每个轮询周期反复抢焦点。
3. `project_id`、`task_id` 或 key 改变时，丢弃旧本地输入、Abort 中的请求和 dismissed key；绝不显示上一项目的确认内容。
4. 命令响应或后续 GET 返回不同 key 时，再按新的后端权威 action 打开弹窗。旧摘要、旧批次与旧恢复 proposal 永不复用。

该 key 不是持久状态，不进入 SQLite、审计、计划 hash 或审批 hash。

### D3：一个确认内容组件对应一个后端命令

| `next_action.type` | 全局内容组件 | 提交的既有命令 | 成功后的行为 |
|---|---|---|---|
| `answer_science_decision`、`provide_input` | `DecisionBatchForm` | `controller.answer(batchId, answers)` | controller 接收后端投影；持久化 scheduler 自动继续。 |
| `revise_goal` | `GoalRevisionForm`（复用批次 contract） | `controller.answer(...)` | 自动重新分析与规划。 |
| `approve_execution` | `ExecutionApprovalReview` | `controller.approve()` | 现有审批服务自动 dry-run、dispatch、monitor。 |
| `approve_recovery` | `RecoveryApprovalReview` | `controller.approveRecovery()` | 现有恢复服务审批并执行。 |
| `review_results`、`view_attention`、`none` | 不自动弹出确认 | 无 mutation | 仅显示 status/详情入口，不制造假审批。 |

每个内容组件必须只允许一个主按钮。按钮在 `controller.mutating` 或 `next_action.disabled_reason` 存在时禁用；提交前保留本地字段校验，提交后立即以 API 返回的完整 `AgentTaskResponse` 替换视图。

### D4：把当前卡片改为状态摘要和重开入口，删除分散 modal owner

重构以下组件：

- `DecisionBatchCard.tsx`：抽出可复用的 `DecisionBatchForm`；卡片不再拥有提交 mutation 或独立 Dialog，只展示待处理摘要、过期时间、推荐与“重新打开确认”。
- `NextActionCard.tsx`：保留 Approval Summary 的只读范围、安全边界、节点、backend、write roots 与限制；不再拥有执行审批弹窗或直接 dispatch。
- `RecoveryActionCard.tsx`：保留诊断、影响范围、未触碰范围与恢复理由；不再拥有恢复审批弹窗或直接执行。
- `AgentWorkspace.tsx`：只负责投影布局、状态、进度、结果、技术详情和“重新打开确认”的事件转发，不再作为确认弹窗唯一载体。

抽取后，默认 Agent 页面仍有一个清晰 primary action；若全局弹窗已经打开，卡片上的重开入口不得与之形成两个并列 primary actions。

### D5：持续可见性与无打扰通知

`useAgentTaskController` 已挂在 `App.tsx`，且在活跃状态每三秒获取后端投影。改进时：

1. 保持只对 `preparing`/`running` 轮询，避免在等待用户或终态产生无意义读取。
2. 当活跃任务的轮询响应首次转为 `requires_user=true` 时，由 `AgentAttentionDialog` 打开；不需要增加 websocket 或在 GET 中做 reconcile。
3. 当用户关闭弹窗但任务仍待处理时，Top Bar 增加项目绑定、可访问的待处理指示；点击只重新打开本地 dialog，不修改任务。
4. 运行中、验证中和终态只更新 status/live region，不抢焦点、不弹成功弹窗、不将用户带去 Runs。
5. 桌面系统通知如需引入，必须是可关闭、默认最小化且不携带 goal 原文、路径、影像数据、Prompt、审批 hash 或审批按钮；首期不依赖此能力。

### D6：收口旧的逐节点执行表面

先建立全仓 inventory，再一次性切换所有当前消费者。每个 `window.confirm()`、`approved: true`、直接 run/execute/dry-run/validation/report 按钮须归入以下一种处理：

1. **Agent 主链已有等价能力**：从普通 UI 删除该 mutation，改为 Agent Task 的目标/决定/审批输入；旧组件只保留可访问的只读证据展示，或在没有当前消费者后删除。
2. **仅用于开发、合成验证或受保护 smoke**：移到明确的 Advanced/Developer 区域，要求环境门控与现有审批，不出现在普通导航与 Agent 的推荐路径。
3. **尚无 Agent 等价能力**：不伪装为自动化；先将它列为结构化 `needs_attention` 原因或本阶段 blocker，再另立完整 Feature Bundle 完成 route/schema/service/runtime/测试迁移。

禁止通过把旧按钮藏在 CSS、增加兼容 fallback、或让前端模拟 `approved=true` 来宣称收口完成。

## 5. 实施台账

### Phase A：基线与收口边界

1. 为 Agent 主链建立用户操作计数的特征测试：无输入任务、决定批次任务、正常执行、plan-only、恢复、失败/人工交接。
2. 全仓搜索并记录 `window.confirm`、`approved: true`、`dry-run`、`execute`、`validation`、`report` 与直接 route 调用；标记每项当前页面、消费者、后端 contract、风险级别与处置类别。
3. 从 `App.tsx`、`AppShellView.tsx`、`AgentWorkspace.tsx`、controller、Agent Task API、planning scheduler、approval service、recovery service 绘制实际调用图，并用 focused tests 固化“回答/审批后无需前端继续请求”的现状。
4. 产出可审计 inventory 作为本方案的实施附件；未分类项目阻止进入 Phase D。

**完成条件**：手动表面没有未经解释的遗漏；保留与移除边界经 Review 批准。

### Phase B：全局确认协调器与复用表单

1. 创建 `AgentAttentionDialog.tsx` 和仅浏览器内的 action-key/dismissal hook；确保 project/task change 时立刻清理。
2. 从 `DecisionBatchCard.tsx` 提取 `DecisionBatchForm.tsx`，使表单同时可用于弹窗与卡片的“重新打开”入口；一次显示全部 1..6 项，保持 option/boolean/number/text、推荐、来源、影响和字段错误。
3. 创建 `ExecutionApprovalReview.tsx`，完整显示稳定 Approval Summary 的 goal、数据范围、节点/backend、write roots、rawdata 只读、限制、科学变化与 Memory 影响；只能调用 `controller.approve()`。
4. 创建 `RecoveryApprovalReview.tsx`，显示 diagnosis、affected subjects、recommended action、untouched scope、是否重规划；只能调用 `controller.approveRecovery()`。
5. 将 `AgentWorkspace` 中的本地确认 state 移除，改传 `onReopenAttention()`；`AppShellView` 在 `ProjectShell` 外挂载全局 dialog，保证 Runs、Settings 与允许的详情页可见。

**完成条件**：一个任务在任意工作区只存在一个相同 action key 的确认层；关闭、Escape、backdrop、项目切换与错误均不发 mutation。

### Phase C：自动续跑状态与可见反馈

1. 给 controller 增加纯派生的 `attention`（或在 `AgentAttentionDialog` 内部派生），不能将其存入任务状态；明确 polling transition 到 `requires_user` 的开窗逻辑。
2. 以 `task.next_action.disabled_reason`、`controller.mutating`、`errorCode` 和新的响应 action key 驱动 loading、disabled、server field error、stale/expired、network failure 与 success 状态。
3. 命令完成后不进行页面导航；保持当前 workspace，依据 API 投影显示 “自动准备”“自动执行”“正在验证”“等待用户”“已完成/部分完成/需注意”。
4. 在 Top Bar 或项目壳层添加最小、可访问的待处理指示，只对当前项目显示，且只能重新打开弹窗或进入 Agent Workspace。
5. 检查任务切换、项目切换、刷新、控制器 abort、任务终态和浏览器返回焦点，确保不出现 stale response 或重复弹窗。

**完成条件**：用户确认后不需要手动 refresh、继续、查看运行或切换页面来推进；UI 仅反映后端权威状态。

### Phase D：历史手动页面迁移

1. 依 Phase A inventory 逐项迁移/删除普通路径中的单节点 mutation；先改调用方，再删除旧 API wrapper、i18n、测试与文档描述。
2. 对无 Agent 等价能力的合法高级操作建立显式的 read-only/开发/受保护 smoke 标识；如果仍会改变项目状态，必须设计完整 Agent Task contract 后才向普通用户暴露。
3. 检查 `AppShellView.tsx` 的 legacy workspace 分支、deep-link、Runs 的 retry/link、Plan/Preprocessing/QC/Results 的按钮以及所有 React route consumers。
4. 运行全仓旧标识搜索，保证普通路径不存在直接执行、独立 approval 或要求用户手动读取结果的表面。

**完成条件**：默认体验只由 Agent Task 驱动；技术详情没有成为第二条执行主线。

### Phase E：端到端验收与文档同步

1. 以隔离 SQLite、临时项目和合成数据运行完整 Agent Task 生命周期；不得使用持久桌面数据库、用户工作区或真实研究数据。
2. 更新 `README.md`、`README_CN.md`、`docs/规划与运行时/受控单AgentHarness.md`、`docs/安全与审批/安全边界.md`、`docs/架构与决策/系统架构.md` 和受影响的前端使用说明，明确“自动推进不等于自动批准”。
3. 只有在 GUI、后端安全回归和文档审查全部通过后，才可更新 `PROJECT_STATE.md`；不得把 source test 误写为 packaged GUI 或真实科学执行验证。

## 6. 关键状态与交互矩阵

| 后端投影 | 自动弹窗 | 用户提交 | 自动后续 | 取消/关闭行为 |
|---|---|---|---|---|
| `preparing` | 否 | 无 | Scheduler/规划继续 | 仅状态展示 |
| `waiting_for_user + answer_*` | 是，DecisionBatchForm | 一次 `answer` | 持久化 wake -> 规划 | 保留 waiting state；显示重新打开入口 |
| `waiting_for_user + revise_goal` | 是，GoalRevisionForm | 一次 `answer` | 重新分析/规划 | 不改旧任务状态 |
| `waiting_for_user + approve_execution` | 是，ExecutionApprovalReview | 一次 `approve`（当前 summary hash） | dry-run -> ticket -> Gateway -> monitor -> evaluate | 不产生批准或执行 |
| `running` | 否 | 无 | monitor/observation/evaluation | 不抢焦点；可查看 Runs |
| `completed` | 否 | 无 | 无 | 结果卡/详情可读 |
| `needs_attention + approve_recovery` | 是，RecoveryApprovalReview | 一次 `approveRecovery` | 现有恢复服务继续 | 不产生恢复执行 |
| `needs_attention + view_attention` | 否 | 无 | 无 | 展示结构化原因与安全建议 |

## 7. 风险、缓解与验证

## 10. 退出条件与人工验收

实施完成前逐项确认：

- [ ] 无需手动导航即可处理当前项目唯一的必要确认；同一动作不会出现多个弹窗或多个 primary action。
- [ ] 一个决定批次只提交一次，确认后 Agent 自动达到下一个后端阻塞点。
- [ ] 执行审批仅批准当前稳定摘要，之后自动完成既有执行与验证链；无“继续”按钮。
- [ ] 恢复仍需要独立当前确认，且不会扩大 scope 或重用历史批准。
- [ ] Runs、Settings、详情页与项目切换均不串 task、summary、proposal、错误或焦点。
- [ ] 普通路径中的旧手动执行面已迁移、删除或被明确限制；不存在未分类的直接执行按钮。
- [ ] 计划、审批、ticket、Gateway、路径/rawdata、科学产物真实性和审计不变量均未削弱。
- [ ] 文档、双语、单元/集成/前端/桌面验证结果与实际范围一致；未验证项目明确记录。

人工 walkthrough：选择一个合成 BIDS 项目，提交目标，停留在 Runs 或 Settings；若需科学决定，弹窗应直接出现。一次提交全部决定后保持当前页面并看到“自动准备”。执行审批弹窗必须展示范围，确认后无需再点击 dry-run、execute、monitor、validate 或 report；系统最终显示真实的结果或结构化恢复请求。重复相同 walkthrough 于项目切换、摘要过期和失败恢复场景，均不得出现跨项目确认、重复 dispatch 或假成功。
