# 04：项目证据收集与科学决策自动化方案

> 状态：Draft，待人工 Review。
> 依赖：03 Action 合同；05 Planner 消费本方案输出。

## 1. 目标

让 Agent 自动读取已有项目证据，并把确实需要用户决定的多个问题合并为一次提交。目标是减少反复人工操作，不是让模型替用户决定 atlas、GSR、TR、template、overwrite 或 experimental backend。

非目标：不扫描项目外目录，不读取影像数值或完整日志，不把 Memory 建议当成当前事实，不自动确认科学参数。

## 2. 当前实现分析

- `HarnessContextBuilder._safe_project_evidence()` 只从 `project.metadata` 取少量字段，不能说明证据来源、时间和完整性。
- `AgentTaskCommandService._science_decision()` 会逐个产生 `PendingDecision`。
- `PendingDecision` 和 `AnswerAgentTaskRequest` 只支持一个 `decision_id + answer`。
- `AgentTaskReadModel._decisions()` 和 `NextActionCard.tsx` 只展示一个问题和一个单选/文本答案。
- 项目已有 dataset index、registered artifacts、Reviewed Plan、run link、Observation、Goal Evaluation 和 MemoryContext，可复用其结构化记录。

## 3. 总体修改思路

新增一个只读 `AgentEvidenceService`，集中构建带来源 hash 的 `EvidenceSnapshot`。Planner 先用证据消除可确定问题，再把剩余阻塞项写入唯一 `PendingDecisionBatch`；前端一次提交全部 answers。

## 4. 项目证据方案

### 4.1 允许来源

| 证据 | 权威来源 | 用途 |
|---|---|---|
| 项目和数据状态 | `ProjectStore.get_project()`、dataset index | 数据类型、受试者数量、准备状态 |
| 已登记输入/产物 | artifact registry、run link | 判断前提和已有结果 |
| 计划与审批 | Reviewed Plan、Approval Summary | 判断当前是否已有稳定计划 |
| 运行状态 | project run projection | 判断运行中、终态和失败 |
| 科学结果证据 | Observation、Goal Evaluation | 结果解释和恢复 |
| 长期建议 | `MemoryContext` 的 refs/suggestions | 仅作为待确认建议 |
| 配置能力 | `ConfigService`、Tool/Node Catalog | 判断当前可用/禁用，不从记忆推断 |

### 4.2 `EvidenceSnapshot` 构建

新增 `AgentEvidenceService.build_snapshot(project_id, lifecycle_id, requested_types)`：

1. 校验 project/lifecycle 绑定；
2. 读取允许的结构化记录；
3. 将绝对路径转换为 project-relative ref 或稳定 ID；
4. 生成 `facts`、`missing`、`warnings`、`source_refs`；
5. 对 canonical JSON 计算 `snapshot_hash`；
6. 持久化不可变快照，供 context、Planner、trace 和 replay 引用。

禁止读取 rawdata 文件、NIfTI/DICOM 正文、stdout/stderr 全文、环境变量和值得保密的 provider 配置。

### 4.3 证据冲突

若 metadata、artifact、run 或 Observation 对同一事实冲突：

- 权威运行/产物记录优先于自由 metadata；
- 冲突写入 `warnings`，不得自动选择有利于继续执行的值；
- 涉及科学参数或输入身份时创建决定项或转 `HUMAN_HANDOFF`；
- 不把冲突摘要写回项目 metadata 作为新事实。

## 5. 决定批次方案

### 5.1 数据合同

用 `PendingDecisionBatch` 替换当前单问题 `PendingDecision`：

```text
PendingDecisionBatch
├─ batch_id
├─ lifecycle_id / project_id
├─ evidence_snapshot_hash
├─ plan_hash_before?
├─ items[1..6]
├─ created_at / expires_at
└─ source

DecisionItem
├─ item_id / kind
├─ question / impact
├─ options[] / recommended_option?
├─ answer_type
├─ required
└─ evidence_refs[]
```

生命周期仍最多存在一个未解决批次，不创建多个并行 decision 对象。

### 5.2 进入批次的规则

只有以下内容允许成为 item：

- 计划所需但项目证据无法确定的输入；
- 会改变科学含义的 atlas、GSR、TR、template、subject scope；
- overwrite、experimental backend 或外部工具确认；
- 当前目标不支持或有歧义时的 goal revision。

以下内容不得询问用户：可从项目索引确定的受试者数、已登记 artifact ID、当前 run 状态、配置是否启用、rawdata 是否只读。这些必须自动读取。

### 5.3 推荐值

- 推荐值必须来自当前项目证据、明确 Memory suggestion 或代码内安全默认；
- 每个推荐值记录 `recommendation_source`；
- 科学建议仍需用户选择，不可由超时或空回答自动接受；
- 无可靠来源时 `recommended_option=null`，不得让模型伪造最佳方案。

### 5.4 Answer API

将请求改为：

```json
{
  "batch_id": "...",
  "answers": [{"item_id": "atlas", "value": "aal"}],
  "command_id": "...",
  "actor": "..."
}
```

后端一次校验：batch 未过期、属于当前 lifecycle、item 唯一、必填完整、option 有效、plan/evidence hash 未变化。任一项错误时不消费批次，并返回字段级结构化错误。

本仓库不保留旧 `decision_id + answer` 兼容路径；同步修改所有当前消费者和测试。

## 6. 执行流程

1. `read_evidence` 构建 Snapshot；
2. Planner 计算缺失前提；
3. 无阻塞项则直接 `draft_plan`；
4. 有阻塞项则排序、去重并限制最多 6 项；
5. 持久化 batch，lifecycle 进入等待用户；
6. 用户一次提交 answers；
7. 后端写入 `command_context.science_answers`，清除 batch；
8. 重新构建 EvidenceSnapshot 并进入 05 的版本化规划。

超过 6 个必要问题说明目标或项目状态不清晰，应请求 goal revision 或转人工，不拆成无上限连续批次。

## 8. 风险与处理

| ID | 风险 | 处理 | 测试 |
|---|---|---|---|
| H04-01 | 读取源影像/秘密 | 来源 allowlist + typed adapter | rawdata/path/secret negative fixture |
| H04-02 | 旧 snapshot 影响新计划 | batch 绑定 evidence/plan hash | 状态变化后回答被拒绝 |
| H04-03 | 模型代替科学决定 | 科学 item 必须显式回答 | 空回答/超时不自动接受 |
| H04-04 | 批次过大 | 1..6 硬上限 | 7 项转 goal revision/handoff |
| H04-05 | 部分答案被静默消费 | 全批次原子校验 | 缺一项时 context 不变化 |
| H04-06 | Memory 变成事实 | 只标 suggestion/source | Memory 与实时证据冲突测试 |

## 9. 测试与验收

至少覆盖：证据充分零提问、多个科学项一次提交、字段级错误、过期批次、项目状态变化、跨项目 ID、无推荐值、Memory 建议仍需确认、GET 纯读。

python -m pytest tests/unit/test_agent_task_commands.py tests/unit/test_agent_task_api.py tests/unit/test_agent_task_read_model.py tests/unit/test_agent_harness_context.py --tb=short --basetemp=.pytest_tmp
npm --prefix src/frontend run typecheck

人工验收：同一任务需要 atlas、TR 和 template 时，用户只看到一个有来源和影响说明的表单；提交一次后系统自动继续到计划或明确的新阻塞点。
