### R-02：启动扫描完整且有界

调用链：应用 startup → planning scheduler / execution coordinator → store 分页查询与扫描 checkpoint → 原有 durable wake → 原 handler。

1. 新增按稳定 `lifecycle_id` keyset 排序的项目隔离查询；SQL 在过滤后 `LIMIT`，单页最多 100 条。查询直接覆盖需恢复的 lifecycle，不先 `list_projects()` 或 fetchall 后切片。规划与执行消费者分别限定合法状态，不能互相获得执行职责。
2. 扫描周期记录消费者、cursor、周期上界和 `_schema_version`（若用 SQLite 行则保持版本列）；持久化页内 wake 与 cursor 的推进必须防止“先越过 cursor、后漏登记”。崩溃恢复允许重扫该页，由稳定 wake/step key 去重。
3. 一次启动只推进有界页；未完成周期通过已有受控 worker/持久任务继续，不要求用户再次刷新。周期结束后归零开始下一周期，避免新增低序 ID 永久遗漏。shutdown、租约、单 owner、通知沿用现有边界，不新增无限自主模型循环。
4. 规划只补缺 wake，不能批准、执行、调用模型；执行只追踪原 run，不创建第二个 run/ticket/dispatch。终态及等待输入/审批不自动推进。
5. 同步 `api/dependencies.py` 的 store Protocol、`services/mock_store.py` SQLite 实现、scheduler/coordinator、测试替身与所有扫描调用方。原通用 list API 若还有消费者继续保持其当前职责，不为续扫增加 fallback。

测试：原 101 项目回归；205 个项目及单项目 205 lifecycle；尾部 CREATED、RUNNING/OBSERVING/EVALUATING；重复两轮；页中断、cursor 提交中断、DB 重开；新插入 ID；每页 SQL 上限；scan 本身 planner/executor/GET 副作用为 0。不能通过提高 RESCAN_LIMIT 或无界全扫“修好”尾部测试。

完成定义：尾部最终可恢复、每批资源有界、重启不重复提交、恢复不依赖后续用户操作。D-10 的实现选择由本次修复确定为续扫；发布性能阈值和真实规模验收仍待维护者确认。

3. 支持目标缺 BIDS/运动参数/必要输入时进入可恢复补充；真正不支持才 goal_revision。metadata-only 计划不得要求不存在的计算产物，也不能标 computed；可执行目标仍需输入链和审批。

完成定义：同一受支持候选可受审；不再误要求用户换目标；没有新增算法/外部节点或科学等级提升。

### R-04：模板与多项科学输入可补充

1. 核对 `llm_planner` 的 `registered_template_resources`、项目诊断、已注册 artifact/资源入口以及 checksum/license/path 校验；复用现有注册链。若缺端到端入口，只增加该项目模板资源的受控输入补充，不建立通用文件执行器。
2. 有合法候选时仍由用户选择；无合法候选时返回结构化 `input_required` 原因与允许下一动作，展示注册/补充入口、来源和影响，禁用无效提交。空 options 不得伪装成可回答科学决定。
3. 前端通过共享 API 或已批准 bridge 选择只读资源，不直接写 FS。后端 resolve、项目/允许读取范围、内容 checksum、许可证和模板空间/格式验证为权威；不自动下载或选择替代模板。
4. 注册完成后重新采集证据并生成当前有效 batch；旧 batch/hash/答案必须失效。保持 atlas/TR/template 多项同表单、有字段级错误，未确认建议不进入计划。

### R-05：拒绝已确认问题的重复模型提问
