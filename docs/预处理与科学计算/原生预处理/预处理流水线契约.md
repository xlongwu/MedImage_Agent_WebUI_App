# Reviewed Preprocessing Pipeline Contract

Current as of 2026-07-25.

This contract summarizes the current reviewed preprocessing pipeline boundary
for developers. `AGENTS.md` remains the authoritative repository operating
contract.

## Architecture Boundary

The frontend may configure and submit reviewed preprocessing requests, but
backend services and registered node runners remain the source of truth for
execution, safety, state, provenance, and artifact registration.

Server-side layering remains:

```text
Route
-> Request/Response Schema
-> Service
-> Runtime / Runner or Scientific Kernel
-> State and Artifact Storage
```

Frontend code must use `src/frontend/src/lib/api/preprocessing.ts` and shared
types from `src/frontend/src/types.ts`. It must not access the filesystem
directly.

## Reviewed Execution Request

The frontend reviewed flow submits
`PreprocessingPipelineExecuteRequest` to:

```text
POST /api/projects/{project_id}/preprocessing/runs/{preprocessing_run_id}/execute-reviewed
```

Required user-side confirmations are:

- `confirm_rawdata_readonly`
- `confirm_reviewed_execution`
- `confirm_external_tools_if_needed`
- `confirm_research_use_only`
- `confirm_no_clinical_use`

The backend still decides whether execution is allowed. UI confirmations do
not bypass Approval Gate, environment gates, safe-path checks, or artifact
precondition checks.

### Reviewed subject and stage scope

When a goal names an explicit BIDS subject such as `sub-001`, the planner must
persist that value as `native_preproc_full_execute.params.subject_id`. If a
goal requests one subject but multiple registered candidates exist without an
explicit ID, planning must stop at a structured subject-selection decision.
The selected subject is then included in the normalized parameter hash,
Reviewed Plan, Approval Summary, execution request, and output provenance.

The phrase “minimal rs-fMRI preprocessing” selects the reviewed minimal stage
profile: input and sidecar validation, realignment, motion QC, nuisance
regression, detrending, temporal filtering, subject QC, validation report, and
final report. All other stages are explicitly disabled in `stage_overrides`;
they must not inherit broader defaults silently.

The review-time Goal Contract uses the same immutable subject and stage scope.
It accepts the reviewed singular `params.subject_id` and normalized
`metadata.subject_scope`, and only requires numerical artifact types produced
by enabled output stages. For example, the minimal profile above requires
`residual_bold` and `filtered_bold`; disabled ALFF, fALFF, ReHo, and functional
connectivity stages are not treated as missing outputs. Legacy reviewed plans
without an explicit output-stage override map retain the historical full-output
contract so an already reviewed expectation is never weakened silently.

Registry-backed and registered-BIDS batch discovery must filter to the reviewed
`subject_id` before invoking the numerical runner. Omitting `subject_id`
preserves the existing reviewed all-subject batch behavior.

## Automatic ACPC Alignment

`native_auto_acpc_align` is an optional standalone reviewed node. It does not
change the default native-full stage order and may run only when a plan names
one registered T1w artifact. The node accepts an artifact ID rather than a
caller-controlled source path, writes only beneath the project
`derivatives/` root, and requires the normal Reviewed Plan, Approval Gate,
Execution Ticket, audit, and execution gateway.

The initial resource is the checksum-pinned SPM12 `avg152T1.nii` manifest
`spm12_avg152_t1_ras`. The CPU-only algorithm performs deterministic 6-DOF
rigid registration, back-projects template AC/PC into subject RAS+ millimetres,
constructs a right-handed ACPC frame, and writes `acpc_t1w`,
`transform_matrix`, `acpc_landmarks`, and `qc_json` artifacts. Landmark fields
are estimates, not manually located anatomy. QC failure or a missing/unsafe
input fails closed and does not register final artifacts. This is `computed`,
not `validated`, until independent manually annotated-reference evidence is
supplied.

## Native CPU Subject Scheduling

`NativeFullPreprocRequest.cpu_policy` controls subject-level CPU
scheduling. `serial` is the default and reference behavior. Reviewed `process`
and `auto` modes may use process-based subject parallelism, but the selected
worker count is always bounded by the request ceilings, available CPU threads,
reserved CPU capacity, a conservative per-subject memory estimate, and the
runtime safety cap. If live memory telemetry is unavailable, planning falls
back to one serial worker.

Each worker owns one subject and writes only to that subject's run-scoped
directory. The parent process remains the single owner of aggregate state,
manifest, progress, and final result assembly. Scientific stage parameters and
the canonical kernels do not change with worker count, and nested subject-level
process pools are not created.

Native async execution is exposed through:

```text
POST /api/projects/{project_id}/preprocessing/native/full/execute/async
GET  /api/projects/{project_id}/preprocessing/native/runs/{run_id}
GET  /api/projects/{project_id}/preprocessing/native/runs/{run_id}/progress
```

The persisted progress projection records per-subject state, heartbeat, and
terminal status. A stale heartbeat is reported as interrupted rather than
inventing success. The current resource plan is deliberately conservative and
fixed for a submitted run; the `adaptive_replanning` contract field must not be
read as evidence of continuous mid-run worker rebalancing.

Agent Task observation uses this persisted native progress as the authority for
subject completion counts. The project-level Pipeline Runtime node still owns
pipeline node totals; subject progress observations do not inflate or conflict
with that single project node count.

## Native GPU Compute Policy

`NativeFullPreprocRequest.compute_policy` is the only reviewed interface for
native GPU execution. It accepts `backend="cpu" | "gpu" | "auto"`, a fixed
`device="auto" | "cuda:0"`, precision, memory/job/chunk ceilings, and
per-stage overrides for the released GPU stages:

- ALFF/fALFF;
- FFT temporal filtering;
- nuisance-regression numerical linear algebra (the design matrix remains
  CPU-built);
- ROI functional connectivity.
- spatial smoothing with nearest-boundary, spatial-axis-only semantics;
- atlas resampling with nearest-neighbour label interpolation only.

`cpu` remains the default reference path. `gpu` is require-GPU: missing CuPy,
CUDA, device tokens, live VRAM, or a GPU numerical failure blocks the stage;
it never silently runs CPU. `auto` may run CPU, and the selected backend plus
its limiting/fallback reason are included in each stage QC/provenance record.
Until a stage has separately met its real-data performance release criteria,
`auto` intentionally remains conservative and chooses CPU.

Completed GPU stages add a path-free sample to the versioned local performance
model. Samples are keyed by algorithm, device/runtime and workload estimate;
they record cold/warm timing and estimated peak memory, but never loosen a
capability, memory, or scientific-parameter gate.

### CPU/GPU numerical and timing comparison contract

Before accepting a GPU numerical artifact, the matching CPU-reference artifact
must have the same shape, `float32` output dtype, affine, and finite-value
status. The numerical comparison is stage-specific; it is never a single
global tolerance. The current released thresholds are:

| Stage | Relative tolerance | Absolute tolerance | Additional invariant |
| --- | ---: | ---: | --- |
| spatial smoothing | `1e-4` | `4e-4` | spatial axes only; nearest boundary semantics |
| nuisance regression | `1e-4` | `5e-4` | same CPU-built confound matrix and timepoint count |
| FFT temporal filtering | `1e-4` | `3e-4` | identical frequency-bin mask and timepoint count |
| ALFF | `1e-4` | `7e-4` | identical TR, numerator and denominator bands |
| fALFF | `1e-5` | `1e-6` | identical TR, bands, and zero-denominator handling |
| ROI functional connectivity | `1e-4` | `1e-4` | symmetric matrix, unit diagonal, constant-ROI policy |
| atlas resampling | n/a | n/a | output labels are a subset of input labels; exact reference affine/grid |

These limits are based on the CPU reference and a real BIDS baseline with
`64 x 64 x 33 x 240` BOLD volumes and `TR=2.0`; they retain margin above the
observed float32 backend differences without changing any scientific parameter.
FC remains restricted to synthetic/reference testing until a reviewed,
caller-supplied atlas supports a real-data comparison. ReHo remains CPU-only.

GPU provenance records synchronized `transfer_seconds`, `compute_seconds`, and
`total_seconds`; CPU reference provenance records zero transfer time and the
same numerical-boundary timing shape. Stage wall-clock time, NIfTI I/O, and
artifact registration must be reported separately from these kernel timings.

GPU computation is not a second pipeline: native stages still own input
validation, artifact writes, QC, manifest registration, and provenance. ReHo,
registration, normalization, I/O, approval, and audit remain CPU-owned unless
separately released by a scientific-validation task. ReHo's CuPy kernel is
experimental and is not selected by the native stage until its independent
release gate is completed.

## Status Semantics

UI, report, validation, and docs must preserve these distinctions:

- `blocked` is not a failed computation; it means execution did not proceed
  because required evidence or gates were missing.
- `metadata_only` must not be counted as computed.
- `preview_only` must not be counted as full research output.
- `partial` must disclose the subset or missing stage.
- `succeeded` requires backend evidence and registered artifacts for the stage.

Artifact-level `metadata.stage_status` and `metadata.capability_level` are
projected into the scientific limitation summary. In particular,
`simplified`, `preview_only`, and `partial` remain visible even when downstream
files are reloadable. Metadata-only report artifacts do not by themselves
downgrade otherwise valid numerical outputs; `metadata_only` is blocking when
it applies to a Goal Contract-required numerical artifact. Optional missing log
excerpts remain disclosed as incomplete observation sources, but they do not
override a satisfied Goal Contract whose required evidence is present,
consistent, registered, and reloadable.

Once numerical stage outputs are appended to the run registry,
`safety_flags.no_preprocessing_executed` is `false`. Input-registration and
preflight-only registries keep the flag `true`.

`execution_limits.preview_limit` is the reviewed preview switch. When it is
present, affected stage results, manifests, reports, validation summaries, and
UI summaries must label the run `preview_only`. `max_subjects` is a subset
limit and must be reported as `partial` when it truncates the discovered
subject scope.

## Realignment And Motion QC Contract

Minimal FC v1 may resume from reviewed registered realignment outputs. A
realignment output is not complete for downstream nuisance regression unless
the registry contains:

- realigned BOLD;
- motion parameters;
- FD time series;
- motion QC JSON or summary evidence.

Registering reviewed SPM sandbox outputs may compute deterministic Python
motion QC from derivative `rp_*.txt` files. This does not enable MATLAB/SPM
execution and does not modify rawdata.

SPM sandbox execution must not silently cap discovered BOLD files. The default
selection policy is `all`; if `preview_limit` is supplied, manifest,
provenance, subject status, and API response must record
`selection_policy=explicit_preview_limit` and `preview_only=true`.

## FC Artifact Contract

Formal FC output should expose, when available:

- ROI time series;
- correlation matrix;
- Fisher-z matrix;
- labels;
- QC;
- provenance;
- artifact registry ids or paths returned by the backend.

Synthetic atlas output remains preview-only. A real atlas path must be reviewed
and must pass backend space/shape checks before the output can be treated as
atlas-grounded.
