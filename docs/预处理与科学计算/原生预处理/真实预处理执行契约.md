## 1. Purpose and Scope

This document defines the **Phase 4A real preprocessing execution contract**
for MedImage Agent.  It specifies the complete end-to-end execution contract
from raw DICOM upload to DPARSFA-style rs-fMRI preprocessing outputs, covering
conversion, preprocessing stages, approval/audit requirements, output policies,
external-tool gating, provenance, QC reporting, and staged implementation
planning.

**Historical Phase 4A constraints (not current implementation claims):**

- **Real preprocessing is NOT implemented in this document.**  This is a
  design contract, not an implementation.
- **Real DICOM conversion (dcm2niix) is NOT implemented.**
- **MATLAB/SPM/DPABI/FSL/AFNI execution remains disabled.**
- **Rawdata remains read-only.**  No pipeline node, executor, or artifact
  may write to or modify `rawdata/` or any file in the DICOM input tree.
- **Safe allowlist is not expanded.**  All external-tool nodes remain
  outside the safe execution allowlist.
- **Research-use only, not clinical diagnosis.**
- **No frontend behavior changes.**
- **No modification to pipeline runtime behavior.**

This contract is a **pre-implementation design document** that establishes
formal invariants, stage definitions, schemas, and test strategies *before*
any code changes to conversion, execution, or external-tool integration are
made.

### 5.2 Future conversion execution

When real conversion is implemented (Phase 4B or later), it must satisfy:

1. **Dry-run first**: `POST .../conversion/dry-run` must return `status=ready`
   and `blocking_issues=[]`.
2. **Approval gate**: `conversion_execute` requires `approved=true` and

   output NIfTI paths, dcm2niix version, and conversion parameters.
8. **Rawdata unchanged**: checksum verification before/after conversion.
9. **Rollback**: if conversion fails, all partial outputs must be removed and
   the failure recorded with `ExecutionFailureRecord`.

## 6. Preprocessing Execution Contract

### 6.1 Execution model

Preprocessing execution follows the existing Phase 3 productized model:

```
Reviewed Plan → Consistency Preflight → Approval Gate → Audit Record
    → Node Execution (DAG order) → Output Manifest → Provenance
    → Artifact Discovery → Run History → State Timeline
```

Each preprocessing stage is a **node** in the pipeline DAG.  Subject-level
nodes execute in parallel within `ThreadPoolExecutor`.  Group-level nodes
execute after all subject-level nodes complete.

### 6.2 Preprocessing pipeline stages

The target DPARSFA-style workflow is modelled as the following ordered stages:

| # | Stage ID | Backend | External Tool | Subject-Level |
|---|---|---|---|---|
| 1 | `dicom_to_nifti` | external | dcm2niix | yes |
| 2 | `bids_organization` | python | none | no (project-level) |
| 3 | `remove_initial_volumes` | python/matlab | SPM (optional) | yes |
| 4 | `slice_timing` | matlab | SPM | yes |
| 5 | `realignment` | matlab | SPM | yes |
| 6 | `t1_coregistration` | matlab | SPM | yes |
| 7 | `t1_segmentation` | matlab | SPM | yes |
| 8 | `normalization` | matlab | SPM | yes |
| 9 | `nuisance_regression` | matlab | SPM/DPABI | yes |
| 10 | `temporal_filtering` | matlab | DPABI | yes |
| 11 | `spatial_smoothing` | matlab | SPM/DPABI | yes |
| 12 | `alff_falff` | matlab | DPABI | yes |
| 13 | `reho` | matlab | DPABI | yes |
| 14 | `functional_connectivity` | matlab | DPABI | yes |
| 15 | `subject_qc` | python | none | yes |
| 16 | `group_summary` | python | none | no (project-level) |
| 17 | `derivative_summary` | python | none | no (project-level) |

Stages 12-14 (ALFF/fALFF/ReHo/FC) are **optional** and controlled by
pipeline configuration.

## 10. Rawdata Read-Only Invariant

Every preprocessing stage, regardless of backend, must satisfy:

- No file in `rawdata_dir` may be opened for writing or appending.
- No file in `rawdata_dir` may be deleted, renamed, or moved.
- Pre-execution and post-execution checksums of all rawdata files must match.
- The `rawdata_read_only` safety flag is set on every node response.
- If the invariant is violated (checksum mismatch), the run transitions to
  `RUN_SAFETY_VIOLATION` and all downstream nodes are blocked.

## 11. External Tool Policy

### 11.1 General policy

- Every external tool invocation must go through a `command_template` wrapper.
- No direct `subprocess.run()` or `os.system()` calls are permitted.
- stdout and stderr must be captured to `<run_dir>/logs/<node_id>_stdout.log`
  and `<run_dir>/logs/<node_id>_stderr.log`.
- Return code must be checked; non-zero → node `failed`.
- Timeout must be enforced per node.
- The `ExecutionProvenance` record must include `command_template_id`,
  `batch_sha256`, and `external_tool_version`.

### 11.2 Required environment flags for real execution

All of the following must be set to `"1"` before any external tool runs:

| Flag | Purpose |
|---|---|
| `MEDIMAGE_MATLAB_ENABLED` | Confirms MATLAB is present and authorised |

| `MEDIMAGE_ENABLE_REVIEWED_EXECUTION` | Gates reviewed-plan execution |
| `MEDIMAGE_ENABLE_REAL_PREPROCESSING` | Node-specific execution gate for preprocessing |

If any flag is missing, all external-tool nodes are blocked regardless of
allowlist state.

## 13. Failure Handling

### 13.1 Per-node failure

| Scenario | Node Status | Run Behaviour |
|---|---|---|
| External tool returns non-zero | `failed` | `stop_on_failure` determines cascade |
| Output manifest missing required file | `failed` | Block downstream |
| Timeout exceeded | `timeout` | Retry eligible |
| Checksum mismatch (post-execution) | `failed` | Block downstream, flag rawdata safety |
| Approval missing | `blocked` | No execution, preflight blocked |
| Environment flag missing | `blocked` | No execution, preflight blocked |

### 13.2 Run-level failure

| Run Status | Meaning | Next |
|---|---|---|
| `failed` | One or more nodes failed, `stop_on_failure=true` | Retry failed nodes |
| `partial` | Some nodes succeeded, some failed, `stop_on_failure=false` | Resume from first failed |
| `blocked` | Unrecoverable pre-condition | Fix condition, re-submit |
| `timeout` | Run-level timeout | Retry with longer timeout |
| `interrupted` | Process terminated unexpectedly | Resume after confirming dead |

### 13.3 Rollback policy

- For external-tool nodes: if failure occurs mid-execution, all output files
  written by that node must be removed (best-effort rollback).
- Successful upstream node outputs are preserved.
- Rollback events must be recorded in the node's `ExecutionFailureRecord`.

## 14. Retry / Resume Policy

Aligned with `docs/规划与运行时/运行重试与恢复契约.md`:

- **Retry**: re-execute failed/blocked/timeout nodes only.  Successful nodes
  from the original run are reused (with checksum verification).
- **Resume**: continue from the first non-terminal node.  Upstream successful
  nodes are reused.
- **Rerun**: fresh execution, all nodes re-executed.
- Retry/resume are NOT implemented in the current phase.

## 17. QC Report Contract

### 17.1 Subject-level QC

After preprocessing completes for a subject, a `subject_qc` node generates:

- Motion parameter summary (max translation/rotation, mean FD, % scrubbed)
- Spatial normalisation quality metric (correlation to template)
- T1 segmentation tissue volumes (GM, WM, CSF)
- Functional-to-anatomical coregistration cost
- Any stage-level warnings or failures

### 17.2 Group-level QC summary

After all subjects complete, a `group_summary` node aggregates:

- Per-subject QC metrics table (CSV)
- Group mean ± SD for key metrics
- Exclusion recommendations (subjects exceeding thresholds)
- Markdown report with embedded tables

### 17.3 QC thresholds (DPARSFA convention)

| Metric | Warning Threshold | Exclusion Threshold |
|---|---|---|
| Max translation | > 2.0 mm | > 3.0 mm |
| Max rotation | > 2.0° | > 3.0° |
| Mean FD | > 0.2 mm | > 0.5 mm |
| % volumes scrubbed (FD > 0.5) | > 20% | > 40% |
| Normalisation correlation | < 0.80 | < 0.70 |

## 18. Subject-Level Execution Model

Each subject is processed independently through the preprocessing DAG.
Subject-level nodes accept `subject_id` and `subject_record` parameters.

Execution flow for subject `sub-001`:

```
1. dicom_to_nifti(sub-001) → converted_bids/sub-001/
2. bids_organization(project) → organises converted outputs
3. remove_initial_volumes(sub-001) → trims first N volumes
4. slice_timing(sub-001) → slice-time corrected BOLD
5. realignment(sub-001) → motion-corrected BOLD + rp_*.txt
6. t1_segmentation(sub-001) → c1/c2/c3 tissue maps
7. t1_coregistration(sub-001) → coregister T1 to BOLD
8. normalization(sub-001) → warp to MNI
9. nuisance_regression(sub-001) → regress WM/CSF/global/motion
10. temporal_filtering(sub-001) → bandpass filter
11. spatial_smoothing(sub-001) → Gaussian smooth
12. [alff_falff(sub-001)] → optional ALFF/fALFF
13. [reho(sub-001)] → optional ReHo
14. [functional_connectivity(sub-001)] → optional FC
15. subject_qc(sub-001) → QC report
```

Subjects execute in parallel via `ThreadPoolExecutor` where DAG dependencies
permit.

## 19. Group-Level Summary Model

After all subject-level processing completes:

```
16. group_summary(project) → aggregates all subject QC
17. derivative_summary(project) → catalogues all outputs
```

Group-level nodes are project-level (not subject-level).  They depend on
all subject-level `subject_qc` nodes completing successfully.
