# MedImage Agent Architecture

This document describes the current architecture. It is not a roadmap,
completion report, or test baseline.

## 1. System Overview

```text
Frontend (React + TypeScript + Vite)
    -> HTTP API / Electron bridge
API Layer (FastAPI + Pydantic)
    -> Request/response schemas
    -> Services and read models
Agent Runtime (Plan-then-Execute + Approval Gate)
    -> Pipeline Runtime (DAG executor + scheduler)
    -> Plugin Node Registry
    -> Tool Catalog
Storage (SQLite project store + atomic JSON state/artifacts)
```

The LLM is advisory. Pipeline execution is deterministic and must flow through
the Pipeline Runtime and registered node runners.

## 2. Frontend

Location: `src/frontend/src/`

Primary responsibilities:

- Project selection and Agent-first workflow navigation.
- A default Agent workspace where the user states one research goal, answers
  only unresolved scientific questions, approves one server-issued summary,
  and reads the evidence-backed result.
- Plan review, run history, artifact preview, QC/readiness panels, DICOM review,
  and preprocessing workspace UI.
- An off-by-default advanced mode that exposes the established specialist
  workspaces without changing backend execution authority.

Current structure:

| Path | Responsibility |
| --- | --- |
| `App.tsx` | top-level app composition |
| `features/` | feature-level UI areas such as dashboard composition |
| `features/agent/` | Agent Task controller, goal/decision/approval/result views, and layered evidence UI |
| `components/` | reusable and domain-specific panels |
| `hooks/` | shared React hooks |
| `lib/api/client.ts` | shared HTTP client and base URL resolution |
| `lib/api/*.ts` | domain API modules |
| `lib/api/legacy_re_exports.ts` | compatibility export surface |
| `state/` | workflow state models |
| `types.ts`, `types/` | frontend type definitions |

Rules:

- Frontend code must call backend HTTP APIs through `src/frontend/src/lib/api/`.
- The removed root-level frontend API module must not be recreated.
- The UI must not directly access local files.
- Feature flags control visibility only; backend gates remain authoritative.

## 3. API Layer

Location: `src/backend/app/api/`

`main.py:create_app()` registers middleware and includes domain routers.

### Middleware

Registered order in `create_app()`:

1. `CORSMiddleware`
2. `RequestLoggingMiddleware`
3. `RequestIDMiddleware`
4. `RateLimitMiddleware`
5. `APIVersionMiddleware`

Starlette executes the last registered middleware first on the request path, so
`APIVersionMiddleware` handles inbound `/api/v1/` rewrites before inner route
handling.

### Router Ownership

`api/routes.py` is limited to:

- `GET /health`
- `GET /api/project-config`
- `_load_project_config()`

Domain routers include advisor, agent, artifact, approval/audit,
Agent Task projection/commands, dashboard/conversion workflow, desktop, DPABI, execute-reviewed, experiment,
external smoke, GPU, LLM planner, pipeline, planner, plan validator,
preset, project, project history, realdata, rs-fMRI, session, and tool catalog.

`dashboard_routes.py` remains a large legacy aggregation and conversion
workflow surface. New unrelated execution domains should be split into new
domain routers rather than added there.

### Error Handling

Routes should raise structured errors through `raise_api_error()` and the
`MedImageError` hierarchy. The global error middleware converts unhandled
exceptions into structured 500 responses.

## 4. Schemas

Location: `src/backend/app/schemas/`

Schemas define stable request/response contracts and pure validation helpers.
They should not perform filesystem writes, launch subprocesses, or import the
Pipeline Runtime for side effects.

Major schema areas include pipeline definitions, execution state and manifests,
DICOM conversion safety/readiness/approval, preprocessing execution, ACPC
alignment contracts, and advisor models.

## 5. Services

Location: `src/backend/app/services/`

Services contain business logic, read models, persistence helpers, readiness
evaluations, and controlled wrappers around domain operations. Routes should
delegate non-trivial work to services.

Important service areas:

- Project and desktop store access.
- Data readiness, BIDS validation, DICOM detection, conversion planning,
  conversion safety/readiness/review package services.
- Preprocessing dry-runs, sandbox execution coordination, output registration,
  validation, and report generation.
- Run artifact discovery/preview, run event/log reading, run summaries, and run
  state timeline read models.
- Run artifact discovery joins the exact selected run link with its
  preprocessing artifact registry and project-scoped audit projection; it
  rejects cross-run registry metadata and path ownership before projecting
  preprocessing, QC, report, audit, or derivative artifacts.
- QC dashboard reports and cache fingerprinting.
- Project-scoped Agent Task commands and read projection over the canonical
  lifecycle, Reviewed Plan, ticket, run, observation, evaluation, recovery,
  and artifact records.
- A bounded post-run reconciler and evidence-derived result summary. Successful
  synchronous reviewed execution coordinates the linked lifecycle before the
  response returns. GET projections remain side-effect free; startup
  reconciliation is an explicit, environment-gated, single bounded pass. The
  managed Electron sidecar enables that pass so a completed run cannot remain
  projected as `RUNNING` after the desktop application restarts.

## 6. Agent Runtime

The Agent command path is finite and service-owned:

```text
goal -> context -> deterministic planning -> optional science decision
     -> validation -> Reviewed Plan -> one stable Approval Summary
     -> human approval -> approval-bound dry-run
     -> Execution Ticket -> Execution Gateway
     -> run evidence -> observation -> goal evaluation
     -> result or one unapproved recovery proposal
```

Terminal observation keeps scientific capability and limitation dimensions
separate. Registered, reloadable numerical outputs can establish `computed`
while a reviewed `simplified` flag remains visible; that flag does not become a
validation claim. Goal evaluation applies the immutable contract's allowed and
forbidden limitation sets independently from its minimum capability threshold.

`AgentTask` is a read projection, not a second state machine. Scientific
choices such as atlas, GSR, conflicting TR, template, output conflict, and an
experimental GPU backend stop for a user answer. Recovery is never
auto-approved. The Agent must not become an open-ended autonomous loop, and
execution remains gated by the Approval Gate, ticket, Tool Catalog, and sole
Execution Gateway.

Planning must not invoke an execution dry-run, runner, external tool, ticket,
or dispatch path. The dry-run that authorizes execution is performed only
after the user approves the unchanged Approval Summary and is bound to that
approval. A dry-run failure stops before ticket dispatch. Plan-only goals stop
after Reviewed Plan persistence and create no execution approval, dry-run,
ticket, run, or numerical artifact.

### 6.1 Controlled single-Agent Harness

The optional Harness (`MEDIMAGE_AGENT_HARNESS_ENABLED=false` by default) is a
bounded control layer around the planning and explanation portion of this
path, not another lifecycle or execution runtime. One `AgentHarnessAttempt`
is bound to each enabled `AgentLifecycleRecord`; immutable redacted context
snapshots and ordered idempotent steps are persisted as dependent records.
Each lease claim processes one step only, with hard limits of at most six model
calls, eight action proposals, 300 seconds, and two stale-lease takeovers.

The model can return only a versioned `ActionEnvelope`: `read_evidence`,
`request_decision`, `draft_plan`, `explain_result`, `propose_recovery`, or
`finish`. Unknown actions, state mismatches, cross-project references, invalid
JSON after one repair request, exhausted budgets, and provider failures stop
safely. `draft_plan` delegates to the existing Goal Planning Service and
validator; no envelope grants approve, ticket, gateway, runner, shell, file,
or database-write capability. A missing provider or Harness failure falls back
to the existing command path. GET projections only read the redacted Harness
summary and never coordinate or call a model.

### 6.2 Memory Domain and the only planner injection path

Long-term memory is a separate, project-scoped domain rather than a second
Agent state machine:

```text
committed lifecycle/run/observation facts
    -> transactional desktop SQLite outbox
    -> deterministic filter and candidate extraction
    -> explicit review -> project-serial consolidation
    -> independent memory SQLite authority + FTS
    -> consent-gated bounded MemoryContext
    -> current-task science confirmation when needed
    -> Reviewed Plan -> Approval Summary
```

The planner receives no scientific memory as a constraint. A scientific
project decision is represented only as an advisory suggestion with revision,
algorithm, configuration, applicability, confirmation event, and source
references. The Agent command service must obtain a current-task answer before
the plan may use the value. The exact context hash and references are then
bound to the Reviewed Plan and Approval Summary, so later memory changes cannot
alter an already reviewed or approved plan.

## 7. Pipeline Runtime

Location: `src/backend/app/runtime/pipeline_executor.py`

Responsibilities:

- Validate DAG dependency order.
- Execute registered nodes through node runners.
- Schedule project-level and subject-level work.
- Persist run/node state and summaries.
- Keep execution deterministic and auditable.

Cleanup, documentation, and route refactors must not change Pipeline Runtime
semantics unless explicitly authorized.

## 8. Node Registry

Locations:

- `src/backend/app/runtime/node_registry.py`
- `src/backend/app/runtime/node_registry_plugins/`

`node_registry.py` is a compatibility shim. Actual node registrations live in
plugin modules:

- `core_nodes.py`
- `dpabi_nodes.py`
- `gpu_nodes.py`
- `spm_nodes.py`
- `qc_nodes.py`
- `rsfmri_nodes.py`
- `report_nodes.py`
- `conversion_nodes.py`

`create.py` merges plugin `REGISTRY` dicts and duplicate IDs must fail. New
nodes belong in the proper plugin, must keep stable `node_id` strings, and
must be covered by Tool Catalog and safety allowlist rules when executable.

## 9. Tool Catalog and Approval Gate

Locations:

- `src/backend/app/runtime/tool_registry.py`
- `src/backend/app/runtime/tool_catalog.py`
- approval/audit routes and planner modules

The Tool Catalog describes permissions such as read-only status, file writes,
destructive behavior, confirmation requirements, and path scopes. File-writing
and execution actions must preserve explicit approval/audit paths.

## 10. Storage

Storage is local and project-scoped:

- SQLite desktop/project store for project metadata and run links.
- The desktop/project SQLite also owns memory consent, transactional outbox,
  source projections, and the forget ledger; it does not duplicate long-term
  memory content.
- A separate memory SQLite is the sole authority for candidates, active items,
  immutable revisions, source links, commands, events, tombstones, watermarks,
  leases, jobs, and FTS. Its schema and recovery are managed independently.
- `work/memory/` JSON/Markdown output is optional, atomically rebuilt, and never
  authoritative. Projection is disabled by default and cannot target rawdata.
- JSON run state, node state, summaries, manifests, and audit artifacts.
- Immutable application audit records plus atomic, schema-versioned
  `project_dir/reports/audit_records/` projections used by run-scoped reads.
- Runtime outputs under ignored work/output roots.

State JSON must use `atomic_write_json()` and carry `_schema_version`.
Rawdata is read-only.

## 11. Desktop Packaging Boundary

Locations:

- `desktop/electron/`
- `desktop/packaging/`

The desktop app uses Electron as the shell and a PyInstaller backend sidecar.
The frontend uses HTTP APIs and the approved Electron bridge. Offline Electron
runtime zips and NSIS caches are local build resources and should not be
deleted during cleanup.

Generated packaging output such as unpacked app directories, installers,
portable EXEs, and PyInstaller `_MEI*` temp directories are runtime/build
artifacts unless explicitly promoted by a release artifact process.

## 12. Safety Boundary

Core invariants:

- No rawdata modification.
- No Approval Gate bypass.
- No direct frontend filesystem access.
- No hidden external-tool execution.
- No hardcoded secrets or private data paths.
- Research use only.

Detailed agent rules live in `AGENTS.md`; this document references those rules
instead of duplicating them.
