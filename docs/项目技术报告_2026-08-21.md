## 1. 项目概述

MedImage Agent 是一个面向静息态功能磁共振（rs-fMRI）研究工程的本地优先、确定性 Plan-then-Execute 平台。它把自然语言研究目标、数据准备、计划审阅、人工审批、受控执行、科学产物、QC、运行证据和可选长期记忆放进同一条可审计链路；它不是临床诊断或治疗决策系统。

Python、React 和 Electron 三个 manifest 当前都标记为 `0.6.0-rc1`；`PROJECT_STATE.md` 将 RC2 作为后续目标。由于当前工作树不是已冻结 release，版本号只能说明 manifest 表面，不能证明这些未提交改动已经打包发布。

主要使用方是通过 React/Electron 桌面界面工作的研究人员；FastAPI 也可被本地脚本和测试直接调用。当前核心能力包括：项目与数据索引、DICOM/BIDS/NIfTI 证据管理、确定性或可选 LLM 规划、Reviewed Plan、稳定 Approval Summary、Execution Ticket、唯一 Execution Gateway、DAG Pipeline Runtime、原生 Python 预处理与 ALFF/fALFF、ReHo、FC、QC/报告、运行图、可选项目级 Memory Domain，以及离线 Agent 评测。

系统最核心的技术思路不是“让 LLM 自主运行命令”，而是把 LLM 限制在建议与结构化计划层，把真实计算交给确定性、注册化、可验证的 runtime：

> 自然语言目标与已登记项目证据 → 形成 Reviewed Plan 和不可变审批摘要 → 人工按 hash 审批 → 服务端签发绑定完整上下文的 Execution Ticket → 唯一 Gateway 调度注册 node → 生成可重载科学产物、状态、审计与结果投影。

## 2. 项目背景与问题定义

本项目处理的原始问题是：rs-fMRI 流程通常同时涉及文件路径、BIDS/DICOM 前提、预处理顺序、科学参数、外部工具、GPU、长时间运行和人工判断。若直接让 UI、LLM 或脚本拼接命令，会出现审批与实际计划漂移、源数据被误写、算法状态虚报、失败后无法复盘、模型建议被误当成执行权限等问题。

当前设计针对这些风险建立了六个硬约束：

1. `rawdata`、登记源 BIDS/NIfTI/DICOM 永远只读。
2. LLM 只规划、解释或提出有限 Action，不拥有执行、审批、路径或命令权限。
3. Reviewed Plan、Approval Summary、环境快照、MemoryContext 和执行 scope 都以 hash 绑定。
4. 真实计算只能通过 `ExecutionGateway.dispatch()` 进入 `pipeline_executor.run_pipeline()`。
5. node 的参数、输入、输出、backend、allowlist 和能力由 `NodeContract`/Tool Catalog/Execution Ticket 联合约束。
6. “已计算”和“已验证”必须由可重载数值产物、provenance 和独立参考证据支持。

这比“LLM 直接产生并执行脚本”复杂，但换来了可重复、可审计、可拒绝、可恢复和科学状态诚实。代价是服务与 schema 数量较多，历史 API 仍在收敛，完整原生预处理中的若干算法仍是简化实现。

```text
React/Electron

  -> FastAPI route + Pydantic schema
```

## 5. 核心执行流程

### 5.1 入口与配置

桌面版由 `desktop/electron/main.cjs` 启动：寻找空闲 localhost 端口，生成每次启动的新 backend session token 和 Agent approval token，启动隐藏的 PyInstaller sidecar，等待带 challenge-response 的 `/api/health`，再创建启用 `contextIsolation`、禁用 `nodeIntegration`、启用 sandbox 的 `BrowserWindow`。sidecar 入口 `src/backend/app/desktop_backend_entry.py` 只允许绑定 `127.0.0.1`，并用 parent PID watchdog 绑定 Electron 生命周期。

后端导入 `src/backend/app/main.py:app` 时调用 `create_app()`：配置 JSON 日志，校验 Node Registry 与 NodeContract 一致性，验证内置 Agent skill，注册 middleware、异常处理和约 30 个 router。lifespan 进行有界 Agent/sandbox reconcile、invariant scan、planning wake 恢复，以及在显式启用时执行 Memory maintenance。

`ConfigService` 从 `MEDIMAGE_*` 环境变量读取 server、Memory、Harness、Agent model；项目运行路径与安全配置由 `ProjectSettings.from_yaml(project_config_path)` 读取。没有 `.env` 自动加载代码，`.env.example` 只是部署模板，实际环境需由 shell/Electron/容器注入。

### 5.2 项目与输入证据

`project_routes.py:create_project()` 对 `rawdata_dir` 和 `project_dir` 做 resolve、系统目录/根目录拒绝、互相包含拒绝；随后只读检查数据，生成项目内 `data/` 索引和 `project_config.yaml`，将项目写入桌面 SQLite。DICOM 转换、BIDS/NIfTI 注册和预处理都以已登记项目证据为前提，不能只凭用户自然语言声称文件存在。

### 5.3 Agent Task 规划

`POST /api/projects/{project_id}/agent-tasks` 进入 `AgentTaskCommandService.create()`，实际委托 `AgentPlanningService.create()`。服务清洗 goal、计算 hash，通过 `AgentOrchestrator.create()` 在同一事务中创建 lifecycle 与 wake outbox，然后通知 `AgentTaskScheduler`。

Scheduler 以 SQLite outbox 为权威，claim 一条 wake、租约 30 秒、每次只推进一个 planning step；失败采用上限受控的指数退避。`advance_planning()` 构造 EvidenceSnapshot、可选冻结 MemoryContext、science answers、goal revision、provider/model profile 等 `PlanningRequest`，再走默认确定性 planner 或显式启用的 Harness。

计划生成后依次：

1. 应用已确认 science answers；
2. 未决科学选择不超过 6 项时进入 `WAITING_FOR_SCIENCE_DECISION`，更多时要求修改目标；
3. 校验 node、依赖、参数、project readiness 和 Memory influence；
4. 构建 `GoalContract`；
5. 保存 `ReviewedPlanRecord`，绑定 plan/evidence/memory/provenance hash；
6. plan-only 任务记录 `execution_performed=false` 并直接 `SUCCEEDED`；
7. 可执行任务构建稳定 `ApprovalSummary`，进入 `WAITING_FOR_APPROVAL`。

### 5.4 审批与真实执行

用户提交的是当前 Approval Summary 的精确 hash，不是泛化的“同意”。`AgentApprovalExecutionService` 重新加载生命周期和 Reviewed Plan，验证状态、actor、scope、plan hash、summary hash、环境与科学前提；随后才运行 post-approval dry-run。dry-run 失败不会签发 ticket。

执行路径 `execute_reviewed_routes.py:_execute_reviewed_application()` 再验证环境开关、显式确认、审计持久化、项目配置、Reviewed Plan、plan validator、Approval Gate、Plan Adapter、安全 allowlist、原生预处理 readiness 和 dry-run/execute consistency。它先写 pipeline YAML、RunLink 和审计，再由 `ExecutionTicketService.issue()` 冻结 node/backend/roots/readonly roots/allowlist/contract/params/environment/sandbox/memory/goal contract。

`ExecutionGateway.dispatch()` 是唯一生产 dispatch：重新验证 ticket 与当前 registry fingerprint、各 hash 和 policy；准备 sandbox；以 command ID 持久化 dispatch started；消费 ticket；构造只能由 Gateway 创建的 `VerifiedExecutionContext`；调用一次 `run_pipeline()`。若发现“已开始但未记录结果”，返回 `GATEWAY_DISPATCH_OUTCOME_UNKNOWN`，不会盲目重复副作用。

### 5.5 Pipeline Runtime 与结果

`pipeline_executor.run_pipeline()` 读取项目 YAML 与 pipeline YAML，拓扑解析依赖，对每个 node 先执行 capability enforcement，再调用 Node Registry runner。dataset node 串行；subject node 可按 project scheduler 配置使用有界 `ThreadPoolExecutor`，失败 subject 不进入下游。

每个 node 在 runner 前写 `RUNNING`，完成后写终态；状态由 `atomic_write_json()` 同目录临时文件、`fsync`、`os.replace` 原子替换，并带 `_schema_version`。数值产物、artifact registry、QC、provenance、pipeline summary 保存到项目批准的 `work/reports/derivatives/exports` 等根。Reconciler 收集 Observation，`GoalEvaluator` 根据 GoalContract 判断满足、存在 gap 或需人工接管；失败可生成 RecoveryProposal，但必须再次审批并签发 child ticket。

## 6. 核心模块设计

### 6.1 Project/Data Domain

- **作用**：把任意本地目录变成有边界、可审计的研究项目，隔离源数据与输出。
- **输入**：`ProjectCreateRequest`、rawdata 路径、可选 project 路径。
- **处理**：危险路径与重叠检查、数据 inventory、FunRaw/T1Raw 或 BIDS/DICOM 识别、写项目配置与索引、登记 SQLite。
- **输出**：`ProjectDetail`、dataset summary、project config、source refs。
- **关键实现**：`api/project_routes.py`、`tools/data_inspector.py`、`tools/project_config_writer.py`。
- **原因与关系**：规划和执行不直接相信 UI 路径，而引用项目证据；下游 EvidenceSnapshot、Approval、Ticket 均依赖这些稳定引用。

### 6.2 Planning/Reviewed Plan

- **作用**：把自然语言目标转换为可验证 DAG，同时区分“目标不支持”和“目标支持但缺少前提”。
- **输入**：goal、EvidenceSnapshot、science answers、MemoryContext、Tool Catalog。
- **处理**：多语言意图识别、确定性模板或可选 LLM JSON plan、schema/contract 校验、GoalContract 与 provenance 绑定。
- **输出**：`ReviewedPlanRecord`、DecisionBatch 或结构化失败。
- **关键实现**：`GoalPlanningService`、`llm_planner.py`、`plan_validator.py`、`goal_contract_builder.py`。
- **设计原因**：将不稳定的模型输出降为候选，最终由确定性 validator 和当前项目证据裁决；避免 LLM 发明 node 或数据。

### 6.3 Approval/Ticket/Gateway

- **作用**：确保用户审阅的内容与真正执行的内容完全一致。
- **输入**：Reviewed Plan、Approval Summary hash、actor、环境快照、路径 scope。
- **处理**：稳定摘要、hash 复验、post-approval dry-run、ticket 冻结、dispatch 幂等和一次性消费。
- **输出**：`ExecutionTicket`、dispatch/run link、审计事件或结构化拒绝。
- **关键实现**：`ApprovalSummaryService`、`ExecutionTicketService`、`ExecutionGateway`。
- **设计原因**：审批不是布尔值，而是对具体 plan、memory、环境、路径和能力的授权；这关闭了审阅后篡改和跨项目复用。

### 6.4 Runtime/Node Contract

- **作用**：提供唯一确定性计算层和插件化 node runner。
- **输入**：verified context、pipeline DAG、project settings、ticket scope。
- **处理**：拓扑执行、参数 schema、backend 选择、path/capability enforcement、状态持久化。
- **输出**：node state、artifact、summary、错误与 provenance。
- **关键实现**：`node_registry_plugins/create.py`、`node_contract_registry.py`、`capability_enforcement.py`、`pipeline_executor.py`。
- **设计原因**：注册表提供扩展性，NodeContract 提供静态能力语义，Gateway 提供动态授权；三者分离可防止“注册即获权”。

### 6.5 Native Scientific Pipeline

- **作用**：在不依赖 MATLAB/SPM/DPABI 的核心安装中产生真实、可重载的 rs-fMRI 衍生结果。
- **输入**：登记 BOLD/T1/sidecar/atlas、预处理参数、CPU/GPU policy。
- **处理**：按 stage graph 运行数据校验、时序/空间处理、回归/滤波、指标、QC 和报告。
- **输出**：NIfTI、NumPy/JSON 矩阵、transform、confound、QC、manifest、provenance。
- **关键实现**：`native_preproc/orchestrator/runner.py`、`stages/`、`core/`、`artifact_registry.py`。
- **设计原因**：canonical kernel 被 service 与 node runner 复用，避免 API/runtime 各写一套算法；每阶段独立产物便于恢复、验证和人工复核。

### 6.6 Read Model/UI

- **作用**：将复杂内部状态投影为稳定用户状态，不让 UI 推断后端成功。
- **输入**：lifecycle、Reviewed Plan、run link、events、observations、recovery。
- **处理**：`AgentTaskReadModel` 将内部状态映射为 `preparing/running/waiting_for_user/needs_attention/completed`，合并进度、下一动作、审批、结果和证据。
- **输出**：`AgentTaskResponse`、Execution Graph、Runs/QC panels。
- **关键实现**：`agent_task_read_model.py`、`useAgentTaskController.ts`、`useExecutionGraph.ts`。
- **设计原因**：读接口无 reconcile 副作用；前端只轮询投影并在终态停止，避免本地 optimistic state 冒充权威状态。

## 7. Agent / Workflow / Pipeline 设计

### Agent 的真实职责

Agent 负责目标澄清、证据审阅、计划草拟、审批前解释、执行后观察与恢复建议。它不直接读取任意文件、不运行 node、不创建批准、不签发 ticket，也不把 Memory 当权限。生产 owner 始终是单一 `AgentOrchestrator` lifecycle；当前没有生产多 Agent 协作。

### 持久状态机

核心状态转移定义在 `agent_orchestrator.py:_ALLOWED_TRANSITIONS`：

```text
CREATED -> CONTEXT_READY / WAITING_FOR_INPUT
 -> PLAN_DRAFTED
 -> WAITING_FOR_SCIENCE_DECISION -> PLAN_DRAFTED
 -> PLAN_VALIDATED
 -> WAITING_FOR_APPROVAL
 -> APPROVED -> EXECUTION_READY -> RUNNING
 -> OBSERVING -> EVALUATING
    -> GOAL_SATISFIED
    -> DIAGNOSING -> RETRY/RECOVERY_PROPOSED -> 再次人工审批
    -> HUMAN_HANDOFF
```

所有 transition 要求 expected state，command ID 幂等，并写 lifecycle event。终态 `GOAL_SATISFIED`、`SUCCEEDED`、`HUMAN_HANDOFF`、`CANCELED` 不再自动前进。

### Bounded Harness

可选 Harness 是有限状态循环，不是无限 ReAct：

```text
Load durable attempt + lease
 -> build redacted Context v3
 -> choose exactly one ActionEnvelope
 -> validate action/state/capability
 -> persist step/action/model ledger
 -> invoke deterministic planning action handler
 -> update budget and lifecycle
 -> next wake or stop
```

限制由 `AgentHarnessConfig` 固定上界：默认 8 steps、最多 16；最多 6 次模型调用、8 个 action proposal、1 次修复、300 秒、每次 wake 最多 3 steps。Action 只有 `request_decision` 和 `draft_plan`。provider 失败时 Harness 停止，不悄悄回退到另一模型行为。

### Pipeline DAG

Pipeline node 使用 `depends_on` 建 DAG，Runtime 负责拓扑顺序、subject fan-out 和终态聚合。可并行的是相互独立的 subject node；共享 dataset/group node 和依赖链必须串行。恢复不是在 DAG 内任意回溯，而是 Observation/GoalEvaluation 后生成新的、受审批的 RecoveryProposal/child ticket。

### 当前多 Agent 边界

当前工作树新增了阶段十四 G0 评估组件：固定 science/safety/completeness 三种只读 reviewer、脱敏 `AgentReviewRoleContext`、严格 structured finding adapter、纯确定性 aggregator、隔离临时 workspace runner 和 append-only bundle。`specs/阶段记录/阶段十四/生产多Agent架构/` 明确标记“G0 可启动、G1 生产编码未授权”；这些模块尚未接入生产 lifecycle，不能称为生产多 Agent。

## 8. Prompt 与 Context 设计

项目存在三个相关但不同的 prompt 路径。

1. **Planner Prompt**：`planner/llm_provider.py:build_planner_prompt()` 将可执行 Tool Catalog、goal 和 constraints 拼成严格 JSON pipeline 要求。固定规则禁止发明 node；动态内容是 catalog、goal、约束。temperature 为 0.1，输出上限来自 Agent model config。
2. **Harness Action Prompt**：`planner/agent_model_adapter.py` 固定 system prompt 为 advice-only、禁止批准/执行/写文件/调用工具/发命令；动态内容只有已脱敏 Context v3、一个产品 skill 的 working procedure 和 `ActionEnvelope` JSON Schema。temperature 为 0。
3. **旧 Advisor Prompt**：`src/backend/app/advisor/` 为 protocol/error/QC/parameter/docs 问答提供另一套 `MEDIMAGE_LLM_*` 配置与 prompt；失败可给确定性建议。它不属于主 Agent execution chain。

Context v3 由唯一 `HarnessContextBuilder` 生成，最多 32 KiB，固定顺序为 goal、policy、project_evidence、decision_state、plan_state、execution_state、latest_observation、last_action_result、memory_context、budget。必需 section 缺失时不调用 provider；超预算时按固定优先级整段删除 optional section，必需 section 本身超限则安全停止，不做不可审计的字符串截断。

Builder 不打开 raw image/full log，过滤 secret、absolute path、rawdata/image/DICOM/NIfTI/transcript/prompt/log 类字段。每个 section、整体 context、evidence refs、policy、prompt、skill 和 model profile 都有稳定 hash。项目没有对任意历史聊天做摘要；上下文控制依赖结构化投影、条目上限和整段裁剪。

## 9. Tool / Function Calling 机制

“Tool”在本项目中分两层：

- **Planner Tool Catalog**：`build_tool_catalog()` 从 canonical `NodeContract` 生成只读能力清单，包含 node id、backend、approval、risk、tags；它只帮助规划，不执行 runner。
- **Runtime Node Runner**：每个插件目录暴露 `REGISTRY: dict[node_id, runner]`，`create_registry()` 合并并拒绝重复 ID。执行前 `NodeContract` 校验参数和路径，再由 Gateway 授权后的 runtime 调 runner。

LLM 只会产生 node ID/params 或 Harness 的有限 Action；Pydantic 与 plan validator 拒绝未知字段、未知 node、非法依赖和危险参数。Tool result 不以自由文本回灌，而被持久化为 step result、run state、artifact、Observation 和 GoalEvaluation，再经 Context builder 选择性投影。

失败策略是结构化传播：参数/路径错误在 runner 前阻断；runner 失败写终态和 failure record；subject 失败不进入下游；Gateway outcome 不确定时不重放；Harness 非法输出最多修复一次。外部 MATLAB/SPM/DPABI node ID 虽保留 contract/preview 语义，但 `create_registry.py` 将生产执行映射到 fail-closed blocker。

## 10. Memory 与状态管理

### 桌面与生命周期状态

`services/mock_store.py:SQLiteDesktopStore` 是当前项目、Reviewed Plan、RunLink、Execution Ticket、Gateway dispatch、sandbox attempt、Agent lifecycle/outbox/Harness/Observation/Recovery，以及 Memory consent/outbox/forget ledger 的长期权威 SQLite。文件名仍叫 `mock_store.py` 是历史遗留；默认库为 `outputs/work/desktop/desktop_state.sqlite`，真实桌面默认空库，只有显式 demo flag 才播种样例。

记录多采用“索引列 + versioned JSON payload”，并用 `RLock` 和 SQLite transaction 保证单进程原子性。scheduler 使用 durable outbox 与 lease，command ID/唯一索引实现幂等；读模型不写状态。

### 长期 Memory Domain

`MemoryRepository` 使用独立 `memory_state.sqlite`，schema `memory-store-v1`，WAL、`secure_delete` 和 FTS5。表覆盖 candidate、item、revision、source、event、command、tombstone、job、watermark、consolidation run、lease。安装级 enabled/generation/use/LLM extraction/LLM consolidation/projection 六类 gate 默认关闭，项目还需 consent。

Memory 读取经 `MemoryRetrievalService` 生成项目隔离的 `MemoryContext`；PlanningRequest 和 Approval Summary 绑定实际 context hash。写入经 source outbox、candidate、人工 accept/reject、consolidation；forget 清除明文、写最小 tombstone/ledger，阻止旧 source 自动重建。Memory 只能给 constraint/suggestion/evidence ref，不能改变审批、执行权限、环境事实或科学等级。

### 其他状态

`runtime/state_store.py` 保存 `state-store-v2` node/pipeline JSON；原生预处理保存 run manifest、progress、artifact registry、QC/provenance 和数值文件。`memory/session_db.py` 还有较早的 runs/nodes/errors/FTS operational session 库，用于历史运行检索，不是长期研究记忆权威。项目没有 Redis 或向量数据库。

## 11. 数据结构与数据流

| 数据结构 | 作用 | 主要转换 |
|---|---|---|
| `ProjectDetail` / dataset index | 项目边界与输入证据 | raw directory → inventory/source refs |
| `EvidenceSnapshot` | 规划时冻结的事实、缺口、warning | project/store records → redacted facts/hash |
| `PlanningRequest` | 一次规划的完整输入身份 | goal + evidence + answers + memory + model profile |
| `ReviewedPlanRecord` | 已审阅候选 DAG 与 provenance | planner output → validator → persistent record |
| `GoalContract` | 成功判据和评估策略 | goal/plan → criteria/hash |
| `ApprovalSummary` | 用户真正批准的稳定摘要 | plan + scope + env + memory + sandbox |
| `ExecutionTicket` | 一次性服务端执行能力 | approval binding → frozen scope/policy |
| `RunLinkRecord` | task/plan/run/dispatch 对齐 | reviewed execution → project Runs |
| node/run state | 运行时进度与终态 | runner transitions → atomic JSON |
| artifact/provenance | 可重载结果与来源 | numerical kernel → file/checksum/params/backend |
| `ObservationRecord` | 执行事实的安全汇总 | run/artifact/log facts → evaluator input |
| `GoalEvaluationRecord` | 目标是否满足 | observation + GoalContract → verdict/gaps |
| `MemoryContext` | 可选历史建议 | accepted memory items → bounded planning context |
| `AgentTaskResponse` | UI 读模型 | lifecycle + plan + run + recovery → public state |

数据不是“request → LLM text → response”的直线，而是多次冻结和复验：输入目录先变成登记证据，证据变成 PlanningRequest，候选 plan 变成 Reviewed Plan，审批变成 Ticket，Ticket 才能变成 Run；Run 的数值文件、状态和 checksum 再变成 Observation、GoalEvaluation 和 UI 结果。中间产物的意义是让每个权限提升和科学结论都可定位、可重启恢复、可人工复核。

## 12. 模型调用设计

主 Agent 支持两个 provider：

- `rule_based`：默认且无需网络。Harness 只选择 `DraftPlanAction`，实际规划仍由确定性 `GoalPlanningService` 完成。
- `openai_compatible`：显式启用并提供 model、base URL、API key 后，调用 `/chat/completions`。API key 使用 `SecretStr`，不进入 public config、日志、审批或报告。

Planner 调用 temperature 0.1；Harness Action 调用 temperature 0 和 JSON object response format。`max_output_tokens`、timeout 配置来自 `AgentModelRuntimeConfig`；当前 planner HTTP 实现实际把 timeout 固定为 60 秒，没有完全使用配置值，这是实现偏差。没有 streaming。Planner 对 JSON/schema 错误可用同一 goal/catalog 做一次修复；Harness 由 budget 控制最多一次修复。provider/network 失败返回安全 error code，不自动切换到不同 provider。

旧 advisor 子系统独立读取 `MEDIMAGE_LLM_*`，默认模型名/temperature/HTTP 实现与 Agent model stack 不同。它是咨询 API，不承担 Planner/Executor 角色；这也形成了双模型配置栈的维护债务。

阶段十四 G0 `StructuredAgentModelAdapter` 只定义 reviewer provider protocol、最多 8 条 `AgentReviewFinding` 和 metadata 校验；当前项目中无法确认任何获准真实 provider 或生产 Team runtime 已接入。

## 13. 配置系统

配置来源包括：

- 环境变量：`MEDIMAGE_*` 和前端 `VITE_API_BASE_URL`；
- 项目 YAML：`project_config.yaml`，定义 runtime dirs、third-party 和 safety；
- pipeline YAML：DAG nodes、params、execution config；
- Python/Pydantic config：`ConfigService`、`ServerConfig`、`MemoryConfig`、`AgentHarnessConfig`、`AgentModelRuntimeConfig`；
- manifests/lockfiles：`pyproject.toml`、requirements、npm package/lock、Electron builder；
- CLI：uvicorn、Agent evaluation、packaging/smoke scripts。

优先级不是通用多层 merge：server/Memory/Harness/model 直接从 environment；项目设置从明确传入的 YAML；前端 API base URL由 Electron preload 或 Vite env 提供。无效整数通常回落到保守默认值，boolean 默认 false。

关键开关包括 `MEDIMAGE_ENABLE_REVIEWED_EXECUTION=0`、Memory 六 gate、Harness/model enable、Agent approval token/actor、desktop session token、rate limit 和外部工具开关。Electron 不主动打开真实执行 gate，只注入每次启动的 approval/session 身份。

已确认配置偏差：`.env.example` 包含 `MEDIMAGE_AGENT_HARNESS_MAX_RECOVERY_ATTEMPTS`，但 `AgentHarnessConfig.from_env()` 未读取该项；`MEDIMAGE_WORK_DIR/REPORT_DIR/LOG_DIR/DERIVATIVES_DIR` 也不是 `ConfigService` 的全局 runtime 权威，真实执行以 project YAML 为准。

## 14. 日志、可观测性与中间结果

后端 `setup_logging()` 输出 JSON 到 stderr/stdout stream，级别由 `MEDIMAGE_LOG_LEVEL` 控制；没有通用 rolling file handler。Request middleware 记录 method、path、status、duration、request ID，并返回 `X-Request-ID` 和 `X-Response-Time-ms`。应用异常以 `MedImageError` 的 code/message/details 结构返回；未处理异常只向客户端给通用 500，详细堆栈留在日志。

模型完整 prompt/response 不写普通日志。Harness 持久化的是 canonical request hash、context hash、response hash、token、latency、provider request ID、repair/network 标记和 redacted step/action ledger。阶段十四 G0 model-call record也明确不保存 prompt/body。

执行链路可由下列证据恢复：Reviewed Plan、Approval Summary、Execution Ticket events、Gateway dispatch events、RunLink、node state、pipeline summary、artifact registry、audit record、Agent lifecycle events、Harness trace、Observation、GoalEvaluation、Recovery records。Electron 另将 sidecar stdout/stderr 写到用户 workspace 的 `backend-sidecar.log`。因此可以重建“发生了什么”，但不能从普通日志恢复被有意删除的完整模型敏感上下文。

## 15. 异常处理与容错机制

| 错误类型 | 当前策略 |
|---|---|
| 非法输入/schema | Pydantic/validator 拒绝，结构化 error code，不进入业务副作用 |
| 路径越界/rawdata 写 | project path check、NodeContract capability enforcement、ticket roots、sandbox 多层阻断 |
| LLM 网络/解析失败 | 网络错误直接安全失败；JSON/schema 最多一次 repair；无隐式 provider fallback |
| Tool/node 失败 | 先写 RUNNING 再写 FAILED；记录 failure/provenance；失败 subject 不进入下游 |
| 审批/计划漂移 | summary/plan/memory/environment/scope hash 不一致即拒绝，需重新审阅 |
| Ticket 过期/已消费 | Gateway 拒绝；过期需新计划/新审批，不复用历史许可 |
| dispatch 结果不确定 | `GATEWAY_DISPATCH_OUTCOME_UNKNOWN`，要求检查已持久 dispatch，不自动重试 |
| Agent scheduler crash | durable outbox + lease + startup bounded recovery；command ID 防重复 |
| 运行失败 | Observation → deterministic GoalEvaluator → Diagnosis/RecoveryProposal；再次人工审批后才 recovery |
| 状态/文件部分写 | SQLite transaction、atomic JSON、同目录 replace、checksum/reload validation |
| 桌面 sidecar 异常 | health timeout 显示错误页；Electron 退出终止 sidecar process tree；sidecar 监视 parent PID |

`AgentInvariantChecker` 在启动时对最多 200 个 active lifecycle 做只读检查，发现问题只记录 warning，不静默修复。GET/list 接口不触发 reconcile，避免读请求改变业务状态。

## 16. 并发、异步与性能设计

FastAPI route 大部分是同步函数，I/O/科学计算也主要走同步 service。Agent planning 用单进程 daemon thread 加速 durable outbox，每次 claim 一项；Reconciler 的 bounded monitor 用 thread 和按 lifecycle lock 防止重复 owner。

Pipeline Runtime 可用 `ThreadPoolExecutor` 并行 subject node；完整 native preprocessing service 对独立 subject 使用 `ProcessPoolExecutor`，避免重 CPU 工作受 GIL 限制，并控制每个 worker 的 BLAS/thread budget。GPU kernel通过可选 CuPy，resource planner 决定 worker 数和 backend；CPU 是可用基线。

前端轮询是串行且可终止的：Agent/Project Runs 通常 3 秒；Execution Graph 失败时指数退避到 15 秒；native preprocessing 视图 5 秒。`AbortController` 和 generation 防止项目切换后旧响应覆盖新状态。

潜在瓶颈是：单个 `SQLiteDesktopStore` 文件承载很多领域；大项目 artifact/JSON 扫描；同步 LLM/HTTP；部分 route/service 巨大；subject 并行可能同时竞争磁盘。当前代码有 lock、lease、worker cap 和 atomic write，但没有分布式任务队列，也没有横向多进程一致性方案。

## 19. 核心技术设计总结

1. **Plan 与 Execute 硬分层**：LLM 只能形成候选，validator/Approval/Ticket/Gateway 才能逐级提升权限。它解决自然语言不可直接信任的问题。
2. **Hash-bound Approval**：用户批准的是具体 plan、memory、环境、scope 与 sandbox policy，而非一次永久授权；任何漂移都要求重审。
3. **唯一 Gateway + capability ticket**：所有真实执行共享一个入口，ticket 一次性消费且 dispatch 幂等，消除 route/service 旁路。
4. **Node Registry 与 NodeContract 分离**：runner 提供实现，contract 提供能力/参数/路径语义，Tool Catalog 只是只读投影；注册不等于可执行。
5. **持久 Agent 状态机 + durable wake**：命令、状态、事件、outbox、lease 都可重启恢复，GET 不产生副作用，避免 UI 驱动状态机。
6. **Canonical scientific kernel + artifact truthfulness**：service/runner 复用同一 kernel；结果必须有真实文件、checksum、shape/dtype、params/backend/provenance。
7. **Purpose-scoped Context v3**：模型只看到固定、脱敏、有限的结构化 section，每个输入可追踪 hash，避免全项目上下文泄露。
8. **项目隔离 Memory Domain**：独立 SQLite、默认全关、consent/outbox/tombstone，把记忆变成可撤销建议而非系统权限。

## 20. 项目的技术亮点

### 工程设计亮点

- Approval Summary → Execution Ticket → Gateway 的连续 binding 较完整，尤其处理了 dispatch outcome unknown 而不盲目重试。
- rawdata 保护不是单点判断，而是项目创建、approval scope、ticket roots、NodeContract、runtime path enforcement 和 sandbox 的分层防线。
- Agent lifecycle、wake outbox、Harness step、run/artifact 和 recovery 证据均持久化，重启后仍能解释任务处于何种状态。
- 前端 controller 明确处理 stale response、终态停轮询、project/run identity 校验和结构化错误，不用本地状态替代后端事实。
- Desktop sidecar 使用 localhost、动态 token、parent watchdog、context isolation 和 renderer health smoke，桌面安全边界比普通“Electron 内开一个 server”更明确。

### 算法与 Agent 亮点

- Harness 把模型能力压缩为两个 typed Action，而不是暴露任意 tools；Skill manifest、Context policy、Action schema 和 model profile 均进入 hash。
- GoalContract 将“pipeline 执行完”与“研究目标满足”分离，运行后仍需 Observation 与确定性 evaluator 判断。
- 原生 pipeline 将每个科学阶段的 artifact/provenance/QC 独立保存，可区分 computed、simplified、metadata-only 和 validated。
- ReHo CPU 使用 tie-corrected Kendall W；检测到 GPU tie 风险时回退 CPU，没有为了 GPU 标签牺牲科学语义。
- 多 Agent 没有因架构吸引力提前上线，而是先做固定角色、脱敏 replay、隔离 runner、统计 Gate 和人工 capability approval，当前仍明确停在 G0。

## 报告结论

MedImage Agent 当前已经不是演示级“LLM 生成 pipeline”项目：它具备真实的持久 Agent 生命周期、hash-bound 人工审批、capability ticket、唯一执行网关、DAG runtime、原生科学 kernel、artifact/provenance、项目级 Memory 和桌面交付链。它最成熟的部分是执行治理与证据链；最需要克制表达的部分是简化预处理算法、GPU/外部工具、Docker 部署、完整 GUI E2E 和尚停在 G0 的生产多 Agent。

本文对照 `AGENTS.md`、`PROJECT_STATE.md`、系统架构、能力矩阵、安全边界、当前阶段十四方案、源码和测试后确认：rawdata 只读、LLM advice-only、Approval 顺序、唯一 Gateway、Memory 非权限源和科学等级真实性在主链上都有明确实现锚点；同时也确认若干历史文档、部署配置和 legacy API 表面与当前真实实现不完全一致，已在 H-01～H-15 中逐项列出。
