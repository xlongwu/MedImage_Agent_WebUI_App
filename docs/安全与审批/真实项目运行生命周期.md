# Real Project Run Lifecycle

This document describes the reviewed plan, run link, audit, and artifact
lifecycle for real BIDS/rawdata projects in the desktop workflow. It is for
future developers and coding agents. It is not a feature plan, and it should
not be read as permission to add autonomous execution or bypass review.

The current delivery state is a safe, project-scoped, plan-then-execute loop:
rawdata is referenced read-only, project context is bound before review, the
reviewed plan is persisted, execution is gated, every real run is linked back
to the reviewed plan, and artifact reads are scoped by project and run.

## Core Concepts

**Project**

A dashboard project represents one real research workspace. It has a stable
`project_id`, a managed `project_dir`, a referenced `rawdata_dir`, and metadata
stored in the desktop SQLite store. Project creation must keep `project_dir`
separate from `rawdata_dir`.

**Project config**

`project_config.yaml` is the executor-facing config generated inside the
managed project directory. It records `project.project_id`, project root,
referenced rawdata, the generated dataset index, third-party tool locations,
runtime directories, and safety flags such as `rawdata_readonly: true`.

**Dataset index**

`dataset_index.json` is generated by dataset inspection under the managed
project data directory. It indexes subjects, sessions, anat/func availability,
and completeness diagnostics. Subject-level reviewed plans should use this
project dataset index rather than walking rawdata directly.

**Reviewed plan**

A reviewed plan is the plan candidate after project context has been applied
and validation has passed for review. For created real projects, the plan must
carry a `project_context` block and node params must point at the selected
project's rawdata and dataset index where required.

**Plan hash**

The plan hash is a deterministic SHA-256 hash of the reviewed plan payload. It
is used to detect whether the submitted execution plan is the same plan that was
saved for review.

**reviewed_plan_id**

`reviewed_plan_id` is stable for the `(project_id, plan_hash)` pair. The ID is
stored in SQLite and used to retrieve the reviewed plan snapshot and to bind
future run links. The same plan content in different projects gets a different
project-scoped identity.

**Approval Gate**

The Approval Gate runs between validation and execution. It checks that
approval exists when required, required nodes are approved, rejected nodes are
absent, manual/GUI nodes are not executed, and high-risk backends such as
MATLAB/SPM/DPABI have explicit node and backend approval.

For the project-scoped Agent Task command path, validation and Reviewed Plan
persistence happen before the user decision, but the execution dry-run happens
only after the unchanged Approval Summary is approved. That dry-run is bound to
the approval; failure stops before Execution Ticket dispatch. Plan-only tasks
do not enter this execution sequence. Legacy/manual dry-run endpoints are
inspection surfaces and do not themselves authorize dispatch.

**Audit record**

An audit record is an immutable JSON record for a review or execution event. It
contains the plan, validation, approval, Approval Gate result, result summary,
actor, source, and stable hashes for traceability.
The immutable authority remains under the application audit root. Reviewed
execution also writes an atomic, schema-versioned project projection under
`project_dir/reports/audit_records/` so the exact selected run can expose its
audit evidence without granting Runs arbitrary access outside project roots.

**Pipeline YAML**

The pipeline YAML is the executor-compatible YAML produced from a reviewed plan
by the plan adapter. It is written only after validation, approval, policy, and
audit preconditions pass. It is the input consumed by the deterministic
Pipeline Runtime.

**Run link**

A run link is the SQLite record that connects one execution attempt to a
project and reviewed plan. It stores `project_id`, `reviewed_plan_id`,
`run_id`, `pipeline_path`, `summary_path`, `audit_id`, status, timestamps,
warnings, and executor payload.

**run_link_id**

`run_link_id` is a UUID-based identifier for a single run link row. It is
unique per execution attempt and is created before the executor is called.

**run_id**

`run_id` is a UUID-based execution identifier injected into the pipeline YAML
before writing. The SQLite `run_links.run_id` column is unique, and repeated
executions of the same reviewed plan receive different `run_id` values.

**Summary JSON**

The executor summary JSON is written under the project runtime work directory,
normally `work/pipeline_runs/<run_id>/summary.json`. It summarizes run status,
node counts, node state paths, errors, scheduler metadata, and timestamps.
Read-side normalization accepts the runtime field names `ended_at` and
`nodes_success` as well as the older preview aliases.

**Goal Contract**

The Goal Contract is finalized inside the immutable Reviewed Plan and binds the
reviewed goal, subject/session scope, required artifact types, capability
threshold, limitation policy, plan hash, and evaluator version. Native full
preprocessing contracts derive their required numerical artifacts from the
explicit reviewed `stage_overrides`; outputs of disabled ALFF/fALFF/ReHo/FC
stages are not counted as missing. A singular native `subject_id` and normalized
`subject_scope` both bind the evaluated subject scope. Already reviewed legacy
plans without explicit stage scope keep their original full-output semantics.
Builder output is only a visible, editable candidate. Saving a plan without
explicit human review produces `NEEDS_GOAL_REVIEW`; dry-run and execution reject
that snapshot with `REVIEWED_PLAN_NEEDS_GOAL_REVIEW`. The reviewer must confirm
the candidate and save it with `reviewed_actor`, which creates a new immutable
`REVIEWED` snapshot and hash-binds the finalized Goal Contract to the exact
normalized plan. The frontend must never infer or auto-accept this review.

**Artifact**

An artifact is a project output or execution file discovered from the run link,
summary JSON, or node state JSON. Examples include pipeline YAML, summary JSON,
QC JSON, markdown reports, CSV tables, logs, images, NIfTI files, and MAT files.
Only safe text-like formats are content-previewed.

**Artifact ID**

`artifact_id` is a deterministic ID derived from the resolved artifact path. The
frontend and API never accept an arbitrary path for artifact preview; they use
`project_id + run_id + artifact_id`, and the backend rediscovers and matches
the artifact inside the run scope.

## End-to-End Flow

1. **Create Project**

   The user selects a local BIDS-like `rawdata_dir` and calls
   `POST /api/projects/create`. The backend rejects dangerous roots, non-existing
   paths, files, and any `project_dir` that overlaps rawdata. The project is
   added to the desktop SQLite store and desktop config.

2. **Create Agent Task**

   `POST /api/projects/{project_id}/agent/tasks` creates a persisted Agent
   lifecycle. Planning advances only through the durable scheduler and produces
   a Reviewed Plan or a structured request for input; there is no standalone
   planner HTTP endpoint.

3. **Apply Project Context**

   Before Plan Review, `load_project_context` resolves the persisted project,
   `project_config.yaml`, rawdata, and dataset index. `apply_project_context_to_plan`
   injects `project_context`, sets data inspection params, and binds
   subject-level nodes to the dataset index. Created projects may not use
   `create_synthetic_bids`.

4. **Save Reviewed Plan**

   `POST /api/projects/{project_id}/plans` validates the submitted plan against
   the selected project context, computes the plan hash, upserts the SQLite
   reviewed plan index, and writes the first immutable project-local snapshot at
   `project_dir/plans/<reviewed_plan_id>.json`. When the request does not include
   an explicitly reviewed `goal_contract_candidate`, the snapshot remains
   `NEEDS_GOAL_REVIEW`.

5. **Review Goal Contract**

   The technical review console projects the persisted candidate, lets the user
   inspect or edit its goal, scope, criteria, evidence and limitations, and
   requires an explicit confirmation. It then posts the candidate with
   `reviewed_actor`; the backend validates reachability and goal consistency and
   returns a new immutable `REVIEWED` plan ID. Dry-run remains disabled until
   this reviewed snapshot is active.

6. **Approval / Audit**

   `POST /api/plans/execute-reviewed` revalidates the reviewed plan and reruns
   the Approval Gate. For `dry_run=false`, execution also requires
   `MEDIMAGE_ENABLE_REVIEWED_EXECUTION=1`, `confirm_execution=true`,
   `persist_audit=true`, and an approved gate result. Audit JSON is written
   before the executor is called.

7. **Execute Reviewed Plan**

   The endpoint resolves the saved reviewed plan for created projects and checks
   that the supplied `reviewed_plan_id`, plan hash, project ID, and project config
   match the persisted record. At this stage the reviewed plan is verified, not
   silently modified.

8. **Create Run Link**

   A new `run_link_id` and `run_id` are generated. The `run_id` is injected into
   the adapter pipeline before the pipeline YAML is written. The run link is
   inserted into SQLite before the executor starts; if this write fails, execution
   is blocked.

9. **Run Pipeline**

   The Pipeline Runtime receives the generated pipeline YAML and
   `project_config.yaml`. It executes registered node runners only. It writes node
   state JSON under `work/states/<run_id>/...`.

10. **Write Summary**

   The executor writes `work/pipeline_runs/<run_id>/summary.json` and returns its
   `summary_path`. The run link is finalized with status, summary path, audit
   payload, executor result, and warnings.

11. **Discover Artifacts**

    `GET /api/projects/{project_id}/runs/{run_id}/artifacts` discovers files from
    `run_link.pipeline_path`, `run_link.summary_path`, summary fields such as
    `outputs`, `artifacts`, `reports`, `report_paths`, `node_states`, and nested
    node state outputs/logs/result JSON.

12. **Preview Artifacts**

    `GET /api/projects/{project_id}/runs/{run_id}/artifacts/{artifact_id}` first
    validates the artifact ID, rediscovers the run-scoped artifacts, matches the
    ID, and only then returns a bounded preview or metadata-only response.

## API Map

**POST `/api/projects/create`**

Creates a managed real project from a local BIDS/rawdata directory. Generates
`project_config.yaml`, optionally generates `dataset_index.json`, updates
desktop config, and persists project metadata in the dashboard store.

**GET `/api/projects`**

Lists dashboard projects from the SQLite desktop store.

**GET `/api/projects/{project_id}`**

Returns project details, including metadata such as `project_dir`,
`rawdata_dir`, `project_config_path`, `dataset_index_path`, and diagnostics.

**POST `/api/projects/{project_id}/agent/tasks`**

Generates a plan from a goal. Requires explicit project context and applies that
context before returning the reviewed-plan candidate.

**POST `/api/projects/{project_id}/plans`**

Persists a reviewed plan for a project. Validates that the plan matches the
project context, computes identity, updates the SQLite index, and writes the
project-local snapshot.

**GET `/api/projects/{project_id}/plans`**

Lists reviewed plans for a project, newest first, with snapshot warnings if the
snapshot file is missing.

**GET `/api/projects/{project_id}/plans/{reviewed_plan_id}`**

Returns one reviewed plan if it belongs to the requested project.

**POST `/api/plans/execute-reviewed`**

The execute-reviewed endpoint. In dry-run mode it validates readiness and may
persist audit if requested. In execution mode it enforces env, confirmation,
audit, project context, reviewed plan identity, validation, Approval Gate, plan
adapter, safe allowlist, pipeline YAML write, run link persistence, audit write,
and only then calls the Pipeline Runtime.

**GET `/api/projects/{project_id}/runs`**

Lists run links for a project. Accepts optional `reviewed_plan_id` filtering.

**GET `/api/projects/{project_id}/runs/{run_id}`**

Returns the run link plus a safe summary preview from the linked summary JSON.
Summary reads are constrained to project output roots and reject rawdata paths.

**GET `/api/projects/{project_id}/runs/{run_id}/artifacts`**

Discovers run-scoped artifacts from the run link, summary JSON, and node state
JSON. Returns artifact metadata, warnings, previewability, QC summaries, and
error excerpts where safe.

**GET `/api/projects/{project_id}/runs/{run_id}/artifacts/{artifact_id}`**

Returns a bounded artifact preview for the matched run-scoped artifact. It does
not accept file paths. JSON, CSV, markdown, text, and log files may be previewed;
binary, NIfTI, and MAT files are metadata-only.

## Storage Map

**Dashboard SQLite store**

Default path: `outputs/work/desktop/desktop_state.sqlite`, overrideable with
`MEDIMAGE_DESKTOP_STORE_PATH`.

The store is an index for:

- `projects`: dashboard project payloads and metadata.
- `imports`: referenced rawdata locations.
- `reviewed_plans`: project-scoped reviewed plan index keyed by stable plan
  hash.
- `run_links`: execution history keyed by `run_link_id` with unique `run_id`.

The module name `mock_store.py` is historical. The implementation is currently
`SQLiteDesktopStore`.

**Reviewed plan snapshot**

Location: `project_dir/plans/<reviewed_plan_id>.json`.

This is an immutable snapshot for the first saved reviewed plan with that ID.
SQLite is the query index; the JSON snapshot is the project-local evidence copy.

**Pipeline YAML**

Location: `outputs/work/reviewed_pipelines/reviewed_<pipeline>_<timestamp>_<planhash>.yaml`.

This is generated execution input. It is not written to rawdata, derivatives, or
reports, and it is referenced by the run link.

**Audit JSON**

Location: `outputs/reports/audit_records/<audit_id>.json`.

This is an immutable audit artifact containing plan, validation, approval,
Approval Gate result, dry-run or execution-request result, actor, source, and
stable hashes.

**Run summary**

Location: project runtime `work/pipeline_runs/<run_id>/summary.json`.

This is a runtime artifact written by the executor. It records status, node
counts, node state paths, errors, scheduler metadata, and timestamps.

**Node state**

Location: project runtime `work/states/<run_id>/<node_id>.json` for
project-level nodes and `work/states/<run_id>/<subject>/<node_id>.json` for
subject-level nodes.

These runtime artifacts record node status, logs, outputs, metrics, warnings,
errors, result JSON, and return code.

**Native subject progress**

Location:
`project_dir/preprocessing_native_runs/<run_id>/native_full_progress.json`.

The native orchestrator owns this atomic per-subject status projection. Agent
Task observation converts each recorded subject into a subject-level evidence
fact for completed/failed/excluded counts without changing the project-level
Pipeline Runtime node totals. Declared aggregate counts must agree with the
subject map or the observation is marked conflicting.

**Artifact files**

Artifacts may live under project `data`, `work`, `reports`, `logs`, and
`derivatives`, or beside the generated reviewed pipeline YAML. `data` is for
managed project evidence such as `dataset_index.json`; it does not make source
BIDS/rawdata an output. Discovery treats these locations as run outputs or
execution evidence. Rawdata is not an artifact root.

Registered artifact metadata also carries stage capability and limitation
truth. Read-side observation projects `simplified`, `preview_only`, and
`partial` into the terminal result instead of treating reloadable files as
unqualified full computation. A reviewed scientifically `simplified`
limitation is independent from capability: complete, registered, reloadable
numerical evidence remains `computed`, while the limitation stays visible and
prevents a false `validated` claim. `preview_only` and `partial` remain blocked
unless the reviewed Goal Contract explicitly allows them. Metadata-only
reports remain reports; they only lower the goal capability when a Goal
Contract requires that numerical artifact type. Appending actual preprocessing outputs changes
`no_preprocessing_executed` to `false`.

**Project metadata**

Project metadata lives in SQLite project payloads and includes `project_dir`,
`rawdata_dir`, `project_config_path`, `dataset_index_path`, diagnostics,
creation timestamp, and update timestamp.

**Desktop config**

Location: `outputs/work/desktop/config.json`.

Desktop config stores active/recent projects, authorized read-only data
directories, local tool paths, LLM settings with secrets redacted in API
responses, GUI provider settings, and desktop health inputs.

## Safety Model

Rawdata is read-only. Project creation references `rawdata_dir`; it does not
copy or mutate raw input data. Managed paths such as `project_config.yaml` and
`data/dataset_index.json` must be inside `project_dir` and must not overlap
rawdata.

Project context must be injected before review. The reviewed plan snapshot is
the object that execution is allowed to use. If a user edits or regenerates a
plan, it must be saved again and receive the matching identity.

The execute-reviewed stage validates the approved plan. It does not silently
patch missing project context, replace dataset paths, or rewrite approved node
params. Mismatches block execution.

The Approval Gate is mandatory before execution. File-writing, derivatives,
MATLAB/SPM/DPABI, and any execution actions must keep the explicit approval
path. `dry_run=false` also requires env opt-in, confirmation, audit persistence,
pipeline YAML writing, run link persistence, and safe policy checks.

Artifact preview does not accept arbitrary paths. The only supported lookup is
`project_id + run_id + artifact_id`. The backend resolves the project and run
link, rediscovers artifacts, and only previews a matched run-scoped artifact.

Rawdata artifacts must be rejected. Summary paths or artifact candidates inside
rawdata produce warnings/errors and are not previewed.

Out-of-bounds paths must be rejected. Summary and artifact paths must resolve
under the project output roots (`data`, `work`, `reports`, `logs`,
`derivatives`) or the generated pipeline YAML directory. Path traversal and
outside-project references are not valid artifact reads.

Binary, NIfTI, and MAT files are not content-read. They may appear as
metadata-only artifacts with kind, path, size, and timestamps, but preview does
not parse or display their contents.

MATLAB/SPM/DPABI/GPU execution is not part of the current safe smoke scope.
Current safety checks cover deterministic project plumbing, reviewed execution
preflight, safe allowlisted/sandboxed paths, and artifact inspection. Full
external data processing is deliberately out of scope.

Frontend code must communicate through backend HTTP APIs. It must not access the
local filesystem directly. Desktop-only open-path behavior goes through the
desktop bridge when available.

## Frontend Consumption

**AgentWorkspace (default source entry)**

`AgentWorkspace` uses the project-scoped Agent Task controller and
`/api/projects/{project_id}/agent/tasks` command/read-model APIs. It renders the
backend-authoritative lifecycle, one atomic `decision_batch` (one to six items),
the backend-authoritative `automation` level (`A0` through `A4`), the stable
Approval Summary, structured rejections, progress, recovery actions, and
terminal result evidence. `automation.requires_user` and its reason code explain
whether a person must act without trusting frontend-local state. The batch is
submitted as `batch_id + answers[]`;
field rejections preserve the remaining local input and never retry a mutation
automatically. The normal view exposes one current action only. Advanced details
may request the read-only, paginated
`GET /api/projects/{project_id}/agent/tasks/{task_id}/harness` projection, which
contains only redacted step, model-call metadata, action/result, and evidence
references. It never returns prompts, raw responses, credentials, absolute
paths, source images, or full logs. Approving a task never enables reviewed
execution automatically: the unchanged summary/hash, actor and scope are
checked again, then the bound post-approval dry-run must pass before ticket
dispatch.
Terminal subject counts come from persisted native progress when the executor
uses the native full-preprocessing node. Optional absent log excerpts remain
visible in observation completeness but do not turn a fully satisfied,
consistent Goal Contract into a false failure.

**PlanReviewConsole (advanced compatibility surface)**

`PlanReviewConsole` requires a selected real project unless explicit demo mode
is used. It calls the project-scoped Agent Task endpoint with `project_id` and
`project_config_path`, stores the returned project-context-enriched plan through
`POST /api/projects/{project_id}/plans`, lists/restores recent reviewed plans,
checks approval, runs dry-run validation, and calls execute-reviewed with
`confirm_execution=true`, `persist_audit=true`, and `write_pipeline_yaml=true`
for real execution.

If a Reviewed Plan is already owned by an Agent Task lifecycle, this advanced
entry must supply that exact `lifecycle_id`; otherwise the backend returns
`AGENT_LIFECYCLE_ID_REQUIRED` before creating a run, ticket, or second
lifecycle. Agent Task approval and retry therefore remain Agent-workspace
operations. A legacy reviewed plan without an Agent lifecycle may still create
one lifecycle, and its run link is bound to that lifecycle before dispatch.

**RunsWorkspace**

`RunsWorkspace` combines the legacy background-task list with project-scoped
run links from `GET /api/projects/{project_id}/runs`. A persisted project run
replaces any same-ID stale background record, so Agent Task execution remains
visible when the legacy task list is empty. Project-scoped run detail uses:

- `GET /api/projects/{project_id}/runs` for the run list.
- `GET /api/projects/{project_id}/runs/{run_id}` for run detail and summary
  preview.
- `GET /api/projects/{project_id}/runs/{run_id}/artifacts` for artifact
  discovery.
- `GET /api/projects/{project_id}/runs/{run_id}/artifacts/{artifact_id}` for
  preview or metadata detail.

Run selection has a dedicated `run_id` state. It is never passed to the legacy
`/api/tasks/{task_id}` controller. Artifact discovery loads the selected run's
preprocessing registry, project audit projection, QC/report outputs, and
derivatives, rejecting registry entries or preprocessing paths bound to any
other run ID.

`/api/tasks/{task_id}` controller. Artifact discovery loads the selected run's

**Run list**

The run list displays persisted run links and lets the user choose one
execution attempt by `run_id`.

**Run detail**

Run detail displays `run_id`, `run_link_id`, `reviewed_plan_id`, `audit_id`,
status, timestamps, pipeline path, summary path, project directory, warnings,
and run-link payload.

**Summary preview**

The summary preview normalizes safe summary JSON fields into run status,
timestamps, node counts, warnings, outputs, failed nodes, errors, and bounded raw
summary content.

**Key Artifacts**

Key Artifacts highlights summary, pipeline, reports, QC, failed logs, and tables
from the discovered run-scoped artifact set.

**QC/Error Summary**

QC/Error Summary combines run summary health, failed-node information, QC JSON
highlights, error excerpts, artifact provenance, missing artifact state, and
warnings.

**Artifact preview**

The preview pane renders JSON summaries/raw JSON, CSV tables, markdown, text, or
logs when the backend marks an artifact previewable. Otherwise it displays
metadata-only detail and path actions.

**Web fallback vs desktop open path bridge**

In the desktop runtime, `window.medimage.openExternalPath` may open a path. In a
browser/web fallback, the UI does not access the filesystem; it shows a notice
and exposes copyable path text instead.

## Known Limitations

The legacy real-project safe-smoke coverage described in this document does not
exercise MATLAB/SPM/DPABI or GPU execution. Current GPU source and packaged
sidecar evidence is tracked separately in `PROJECT_STATE.md` and the capability
matrix; it must not be inferred from this legacy smoke.

There is no NIfTI viewer. NIfTI artifacts are metadata-only in this lifecycle.

There is no complete QC dashboard. Current UI shows summary, QC highlights,
errors, provenance, and previews, not a full analytical QC workspace.

There is no report editor. Report artifacts are discoverable/previewable when
safe, but editing reports is out of scope.

The external BIDS smoke requires `MEDIMAGE_EXTERNAL_BIDS_SMOKE_DIR` and should
be run only against a deliberately bounded read-only test dataset.

The dashboard SQLite store and filesystem artifacts are not a single
transaction. A run link can exist while a summary or snapshot is missing; APIs
surface warnings rather than assuming consistency.

`mock_store.py` remains a historical module name even though it now contains the
SQLite-backed desktop store.

Packaged Electron cannot start when the current Electron runtime installation is
incomplete. Browser/web fallback remains available, but desktop-only open-path
bridges depend on a working Electron runtime.
