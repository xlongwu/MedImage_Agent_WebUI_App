# Capability Matrix

Current as of 2026-08-16. This matrix records the real capability level of
each preprocessing stage in the MedImage Agent pipeline runtime. It is a
record of **current code behavior**, not a roadmap.

When code and documentation disagree, current executable code wins
(see `AGENTS.md` "权威来源"). Update this matrix whenever a stage's
real output level changes.

## Capability Levels

Each stage is classified at exactly one **Capability Level**. Levels are
strictly ordered from least to most real:

| Level | Meaning |
|-------|---------|
| **Contract Only** | Only the request/response schema and safety gate exist. No execution body. |
| **Dry-run** | A dry-run plan or preview is produced without touching the functional input. |
| **Sandbox Scaffold** | Input is copied into a sandbox workspace but no metric is computed. |
| **Metadata Only** | Descriptor files (shape, status JSON) are written; no real numerical artifact persists. |
| **Numerically Implemented** | A real numeric artifact (NIfTI map / `.npy` matrix) is produced by a unified compute kernel and is reloadable. |
| **Reference Validated** | Numerically Implemented **and** validated against an independent reference / golden dataset within tolerance. |
| **Release Ready** | Reference Validated, covered by CI, and the production execution path is enabled by maintainer approval. |

## Validation Status

Separate from capability level, each stage carries a **Validation Status**
describing the state of independent verification:

| Status | Meaning |
|--------|---------|
| **Unvalidated** | Numerically implemented but no independent reference or golden test exists, OR the implementation has known gaps on certain backends (e.g. GPU ties handling). |
| **Needs Verification** | An external tool path (SPM/MATLAB) exists but is not exercised in this environment; not a claim of numerical correctness. |
| **Golden Validated** | Validated against committed golden `.npy` fixtures via `tests/test_scientific_golden.py` or `tests/golden/test_algorithm_golden.py`. |
| **Reference Validated** | Golden Validated **and** validated against an external established implementation, trusted reference software, or independently produced reference dataset (not merely an in-repository reference). |
| **E2E Validated** | Validated end-to-end against DemoData via integration smoke test (default-skipped in CI). |

## Availability

Describes whether and how the stage can be exercised:

| Availability | Meaning |
|--------------|---------|
| **Default-Blocked** | Requires explicit env flags and/or external tools to run; never executes by default. |
| **Sandbox-Only** | Execution confined to sandbox workspace; no production path. |
| **CI-Covered** | Golden/regression tests run in the backend CI job on every push/PR. |
| **Manually Release-Validated** | Requires a persisted human release approval record before execution. |

### Native full validation note

Phase 07 adds local synthetic native full validation for BIDS-to-FC, a
post-DICOM-conversion handoff check, artifact integrity, report consistency,
and status truthfulness. These tests validate that the native full runner
produces reloadable artifacts and does not call MATLAB, SPM, DPABI, or runtime
`third_party` `.m` files. They do not upgrade simplified or affine-only stages
to **Reference Validated**, because no approved external SPM/DPABI or
independent reference fixture was supplied.

The Agent terminal evaluator preserves that distinction. A minimal native run
whose required numerical outputs are registered, reloadable, and provenance
bound is `computed` even when realignment or another stage is truthfully marked
`simplified`. The simplified flag remains a reviewed limitation and prevents
promotion to `validated`; it is not a reason to relabel real numerical output
as `metadata_only`. Preview-only or partial evidence is still rejected unless
the immutable Goal Contract explicitly permits it.

### ACPC alignment note

Automatic ACPC anterior-commissure localization produces a computed,
reloadable derivative only from
one registered 3D T1w source and writes only below the approved project
`derivatives/` root. The reported landmarks are deliberately named
`estimated_ac_mm` and `estimated_pc_mm`: the former is the primary anterior-
commissure localization result, while the latter is retained only to define
the AC-PC axis. Both are template-back-projected estimates, not direct manual
anatomical labels. QC requires optimizer
convergence, non-degraded normalized mutual information of at least 1.0,
foreground AC/PC estimates, right-handed rigid transforms, and a reloadable
output. Any failed check leaves final artifacts unregistered and requires
human review. The capability remains `computed` until an independently
annotated T1w reference set reports AC/PC error, failure rate, 95th percentile,
and QC false-positive/false-negative evidence.

### Native default workflow note

The source UI now defaults to an Agent-first projection over the existing
reviewed lifecycle. This changes interaction and orchestration, not any
scientific capability level in the matrix. The Agent may prepare a deterministic
stage graph, stop for unresolved scientific choices, and expand one approval
summary into the existing granular confirmations. Actual computation still
requires the same Approval Gate, Execution Ticket, registered runner, artifact
registration, reload validation, and capability evidence. Packaged visible-UI
validation of this new interaction remains separate from source validation.
The optional controlled Harness is likewise orchestration rather than a
scientific-computation capability; its source/test/release evidence is tracked
separately and cannot raise a numerical level in this matrix.

The Harness automation boundary is fixed at A0/A1: it may read redacted,
allowlisted evidence and persist only managed control-plane state or advisory
decisions/explanations/recovery proposals. A2 execution is performed only by
the deterministic post-approval Ticket/Gateway path; A3 scope changes require
a new plan and approval; A4 rawdata writes, arbitrary execution, bypasses and
clinical conclusions are permanently unavailable. This governance does not
change the listed scientific capability level or validation status.

The reviewed preprocessing preview, stage catalog, reviewed execution
orchestrator, Tool Catalog, Approval Gate, native API routes, and frontend
workflow are native-first as of 2026-06-28. They do not default to `spm_*`
execution nodes. External SPM/DPABI backends remain explicit opt-in paths that
require approval, environment gates, audit evidence, and safe-path handling.

The DICOM-to-native-preprocessing path remains a conversion-domain handoff.
Before native preprocessing, the reviewed execution ticket authorizes the
in-project converter to execute a persisted conversion package when necessary,
or to reuse a previously verified conversion manifest, provenance, audit, and
artifact registry. Native preprocessing resolves its subject inputs from that
registry by conversion run id. No external process is launched.

### DICOM Conversion note

DICOM Conversion is classified as **Reference Validated** (not Release Ready)
because the production execution path remains guarded by release flags,
approval/readiness evidence, audit, safe paths, rollback checks, and native
Python dependency availability. The supported converter is implemented inside
this project and does not require dcm2niix, MATLAB, SPM, or DPABI. The opt-in
three-subject smoke test
(`tests/integration/test_dicom_conversion_internal_funraw_t1raw_smoke.py`) is
default-skipped in CI and was executed locally against DemoData. The packaged
backend sidecar/API three-subject workflow has also been validated. It is not
"Release Ready" until the default-blocked constraint is lifted by maintainer
approval; visible Electron UI E2E remains a separate pending validation layer.

### RC2 capability freeze note

For the `v0.6.0-rc2` convergence window, the capability levels in this matrix
are frozen. Release work may correct defects or evidence, but must not add a new
execution path, scientific algorithm, capability-level upgrade, public API, or
required dependency without reopening scoped capability and scientific review.

The project-scoped Memory Domain is an engineering context-management feature,
not a scientific compute capability. Its implementation and tests do not
upgrade any algorithm, backend, validation, execution, or clinical capability
level in this matrix. Scientific memories remain advisory and require a fresh
task-level confirmation.

### Reviewed preprocessing pipeline note

The reviewed preprocessing orchestrator and frontend reviewed flow are
implemented as of 2026-06-28. They provide a gated request path, stage status
timeline, preprocessing-run creation from registered converted input, artifact
handoff links, report/validation links, and FC result summary. Registered
realignment outputs now require or produce motion QC artifacts (`motion_qc.json`,
`fd_timeseries.tsv`, and a dataset summary) before nuisance regression can be
treated as available. The default reviewed execution path delegates to native
full preprocessing; this is not a claim that external SPM/MATLAB stages have
run successfully in the local environment. External stages remain
default-blocked unless backend approval, environment flags, and reviewed
registered artifacts support the requested stage.

### FC capability breakdown

The FC entry above covers the **Pearson correlation kernel** only
(`tools/functional_connectivity_compute.py::compute_fc_backend`), which is
Reference Validated via golden regression. The backend FC runner can use a real
atlas only after the atlas is either already in a safe derivatives/work
location or copied from a known repository template source into derivatives
with checksum/provenance. Synthetic x-chunk atlas output remains preview-only
and must not be displayed as formal atlas-grounded FC. Therefore:

| Sub-capability | Status |
|----------------|--------|
| ROI Pearson correlation kernel | Reference Validated |
| Synthetic x-chunk atlas FC preview | Numerically Implemented; preview_only |
| External atlas loading | Numerically Implemented with safe-path, checksum, shape, and affine checks |
| Atlas-grounded subject FC matrix | Numerically Implemented and reload-tested in backend regression tests, including atlas artifact reload |
| Full DICOM-to-reviewed-FC GUI workflow | Ticket-bound conversion handoff implemented; source-level three-subject ALFF/fALFF path demonstrated; atlas-grounded FC and packaged GUI E2E not yet validated |

### ReHo CPU vs GPU validation breakdown

The ReHo entry distinguishes CPU and GPU validation:

| Backend | Validation Status | Notes |
|---------|-------------------|-------|
| CPU (NumPy) | Golden Validated | Kendall's W with ties correction (average ranks + tie factor). Validated against committed golden fixtures and an independent pure-NumPy reference; subject artifact writing uses the canonical compute backend. |
| GPU (CuPy) | Unvalidated | The experimental kernel now implements deterministic average ranks and complete tie correction, but remains opt-in and outside the native full runner until an actual-GPU whole-volume comparison and reviewed real-data release gate pass. Default execution continues on the CPU canonical path. |

### Execution-infrastructure status

The Windows restricted-process provider is safety infrastructure, not a
scientific capability level. Its fixed source and packaged self-tests verify
ACL, environment, timeout, memory and owned-process-tree behavior. Network
isolation remains explicitly `not_enforced`, and MATLAB, SPM, DPABI and other
external scientific nodes remain unavailable. Passing those infrastructure
tests cannot promote any row in this matrix to Numerically Implemented,
Reference Validated or Release Ready.

## Traceability

Each **Numerically Implemented** or higher stage is backed by:

- A unified compute kernel under `src/backend/app/tools/*_compute.py`.
- A sandbox execution service under `src/backend/app/services/preprocessing_*_execution.py` that calls the kernel (no inline math).
- A per-metric status entry in `manifest.json` distinguishing sandbox-prepared vs numerically-computed.
- Golden/regression tests under `tests/test_scientific_golden.py`, `tests/test_scientific_gpu_consistency.py`, and `tests/golden/test_algorithm_golden.py`.
- Native full phase 07 tests under
  `tests/integration/test_native_preproc_bids_to_fc_e2e.py`,
  `tests/integration/test_native_preproc_dicom_to_fc_e2e.py`,
  `tests/integration/test_native_preproc_artifact_integrity.py`,
  `tests/integration/test_native_preproc_status_truthfulness.py`, and
  `tests/golden/test_native_preproc_reference_comparison.py`.
- Pipeline validation reload checks for numeric metric maps and atlas-grounded
  FC artifacts, including ALFF, fALFF, ReHo, atlas, ROI timeseries, FC, and
  Fisher-z outputs.

"Needs Verification" in the Validation Status column means the SPM/MATLAB
external tool path (or an equivalent Python kernel) exists but is not
exercised in this environment; it is not a claim of numerical correctness.
